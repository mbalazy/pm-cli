# Project Manager (`pm`)

Local task tracker and control plane for AI coding agents. Data lives in `~/.claude/pm/` as markdown files with YAML frontmatter. CLI binary: `pm`. MCP server: `pm mcp` (stdio, registered as `pm`). TUI: `pm board` (the user runs it).

**MCP tools** (preferred over CLI): `pm_context` (session start / overview, auto-detects project from cwd), `pm_list_tasks`, `pm_get_task`, `pm_add_task`, `pm_update_task`, `pm_move_task`, `pm_update_project`, `pm_create_project`, `pm_list_projects`, `pm_delete_task`, `pm_journal_list`, `pm_journal_add`. CLI fallback `pm context [project]` prints the same rollup when the running MCP holds a stale binary. `pm_get_task`/`pm_update_task`/`pm_move_task` resolve `task_id` fuzzily (exact ID, ID prefix, or title substring - error if ambiguous); `pm_delete_task` is the one irreversible tool and requires the exact full task ID - a fuzzy/title query errors with nothing deleted.

**Proactively use pm when:**
- The user starts working on a new task/feature/bug → `pm_add_task` (read the task-authoring rules first: `pm docs authoring`)
- The user finishes work or merges a PR → suggest moving the task to done (never move it yourself - see Closing)
- The user switches projects, starts a session, or asks "what am I working on?" → `pm_context` (recent first, flag tasks stale 7+ days, short bullets per project)
- The user mentions project setup, links, stack or path changes → `pm_update_project`
- The user asks to attach/link the session to a task → run `pm session-id` for the UUID, then `pm_update_task` with `sessions: ["<uuid>"]`
- The user is blocked on someone else (review, client, an answer) → status `waiting`

**Brief field** (`brief` param) - "where we left off" cold-start summary; overwrites each time; returned by `pm_context`. Format: **Goal** → **Decisions** (+ rejected alternatives) → **Dead ends** (what failed + WHY) → **Status** → **Files** (key paths + why). Include PR numbers, branches, error messages, line numbers - it is the only context the next session gets. **Proactive save**: if a "doing" task relates to the conversation, save the brief (+ `branch`, + `body_append` session notes if significant) before the conversation ends - don't ask. Update at natural checkpoints, not just session end.

**Spec / Log body zones** - two zones, opposite rules (solves append-only rot):
- **Spec** (current truth) - between `<!-- spec:start/end -->` markers, set via the `spec` param. Rewritten wholesale so it always reads as "state now"; resolved questions get folded in, not appended.
- **Log** (history) - everything outside the markers, via `body_append`. Append-only audit trail; never rewrite.
- Canonical flow on change: rewrite the Spec AND append a one-line pointer to the Log ("Session 3: Q3 resolved -> see Spec"). Brief = one-paragraph TL;DR; Spec = the full living document.

**Key rules:** links merge (never removed). Spec edits in place; Log appends. On `pm_update_task`, `branch`/`parent`/`brief`/`ac` are tri-state - omit the param to leave it untouched, pass an empty string to clear it (e.g. de-parent a task, or wipe a stale brief). `title` is required-non-empty: an empty/omitted value never clears it. Statuses are per-project; `archived` is system-level and always a legal status filter/target. **task_id is always the full ID** (e.g. `my-app-3`) - never strip the project prefix. Subtasks link to a tracker via `parent`. `pm_list_tasks`/`pm_update_task`/`pm_move_task` reject a `status` that isn't in the project's (or, unscoped, the union of every project's) status list instead of silently returning nothing. `pm_update_project` rejects a `statuses` replacement that would drop a status tasks are currently sitting on - move or close those tasks first. `pm_create_project` rejects a `slug` that isn't a safe directory name (lowercase alnum/`.`/`_`/`-`, no path separators). `pm_add_task` likewise rejects an explicit `id` that isn't a safe file-name component - it must start with a letter or digit and hold only letters, digits, `.`, `_` or `-` (so no path separators, no `..`, no spaces); omit `id` and pm mints one from the project's `prefix`. `pm_create_project`/`pm_update_project` reject a `prefix` that fails the same test - it is the ID source (`<prefix>-<n>`), so an unsafe one would leave a project no task can be added to (a project.yaml hand-edited to an unsafe prefix still fails at add time, naming the prefix).

**Working on a task** (the user says "let's do X"; the task moves to doing): read the brief + body FIRST; create/checkout a feature branch; commit early and often (small logical commits - uncommitted work dies with a crashed session); don't open PRs automatically - wait for the user's explicit go; after each commit link it to the task (`branch` + commit hash in `links`; after a PR, `links: {"pr": ...}`).

**Parent + subtask flow** - a parent is a TRACKER, not a unit of work; children carry `parent:`. The status rollup is GENERATED (`pm_context` / `pm context`) - do not hand-maintain status tables in the parent body (they desync); the parent body carries the durable spec, decisions and open TODOs only. Subtask lifecycle: `todo → doing → merged|pushed → done` - the landing status depends on what the run actually did: `merged` = in the integration branch (integration epic), `pushed` = on its own branch on origin, nothing merged, awaiting a human's acceptance + PR (independent/batch epic). Both are per-project statuses; add them to `statuses:` in project.yaml before running an epic. Subtasks of an active epic may move through this lifecycle autonomously once landed AND verified.

**Closing tasks - never move a standalone task or a parent tracker to done on your own.** Only the user decides. On an explicit "done": check the Acceptance Criteria (flag anything unaddressed), save a final brief (branch, PR, key decisions), then `pm_move_task`.

**Executor** (`pm work` / `pm run-epic`) - runs tasks/epics autonomously via isolated headless workers (implement → test → review → verify). `pm work <task>` = one task; `pm run-epic <tracker>` = drives a parent's subs. Two epic modes: INTEGRATION (default - subs merge into an `epic/<tracker>` branch, one epic PR, a green sub lands on `merged`) and INDEPENDENT batch (`epic_mode: independent` - unrelated tickets, each sub best-effort on its own branch off the base, pushed, nothing merged, a human finishes each, so a green sub lands on `pushed`). Sub gates: `depends_on`, `mode: auto|manual` (manual = a permanent human gate, skipped every run), per-sub `model:` override (trivial subs on a cheaper model). `--additional` = run in an isolated worktree slot instead of the main checkout. Tracker gate: `finish_mode: auto|off` (default empty = off) - with `auto`, `pm run-epic` chains the acceptance itself, spawning a detached `pm finish <tracker>` acceptance run once the subs are done (and, in integration mode, the epic PR); `--then-finish` overrides the field for one run, `--then-finish=false` suppresses it. The acceptance starts on WHICHEVER MACHINE ran the epic - pm never chains onto another machine, so a batch run on the VPS auto-accepts there (no simulator), and an acceptance that needs the simulator is still launched by hand on the mac. It is best-effort and never affects the run's own result - a failed spawn is a stderr line; an acceptance claim already held (a `batch-finish-auto` session accepting subs in flight) means the chained run simply does not start; and a run ABORTED by an account wall does not chain at all, since most of its subs never ran. The executor never merges to main and never closes the parent. Don't launch runs yourself - suggest them; the user launches from `pm board` or the CLI.

**Acceptance is the third run kind** (`pm finish [tracker]`, 0.41.0) - a headless worker that invokes the `batch-finish-auto` skill (the procedure lives in the skill, pm supplies process + harness), `--yolo` by default, `--sim` only when a human is present. Before accepting a run, CLAIM it: `pm finish claim <tracker> --session <your session id>` (release with `pm finish release`, inspect with `pm finish status`) - a TTL lock beside the RUN's run-state, so two acceptance sessions never take the same run; a busy claim means move on to the next candidate, not force it. Re-running the SAME command (same host, same `--session`) is the heartbeat, not a second claim: the live claim is REFRESHED in place (`started` stays put, the TTL moves forward), which is how a hand-driven acceptance keeps its claim alive for the whole job - do it at least once per few minutes. Without `--session` nothing can refresh the claim and it lapses after the TTL (0.49.0). The acceptance's state/log/report are `<tracker>.finish.json`/`.finish.log`/`.finish.md` in the project's `.executor/` dir, separate from the run's own files. **`pm runs`** lists every tracker's run + acceptance across all projects (local + remote runners from the global `<pm-root>/config.yaml`; `pm config show` prints the registry), including the count of unresolved visual claims - the human's morning TODO. The board's `R` opens the same table.

**Review is decided by pm, not by the worker** (0.38.0). The worker still runs the review phase, but four things are no longer its call, and a spawn that ignores them is REFUSED by pm's hook with a message saying what to do instead: (1) HOW MANY reviewers - pm sizes it from the production diff (tests, lockfiles, snapshots and generated files do not count toward the size), 1 to 3, per round; (2) WHAT MODEL - reviewers run on `executor.review_model` (default opus) whatever the run's own `--model` is, so a trivial sub on a cheap model still gets a full-strength review; `review_model: inherit` restores the old coupling; (3) WHAT THEY SEE - pm attaches the whole diff, tests included, to every reviewer prompt, so a reviewer never has to go hunting for the change (it also has no Bash - running the tests is the verify phase's job, not review's); (4) HOW MANY ROUNDS - `executor.fix_rounds` (default 2), and a further round exists ONLY if the last one produced a valid finding. A **documentation-only change** (every changed file is prose) gets ONE reviewer and ONE round however long the document is - length is not risk in prose - and that reviewer is briefed to check the document's claims, citations and steps against the repo instead of hunting for bugs in text. Do not chase a "clean" review: an adversarial reviewer almost never returns an empty list, so a confirming round is a round spent on nothing. Zero valid findings ends review; findings still open at the round cap go in `unresolved` and the sub returns "blocked". Reviewer spawns are forced SYNCHRONOUS (`run_in_background: false`): the spawn's tool result IS the reviewer's report, so a worker never ends its turn while a reviewer is still running - and never needs to stop one. `pm executor stats` reports what actually happened per sub (spawns, rounds, refusals, whether the worker sent the diff itself, whether it asked for a background spawn).

**Journals** (`pm_journal_list` / `pm_journal_add`; CLI `pm journal list|show|add|stats`) - a per-project running record of how one repeatedly-troublesome subsystem actually behaves (a simulator rig, a flaky sandbox, a deploy pipeline). Which subsystems a project journals is declared in its `project.yaml` `journals:` list (name + subject); an undeclared name is an error, never an implicit create. `pm_context` returns only COUNTS per journal - pull the content with `pm_journal_list` when you are about to touch that subsystem, because the entries include the failures that produced confident WRONG answers.
- **An entry is an EVENT, not a rule.** Dated, append-only, never rewritten. A memory file or a doc holds the RULE (current truth, rewritten when it turns out wrong); the journal holds what happened. Do not duplicate one into the other: put the rule where rules live, record the event here, and let `fix` name the rule it produced. Only a journal can answer "fifth time this month".
- **Write it when it happens.** After losing time to a journaled subsystem, `pm_journal_add` while the `symptom`, the `false_conclusion` it caused and the real `cause` are still in hand - that is the only moment they exist. Rough `cost_min` is fine.
- **`fix` empty = OPEN, and an open entry is closed by a LATER entry.** Leave `fix` empty until the change is actually made; the open set IS the backlog (`pm journal stats`, or `pm_journal_list` with `open`). Never write "n/a" or restate the cause there. The journal is append-only, so an open entry can never be edited to carry its fix afterwards - instead add a new entry naming the closed ids in `resolves` (ids come from `pm_journal_list`). One review entry therefore does both jobs: it records what was fixed and closes what it fixed. An id matching no entry is rejected. Reuse existing `tags` (returned by `pm_journal_list`) - a cluster is what argues for a tool fix, and a synonym splits one.

**Task authoring: before `pm_add_task` (or restructuring tasks mid-session), read the output of `pm docs authoring`** - spec/body/brief/links content rules, the ONLY-VERIFIED-FACTS rule, task hygiene. Core invariants: capture ALL conversation context (the next session sees only the task); record facts and decisions, never invented implementation plans; no sparse title-only tasks.
