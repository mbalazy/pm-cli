# Project Manager (`pm`)

Local task tracker and control plane for AI coding agents. Data lives in `~/.claude/pm/` as markdown files with YAML frontmatter. CLI binary: `pm`. MCP server: `pm mcp` (stdio, registered as `pm`). TUI: `pm board` (the user runs it).

**MCP tools** (preferred over CLI): `pm_context` (session start / overview, auto-detects project from cwd), `pm_list_tasks`, `pm_get_task`, `pm_add_task`, `pm_update_task`, `pm_move_task`, `pm_update_project`, `pm_create_project`, `pm_list_projects`, `pm_delete_task`, `pm_journal_list`, `pm_journal_add`, `pm_timeline_list`, `pm_timeline_add`. CLI fallback `pm context [project]` prints the same rollup when the running MCP holds a stale binary. `pm_get_task`/`pm_update_task`/`pm_move_task` resolve `task_id` fuzzily (exact ID, ID prefix, or title substring - error if ambiguous); `pm_delete_task` is the one irreversible tool and requires the exact full task ID - a fuzzy/title query errors with nothing deleted.

**Proactively use pm when:**
- The user starts working on a new task/feature/bug → `pm_add_task` (read the task-authoring rules first: `pm docs authoring`)
- The user merges a PR into the base branch (main/development) → move the task to `done` yourself and say so; anything without a PR → suggest done, never move it (see Closing)
- The user switches projects, starts a session, or asks "what am I working on?" → `pm_context` (recent first, flag tasks stale 7+ days, short bullets per project)
- The user mentions project setup, links, stack or path changes → `pm_update_project`. `group` (a slug) joins several repos into ONE cockpit project (acme = acme-api + acme-zap + ...); a project without one is its own group. A dormant project is `archived: true` on the project - that flag alone puts it to sleep for every cross-project view (the board's hidden list is not it).
- The user asks to attach/link the session to a task → run `pm session-id` for the UUID (works inside `claude` only; in another client, take the session id from that client's own surface), then `pm_update_task` with `sessions: ["<uuid>"]`
- The user is blocked on someone else (review, client, an answer) → `pm_update_task` with status `waiting` + `waiting_for` naming who/what ("review by the lead, PR #940", "client answer") - a bare `waiting` says nothing about the blocker

**Attention block** (`attention` in `pm_context`; the cross-project one is the whole queue, the project one is narrowed to that project) - what needs the human, computed once by pm and shared with the cockpit's home screen and `pm today`: `needs_me` (worst first, each row with a `reason` and `age_seconds`), `waiting` (the `no_reason` rows first - a waiting task with no `waiting_for` is an ALARM to fix, not a blank; `age_seconds: null` means the task predates `status_changed`, never "just now"), `stuck_projects`, `counts`, `wip`. Every row carries the closed set of `actions` legal for its state. Open a session with the right question from it instead of listing tasks; the full queue is `pm today --json`.

**Brief field** (`brief` param) - "where we left off" cold-start summary; overwrites each time; returned by `pm_context`. Format: **Goal** → **Decisions** (+ rejected alternatives) → **Dead ends** (what failed + WHY) → **Status** → **Files** (key paths + why). Include PR numbers, branches, error messages, line numbers - it is the only context the next session gets. **Proactive save**: if a "doing" task relates to the conversation, save the brief (+ `branch`, + `body_append` session notes if significant) before the conversation ends - don't ask. Update at natural checkpoints, not just session end.

**Spec / Log body zones** - two zones, opposite rules (solves append-only rot):
- **Spec** (current truth) - between `<!-- spec:start/end -->` markers, set via the `spec` param. Rewritten wholesale so it always reads as "state now"; resolved questions get folded in, not appended.
- **Log** (history) - everything outside the markers, via `body_append`. Append-only audit trail; never rewrite.
- Canonical flow on change: rewrite the Spec AND append a one-line pointer to the Log ("Session 3: Q3 resolved -> see Spec"). Brief = one-paragraph TL;DR; Spec = the full living document.

**Blockers** (`waiting_for` param) - free text naming who or what a task is blocked on. It lives on `pm_add_task`/`pm_update_task` only, NOT on `pm_move_task`: to park a task with its blocker in one call, use `pm_update_task` with both `status: "waiting"` and `waiting_for`. Nothing clears it for you - a stale `waiting_for` on a task that has moved on is just leftover text, so clear it (empty string) when the block lifts. It is never validated and never required, so a `waiting` task without it reads as "blocker not recorded". Its companion `status_changed` is stamped by pm itself on every real status change (and at task creation) - it answers "waiting since when", which `updated` cannot, because `updated` moves on any edit. Both come back from `pm_get_task` and `pm_list_tasks` (and from `pm_context`'s doing/focus task summaries - a tracker's child rollup carries neither). `status_changed` is ABSENT on tasks written before the field existed (pm never migrates files): read that as unknown, never fall back to `updated`.

**Key rules:** links merge (never removed). Spec edits in place; Log appends. On `pm_update_task`, `branch`/`parent`/`brief`/`ac`/`waiting_for` are tri-state - omit the param to leave it untouched, pass an empty string to clear it (e.g. de-parent a task, or wipe a stale brief). `title` is required-non-empty: an empty/omitted value never clears it. Statuses are per-project; `archived` is system-level and always a legal status filter/target. **task_id is always the full ID** (e.g. `my-app-3`) - never strip the project prefix. Subtasks link to a tracker via `parent`. `pm_list_tasks`/`pm_update_task`/`pm_move_task` reject a `status` that isn't in the project's (or, unscoped, the union of every project's) status list instead of silently returning nothing. `pm_update_project` rejects a `statuses` replacement that would drop a status tasks are currently sitting on - move or close those tasks first. `pm_create_project` rejects a `slug` that isn't a safe directory name (lowercase alnum/`.`/`_`/`-`, no path separators). `pm_add_task` likewise rejects an explicit `id` that isn't a safe file-name component - it must start with a letter or digit and hold only letters, digits, `.`, `_` or `-` (so no path separators, no `..`, no spaces); omit `id` and pm mints one from the project's `prefix`. `pm_create_project`/`pm_update_project` reject a `prefix` that fails the same test - it is the ID source (`<prefix>-<n>`), so an unsafe one would leave a project no task can be added to (a project.yaml hand-edited to an unsafe prefix still fails at add time, naming the prefix).

**Working on a task** (the user says "let's do X"; the task moves to doing): read the brief + body FIRST; create/checkout a feature branch; commit early and often (small logical commits - uncommitted work dies with a crashed session); don't open PRs automatically - wait for the user's explicit go; after each commit link it to the task (`branch` + commit hash in `links`; after a PR, `links: {"pr": ...}`).

**Parent + subtask flow** - a parent is a TRACKER, not a unit of work; children carry `parent:`. The status rollup is GENERATED (`pm_context` / `pm context`) - do not hand-maintain status tables in the parent body (they desync); the parent body carries the durable spec, decisions and open TODOs only. The rollup lists a tracker's OPEN children (closed ones are only counted in `progress`), and the cross-project `pm_context` shows trackers as headers with no children at all - pass the project to see them, `pm_list_tasks` for the full list. Subtask lifecycle: `todo → doing → merged|pushed → done` (`merged` = in the integration branch, `pushed` = on its own branch on origin, nothing merged, awaiting a human's acceptance + PR; both are per-project statuses).

**Closing tasks - a merged PR closes the task, everything else the user closes.** A PR merged into the BASE branch (main/development) is verifiable evidence, not a judgment call: once it is merged, move the task to `done` yourself (save the final brief first - branch, PR, key decisions - and name the move in your report). A sub `merged` into an epic branch is NOT that event - the epic's own PR to the base branch is, and it closes the tracker too once every child is closed. A task with no PR (research, a decision, configuration, a client conversation) has no merge event, so there the old rule holds: never move it to done on your own - suggest it, and on the user's explicit "done" check the Acceptance Criteria (flag anything unaddressed), save the final brief, then `pm_move_task`.

**Journals** (`pm_journal_list` / `pm_journal_add`; CLI `pm journal`) - a per-project append-only record of how one repeatedly-troublesome subsystem actually behaves, declared in `project.yaml` `journals:` (an undeclared name is an error, never an implicit create). `pm_context` returns only COUNTS per journal - read the entries with `pm_journal_list` before touching that subsystem; they hold the failures that produced confident WRONG answers. An entry is an EVENT (dated, never rewritten), not a rule: the rule lives in a memory file or a doc, and `fix` names it. Write it while the `symptom`, the `false_conclusion` it caused and the real `cause` are still in hand. Empty `fix` = OPEN, and the open set is the backlog; an open entry is closed by a LATER entry naming it in `resolves`, never by an edit. Reuse existing `tags`.

**Timeline** (`pm_timeline_list` / `pm_timeline_add`; CLI `pm timeline [project]`, `pm timeline add|list`) - a per-project append-only record of what happened TO the project, plus dated `state` snapshots of where it stands. Project-scoped `pm_context` carries its default read as the `timeline` block (absent when the project has no timeline); the cross-project rollup carries only `timeline_state`, the latest state's date and first line.
- **Three kinds, nothing else.** `event` - something happened to the project (a direction change, a client decision, a milestone, a new person, a document arriving), one to three sentences; `decision` - one sentence plus `refs` to the full record in a task or doc; `state` - a snapshot that fits on a screen, 10-20 lines: where we stand, what blocks, what is next, open questions, links. Long material stays in the task or document; the entry points at it.
- **A state is an entry, not a field.** Entries are never edited: a changed picture is a NEW state, and older states stay, so "where did we stand on 27.08" stays answerable. A task brief overwrites because a task ends; a project does not.
- **Read the latest state PLUS every entry after it, never the state alone** - a state goes out of date with the first entry written after it. That is the default read (`pm_timeline_list` with no filters; the `pm_context` block keeps the state whole and the newest 20 entries after it). `stale: true` (10+ entries or 7+ days since the state) means: write a new state. Reach for `pm_timeline_list` with `since`/`kind` when the state does not say WHY, for what happened between two dates, or when a task contradicts the state.
- **Every state line carries its provenance.** End a line with `[verified YYYY-MM-DD by <command or doc>]` when you checked it in THIS session (the day you ran the command, the command or document that showed it), or `[assumed]` when you did not - a state is prose you wrote, and after a compaction the next reader cannot tell a fact you saw from one you inferred. A line with neither is UNMARKED and every read counts it as unverified; a `[verified]` marker without a day, or with a future day, is refused. Never copy a `[verified]` marker forward from an older state without re-running its source. The read's `verification` block counts the lines (verified / recheck / assumed / unmarked) and lists in `recheck_lines` the verified lines 7+ days old: re-establish those with a tool call before relying on them. `event` and `decision` entries carry `refs` instead - no marker.
- **Task Log vs timeline.** What happened IN a task goes to that task's Log (`body_append`); what happened TO the project goes here. Machine events (commits, PRs, the cockpit's change feed) never go here.
- **When to write**: at the same checkpoint where you save a brief, if something happened at project level - most sessions write nothing here.

**Task authoring: before `pm_add_task` (or restructuring tasks mid-session), read the output of `pm docs authoring`** - spec/body/brief/links content rules, the ONLY-VERIFIED-FACTS rule, task hygiene. Core invariants: capture ALL conversation context (the next session sees only the task); record facts and decisions, never invented implementation plans; no sparse title-only tasks.
