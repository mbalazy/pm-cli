## Key patterns

- **Parent/subtask rollup**: `parent` in frontmatter holds a parent task ID (e.g. `atlas-39`), making the task a child of a tracker. Link is one-way (child→parent); a task is a "tracker" iff some other task names it as parent (derived, never stored on the parent). `storage.BuildTrackers(tasks, extraTerminal...)` (in `internal/storage/tracker.go`) groups tasks by parent and returns `[]Tracker` (parent + progress map + child rollup with `brief_line`) plus a `suppressed` set (children + trackers, excluded from flat doing lists). Used by `pm_context` (MCP, `trackers` section) and `pm context` (CLI). The generated rollup replaces hand-maintained board tables in the parent body. Subtask lifecycle: `todo → doing → merged|pushed → done` (add both to the project's `statuses`; which one a green sub lands on depends on the epic mode - see Landing statuses). Children (and the `TrackerChild.order` field) sort by `storage.LessByOrder` (Order asc, then numeric ID, then most-recently-updated) - the SAME comparator the board columns (`filteredTasks`) and the TUI tracker list (`taskChildren`) use, so all three never disagree. Set `order` via the `order` param of `pm_add_task`/`pm_update_task` (`pm_update_task` accepts a 0 to clear it), the `--order` flag of `pm add`, or `pm reorder <parent> <child-id>...` (renumbers the listed children to 10, 20, 30... in the given sequence; resolves the project by the parent's full ID, validates every ID is a real child before writing).
- **Concurrency (lost-update protection)**: task writes are atomic (tmp+rename), so the ONLY hazard is two pm processes (parallel CC sessions' MCP servers, executor managers, the board) interleaving read-modify-write and dropping each other's edits. `Store.LockProject(slug)` (internal/storage/lock.go) is a cross-process flock on `<projectDir>/.pm.lock` - hold it around FindTask -> mutate -> WriteTask and read the task FRESH inside. Wired into: the mutating MCP handlers (add/update/delete), the CLI's own minting/multi-file writers `pm add` (the lock MUST cover `NextTaskID` -> `AddTask`: the ID is derived from the tasks on disk, so two unlocked adds mint the SAME id - O_EXCL only protects the file NAME, and two different titles produce two different names) and `pm reorder` (the widest read-modify-write among the CLI commands: several children, whole-struct writes, so an unlocked run reverts a concurrent `pm_update_task` brief and body included - it re-reads the children FRESH inside the lock), `applyWorkerResult` + `recordSubFeedback` (the executor's long-window writers: their task copies predate a 30+ min worker run and MUST be re-read before writing), and `Store.MoveTask` itself (self-locks + re-reads fresh + refreshes the caller's copy in place - covers all 24 move sites incl. the board's stale card copies). Deliberately NOT wired into the board's OWN writers (the `Ctrl+j/k` order swap in `actions.go`, the add prompt's `time.Now().Unix()%100000` id) - same hazard class as `pm add`/`pm reorder`, still open. RULES: never nest LockProject in one process (second flock on a fresh fd deadlocks against your own lock - release before calling a self-locking callee like MoveTask; the release closure is sync.Once-idempotent for exactly this handoff), and `pm_move_task` deliberately has NO handler-level lock. `MoveTask`'s fresh re-read is a PRECONDITION, not a best-effort refresh: if the task file is gone (a parallel `pm_delete_task`) or the dir cannot be read, it returns an error and writes NOTHING - swallowing that error resurrected deleted tasks from the board's stale card pointers. The executor's two long-window writers now enforce the SAME precondition (via `FindTaskExact`): `applyWorkerResult` returns an error (`pm work` surfaces it; the manager parks the sub) and `recordSubFeedback` returns one that `logIfErr` reports without aborting the run - a task deleted during a 30-minute worker run no longer comes back carrying a brief nobody will look for. `Store.WriteTask` stays lenient on purpose: the board's `doUndo` resurrects a snapshot deliberately. **project.yaml is covered too**: its write path `writeProject` MERGES into the existing file (to keep comments + unknown keys), so its read->write window is wider than a task write's - `Store.CreateProject` (lock taken after MkdirAll; the lock file lives in that dir), `Store.UpdateProject` and `Store.MutateProject` all self-lock, and the same no-nesting rule applies to them. `LockProject` no longer MkdirAll's the project dir - it STATS it and errors when it is missing. The lock file lives inside that dir, so creating it made every one of the 11 lock sites able to conjure a project: a write to a typo'd slug silently created one, and locking a project someone had just deleted resurrected its dir, into which `applyWorkerResult` then wrote a 30-minute-old task - invisible forever, since no `project.yaml` comes back with it. `CreateProject` is the only site that legitimately makes the dir and it MkdirAll's before it locks; every other site resolves an existing slug, and the callers that degrade to an unlocked write on a lock error keep exactly the behaviour they had. A partial-field edit must go through `Store.MutateProject(slug, fn)` (lock -> re-read FRESH -> apply fn -> write), NOT GetProject -> mutate -> UpdateProject, whose lost-update window is as wide as the caller's think time: `pm_update_project` and `pm executor init` patch single fields and would otherwise revert a parallel session's edit to an untouched field. The worktree slot lock is separate and ALSO atomic: claim = link(2) of a fully-written tmp (rival can never read a half-written winner), stale takeover = rename-aside (see AcquireWorktreeLock).
- **Identifiers are PATH COMPONENTS, validated at the store** (pm-cli-74-1): a task ID becomes the leading component of its file name (`Filename` = `<id>-<title-slug>.md`) and a project slug becomes a directory, so both are validated where they are WRITTEN, not only in the MCP handlers - `storage.ValidateTaskID` in `Store.AddTask` (covers `pm add --id`, `pm_add_task`'s `id`, the board's add prompt; runs BEFORE the O_EXCL claim so a rejected ID leaves no phantom file) and `storage.ValidateSlug` in `Store.CreateProject` (before MkdirAll, so `pm projects add ../outside` creates nothing). `ValidateTaskID` is deliberately WIDER than `ValidateSlug` - real data holds `30422` and `ACME-253`, so digits-only and uppercase stay legal - but rejects spaces/non-ASCII on purpose (IDs get quoted into shell commands, branch names and log paths). The third identifier is `project.yaml`'s **`prefix`**, the ID SOURCE for auto-minted ids (`<prefix>-<n>`): `storage.ValidateProjectPrefix` gates it in `CreateProject`, in `pm_update_project`, and in `MutateProject` **only when the value CHANGES** (a legacy project carrying a bad prefix must stay editable in its other fields, or `pm executor init` could never touch it). A prefix that slipped in by hand still fails at add time, with an error that names the prefix and the project.yaml path instead of an ID nobody typed. `pm migrate-ids` is the one renumbering path that bypasses `AddTask` (it rewrites via the lenient `WriteTask`), so it validates the prefix in its PREFLIGHT - checking per task would renumber the alphabetically earlier projects before failing.
- **`pm work`/`pm run-epic` one-arg resolution** (pm-cli-74-1): the single-argument form scans projects in `FindTask`'s OWN three tiers (exact ID -> unique ID prefix -> title substring), each tier deciding alone, and ERRORS listing the candidates when a tier matches several projects - first-hit-wins in sorted order used to spawn a 60-minute worker in the WRONG repo. The cwd project is a TIEBREAK INSIDE a tier, never a short-circuit: standing in a repo settles a tie but does not let its title mention outrank another project's exact ID. Archived projects are excluded (as in `GetAllTasks`) unless you are standing in one; the explicit two-arg form still reaches everything. A query that is ambiguous INSIDE one project contributes `<slug>/<several>` rather than dropping out of the scan (dropping out is first-wins by another route).
- **Statuses are per-project** — read via `Store.GetProjectStatuses(slug)`. Default: `[todo, doing, waiting, done]`. Override in `project.yaml`. "ALL" view merges all projects' statuses. **Every mutation path validates** (0.29.2): `Store.MoveTask` and MCP `pm_update_task`'s `status` param reject a status outside the project's set (plus system-level `archived`, always legal) - a typo'd `pm mv` used to write it and the task vanished from every board column. `pm run-epic` hard-gates an unlisted `done_status` at run start (failing the merged-move AFTER the merge landed would desync the re-entrant done check and re-drive the sub); the INDEPENDENT-mode landing status degrades instead of gating when it is the built-in default - see Landing statuses.

## Debugging TUI layout

The instrumentation recipe and the height budget behind CLAUDE.md's layout-debugging rule:

1. **Colored section markers** - add `lipgloss.NewStyle().Background(color).Render("[TAG]")` at section boundaries to see exactly where each section starts
2. **Debug status bar** - replace the status bar with key metrics: `h` (terminal height), `curH` (computed height), `pad` (padding lines), `mch` (max card height), per-column content line counts
3. **Key formula**: `viewBoard` total visual lines = `strings.Count(output, "\n") + 1`. Must equal `m.height`. If `curH > h`, top lines get cut off by bubbletea
4. **Build with `-dbg` suffix**: use version like `0.7.1-dbg` so debug builds are clearly identified
5. **Clean up**: remove all debug code before committing. Restore `version` import if status bar uses it

Layout height budget for `viewBoard` (each item = newlines contributed):
- Title with `Padding(0,0,1,0)` + explicit `\n`: 2
- Tabs + `\n\n`: 2
- Column border/padding (`Padding(1,2)` + `RoundedBorder`): 4
- Column content (cards): `maxCardHeight` (variable)
- `\n` after columns: 1
- Confirmation line (always reserved): 1
- Status bar (no trailing `\n`): 1 visual line
- Total = `maxCardHeight + 11` (+ 1 if search/add active)

The `maxCardHeight` is computed dynamically: `m.height - overhead` where overhead accounts for all non-column lines. Column content is clamped (truncated if over, padded if under) to exactly `maxCardHeight` newlines so `JoinHorizontal` produces consistent height across projects.

## MCP server (`pm mcp`)

- **No MCP resources** (pm-cli-72-3): the 3 resources (`pm://projects`, `pm://tasks/{project}/{status}`, `pm://project/{slug}`) were removed - `pm://tasks` bypassed every output budget `pm_list_tasks` enforces (full briefs, no 50-task cap, no archived exclusion - exactly what 0.24.0/0.28.1 fixed), `pm://projects` dropped the `archived` field, and all three duplicated a tool with a worse copy. Grepped for real consumers (repo, docs/, `~/.claude/CLAUDE.md`) before deleting - none found. Use the equivalent tool instead: `pm_list_projects`, `pm_list_tasks`, `pm_get_task`/`pm_context`.
- **Output budget** (0.24.0): `pm_list_tasks` defaults to the 50 newest tasks (`limit` param overrides; `limit<=0` → default) and returns a wrapper `{tasks, total, shown, note}` - `note` states "N of M tasks shown ... narrow with project/status or raise limit" whenever the list was truncated. List summaries carry ONE-LINE briefs (`storage.BriefLine`: first non-empty line, 120-rune cap); `ac` stays full. `pm_context` caps each doing-task `body` at 2000 runes (`contextBodyLimit` in `tools.go`) with a pointer to `pm_get_task` for the rest - `brief` is never truncated there (it IS the designed cold-start vehicle). `pm_get_task` remains unbounded. **The rollup is a summary, not a reading surface** (0.28.1, pm-cli-50 - `pm_context` for orbit returned 61 757 chars over MCP and blew the tool's token limit while the same rollup from the terminal was 15 746): every brief inside `trackers` is one line - `storage.Tracker.BriefLine` (JSON `brief_line`, was the full `brief`) alongside the children's, set in `BuildTrackers` so the CLI/TUI/MCP share ONE rule - and a **finished tracker collapses its children** (`trackerFinished`: the parent's own status is terminal AND every child is `done`/`archived`/a landing status → `Children` nil + `children_omitted: true`, `Progress`/`Total` survive). That collapse is the structural half: finished epics accumulate forever and were the one part of the payload growing without bound, while a still-open child (e.g. `waiting` under a closed parent) keeps the full list. `focus_tasks` briefs and the cross-project branch's `doing_tasks` briefs compress too - they are listings. The project-scoped `doing_tasks` brief stays FULL on purpose. Measured on orbit: 62 726 → 44 350 chars MCP, 15 771 → 13 077 CLI.
- **Invariants**: links merge (never remove), body_append appends to the Log (never replaces), spec rewrites the Spec block in place, tags replace if provided, epic_mode overwrites if provided (validated). `branch`/`parent`/`brief`/`ac` are tri-state on `pm_update_task` (pm-cli-72-3, matching `mode`/`model`/`epic_mode`): omit = keep, empty string = clear; `title` stays required-non-empty (never clearable). `pm_list_tasks`/`pm_update_task`/`pm_move_task` reject a `status` outside the project's (or, cross-project, the union of every active project's) status list - `archived` is always legal. `pm_update_project` rejects a `statuses` replacement that would orphan tasks sitting on a dropped status (handler-level only, not storage - CLI/manual project.yaml edits stay lenient); an empty `statuses: []` resets to `DefaultStatuses` and is checked against THAT effective set, not the empty literal. `pm_create_project` rejects a `slug` that isn't a safe path component (`storage.ValidateSlug`, `^[a-z0-9][a-z0-9._-]*$` - deliberately not `slug == Slugify(slug)`, since `Slugify` strips literal hyphens and would reject real slugs like `app-orbit`).
## Journals (`pm journal`)

Added 0.35.0 (pm-cli-83). A **journal** is a per-project append-only record of how ONE chosen, repeatedly-troublesome subsystem actually behaves - the first instance is the iOS simulator rig in app.orbit, whose incidents had accumulated as 15 separate Claude memory files plus a hand-grown section in `.simulator-verify/config.md`: none dated, none counted, none connected to a fix.
- **The distinction that stops it duplicating memory files**: a memory file or a doc holds a **RULE** (current truth, rewritten when it turns out wrong); a journal entry holds an **EVENT** (dated, append-only, never rewritten). A rule can never answer "fifth time this month"; a journal never replaces the rule. The entry's `fix` field NAMES the rule/change it produced, and **an entry with an empty `fix` is OPEN - the open set IS the backlog**, derived, never hand-maintained. This is why the sim-naming norm from the same session went into the skill (a rule) and not into a memory file AND the journal.
- **Storage** (`internal/storage/journal.go`): JSONL per subject at `<projectDir>/.journal/<name>.jsonl`, deliberately the same grain as the executor journal one directory over (`.executor/journal.jsonl`), so the code shape and the reading habit already existed. `Incident` = `{ts, symptom, false_conclusion, cause, cost_min, fix, tags, session}`. `false_conclusion` is the load-bearing field: a subsystem that fails LOUDLY is cheap, one that returns a confident wrong answer is what burns afternoons (the trigger incident was a `RIG DEAD` printed for a live rig). `AppendIncident` RETURNS its write error rather than swallowing it like `AppendJournal` - the executor journal is observability written by a machine mid-run, this is written by whoever just paid the cost, and losing it silently loses the only record.
- **Closing an entry is a new EVENT, never an edit** (0.36.0): `Incident.Resolves []string` lists ids of EARLIER entries this one closes, and `StillOpen` = no own `fix` AND nobody has since closed it. Without it the open count could only ever grow - append-only means an entry cannot be edited to carry a fix decided weeks later - and the backlog would rot, which is the failure the journal exists to prevent. `JournalStats.ClosedLater` reports resolved-by-a-later-entry separately from `Open`, so a review's effect stays visible instead of entries silently vanishing from the count. An unknown `resolves` id is REJECTED before the write: it would fail silently otherwise (entry lands, target stays open, nobody re-derives). **The id is DERIVED, not minted** (`incidentID` = UTC day + 2-byte hash of ts+symptom): deterministic from stored fields, so `ReadIncidents` computes it for lines written before the field existed and the entire pre-existing backlog became closable without rewriting one byte of an append-only file.
- **Ordering rules, both learned from a real bug**: entries are read newest-first (the file stays append-order) and an entry whose `ts` does not parse sorts **LAST** - a raw string comparison put `"not a timestamp"` above every real date, straight to the top of the actionable list. `JournalStats.First/Last` come off the PARSED instant for the same class of reason: RFC3339 permits a numeric offset, so `...T10:00:00+02:00` compares lexicographically after a later `...T09:00:00Z`.
- **Surfaces**: `pm journal list|show|add|stats` (CLI, `--project` flag rather than a second positional) and `pm_journal_add` / `pm_journal_list` (MCP). `pm_journal_add` reports back the recurrence its own entry just produced ("2 entries now share tag X") - that sentence is what turns a log into an argument for fixing the tool, and it costs one line at the one moment someone is already paying attention. Stats travel WITH the entries in `pm_journal_list` rather than in a separate tool: the reason to read a journal is to see whether something recurs, and a caller who needs a second call for the counts will skip it.
## Executor (`pm work` / `pm run-epic`)

Runs pm tasks/epics by spawning **isolated headless `claude -p` workers** that implement → test → review → fix → verify, so a multi-subtask epic executes without blowing one session's context. Built + validated (epic `pm-cli-18`; first real run = atlas-64-3 → PR #151, 2026-06-17).
- **`pm work [project] <task>`** (`internal/cmd/work.go`, `work_prompt.go`, `work_git.go`) — the ATOM. Spawns one fresh `claude -p` in the project dir (loads that project's skills/CLAUDE.md/MCP by cwd), runs the inner loop on one task, returns a JSON contract (`{status,summary,branch,commits,unresolved}`). Standalone → draft PR; `--epic` → commit only. `planWork` (assemble, no side effects) + `executeWork` (run + record). `--dry-run` prints the prompt+argv without spending tokens. Flags: `--model` (opus), `--max-turns` (150), `--timeout` (60m), `--yolo`, `--allow-dirty`, `--additional` (+ `--slot N`, `--base`) - see Additional worktree mode.
- **`pm run-epic [project] <tracker>`** (`internal/cmd/run_epic.go` + `run_epic_sub.go`) — the MANAGER. Split like `pm work`: side-effect-free `planEpic` (project preflight via the shared `preflightProject`, ready subs, mode, branches - what `--dry-run` prints) + `executeEpic` (the loop). One `driveSubFlow` drives a sub in both modes; the integration/independent differences (fork base, pre-branch checkout, parking, push, merge, branch cleanup) are the `subFlow` hook struct in `run_epic_sub.go`. Creates integration branch `epic/<tracker>`, drives ready subs sequentially (by `Order`), each on `feat/<slug>` branched off the integration branch; merges back `--no-ff` on verify-green → `done_status` (integration) / `done_status_independent` (batch). Blocked/failed/conflict → park on `waiting` + continue, and the sub's reason+open-questions bubble to the parent's `## Manager Notes` (via `recordSubFeedback`, deduped per-sub, refreshed/cleared on eventual merge). Re-entrant (skips merged/done). Ends with ONE draft `epic→main` PR. Never merges to main, never closes the parent.
- **`depends_on` gate** (`unmetDeps` in `run_epic.go`): a sub's `depends_on: [<sub-id>...]` frontmatter lists subs that must be `merged`/`done` first. The manager checks it BEFORE spawning a worker — an unmet dep skips the sub (no worker, no wasted tokens) and leaves it on its ready status (NOT parked on `waiting`), so a re-run auto-picks it up once the dep merges. A genuinely failed sub still goes to `waiting` (needs a fix + flip back to `todo`); a dep-skip is just "not its turn yet". Opt-in (empty = run by `Order`). Settable via `pm_add_task`/`pm_update_task` `depends_on` param; shown in `pm run-epic --dry-run`.
- **`mode: auto | manual` gate** (`classifySub` in `run_epic.go`): a sub's `mode` frontmatter marks it autonomous (`auto`/empty, default - backward compatible) or human-only (`manual`). A `manual` sub is a PERMANENT gate: the manager skips it entirely (no worker spawned, status untouched) on EVERY run, records a distinct `manual` outcome (not `skipped`), and never re-picks it - unlike the re-entrant `depends_on` skip. The human does the work by hand / with CC and moves the sub to `done_status` themselves; only then does the re-entrant done check pick it up. Use for subs needing interactive/visual work (simulator verification, design checks) that a headless `claude -p` can't do. A later auto sub with a `manual` sub in its `depends_on` stays blocked via the normal `unmetDeps` gate until the human moves the manual sub to done (no special-case logic). Only `auto`/`manual` (lowercase) are valid - `storage.ValidateMode` rejects anything else at write time. Settable via `pm_add_task`/`pm_update_task` `mode` param; shown as `[MANUAL]` in `pm run-epic --dry-run`. No CLI flag - it's a per-task frontmatter field.
- **`model` per-sub override** (0.21.1): a sub's `model:` frontmatter (claude alias or full name, e.g. `sonnet`) overrides the run-level `--model` for THAT sub in `pm run-epic` (stderr announces `model override -> ...`), and in `pm work` it wins over the flag DEFAULT but an explicitly passed `--model` wins over the frontmatter (`cmd.Flags().Changed`). Empty = inherit (backward compatible). Purpose: token economy - trivial subs (copy/color/one-prop tweaks) run on a cheaper model while investigation subs stay on opus; batch-prep/epic-prep tag subs at creation. Settable via `pm_add_task`/`pm_update_task` `model` param. Related: the reviewer count was ALSO a prompt rule at 0.36.2 (<~50 changed lines across <=2 files -> 1 reviewer, larger -> 3, production files only) - SUPERSEDED in 0.38.0, where pm sizes the review itself and refuses the spawn past the cap, and the prompt no longer states a number at all. The per-sub `model` override is deliberately independent of it: reviewers run on `executor.review_model` (default opus) whatever cheap model the sub itself was put on.
- **Hook bypass, lost results, and who owns "full validation"** (0.36.3, `worker_guard.go` + `work_result.go` + `work.go` + `work_prompt.go`; all three found in the FIRST real run under the 0.36.2 gate - `orbit-vps-1` on the orbit VPS runner, 2026-08-05 21:11-21:31 UTC, evidence in pm-cli-66-6): the gate change worked (see below), and the run surfaced three defects the isolated validation could not.
  - (a) **The envelope left the forbidden door as the only open one.** A worker's pre-commit hook died on `gitleaks: not found` (the binary was simply absent from that runner). It tried `PATH=... git commit`, then `export PATH=...`, then `ls` outside the repo - the allowlist denied each, because each needs a shell construct the envelope withholds - and then found the one form nothing blocked: `git -c core.hooksPath=/dev/null commit`. That commit is on origin: no secret scan, no lint-staged, and it reads as hook-checked. Two fixes, plus one environment fix (gitleaks installed on the runner). `workerDisallowedTools` grew the leading forms, and **`pm worker-guard`** (hidden command) is now attached to every worker as a PreToolUse hook via `--settings` inline JSON, blocking `--no-verify` / `-n` on commit+push / `core.hooksPath` / `HUSKY=0` / `rm`-ing hook files with an exit-2 message that names the legitimate move (`BLOCKED-ENV:` + return "blocked"). It rides along in `--yolo` too: yolo waives permission PROMPTS, not the project's right to have its commits pass its own hooks. Facts worth not re-deriving, each measured against a probe repo with a deliberately failing hook (2026-08-06): permission patterns match **whole tokens**, so `Bash(git -c core.hooksPath:*)` does NOT match `git -c core.hooksPath=/dev/null ...` (hence the blunter `Bash(git -c *)`); prefix patterns cannot see a **trailing** flag, so `git commit -m x --no-verify` ran under the full disallow list and only the guard stops it; `--settings` **merges** with the repo's own `.claude/settings.json` (a project PreToolUse hook still fired alongside the guard), and inline JSON is accepted by claude 2.1.71 (VPS) as well as 2.1.223 (mac), which materializes it into `/tmp/claude-settings-<uuid>.json` and leaves it there (one ~110-byte file per worker run - harmless, but do not go hunting for what wrote them). The guard **fails open** on an unreadable payload - a guard that failed closed would stop every worker on the machine the first time the hook schema moved.
  - (b) **A finished sub was recorded as failed because its receipt arrived one turn too early.** `orbit-vps-1-1` emitted `StructuredOutput` with `status: "verified"`, branch and commit - and 9 s later a background-task notification (it had run the gate with `run_in_background`) forced one more text turn, so the envelope's `structured_output` came back null and pm reported "worker returned no structured result". `parseWorkerOutput` now falls back to the worker's transcript (`<config>/projects/<encoded cwd>/<session>.jsonl`, both the project's config dir and the default; last StructuredOutput call wins, run stats still lifted from the envelope) and ANNOUNCES the recovery - silent recovery would hide the worker's turn-order defect behind pm papering over it. The prompt side tells the worker to emit the result as its final act with no background task still running.

- **Liveness has a second criterion: a recycled pid is not the holder** (0.37.1, `internal/storage/process.go` + `process_{darwin,linux,other}.go`; pm-cli-93, same external review): `ProcessAlive` was a bare `Signal(0)`, i.e. it answered "does a process with this number exist" when every caller meant "is the process that wrote this lock still running". Pids get RECYCLED - the journal already learned this on the other side of the same hazard (the `run_id` fix, 0.27.0) - so a `.pm-executor.lock` orphaned by a reboot or a `kill -9` read as held by whoever later inherited the number, and the worktree slot stayed busy until a human deleted the file; `pm executor stats` booked the crashed run as still running. `WorktreeLock.Started` had been written since day one and compared against nothing. - **Run-state heartbeat + `storage.RunWriter`** (`internal/storage/executor_run.go`): before this, `Updated` only moved on sub BOUNDARIES, so a 41-minute sub was indistinguishable from a hung run (`IsLive()` says "the process exists", not "it is making progress") - and with a 60m worker timeout an observer waited up to an hour to find out. Now `executeWork` starts a ticking goroutine right before spawning the worker and stops it the moment the worker returns (`RunWriter.Heartbeat(storage.HeartbeatInterval)`, fixed 30s - deliberately no flag and no project.yaml knob), covering `pm run-epic` (per sub, on the manager's shared epic-level run-state passed down via `workOptions.runWriter`) AND standalone `pm work` (its own). The stop func is idempotent and WAITS for the goroutine to exit, so nothing can stamp the file after the run. The heartbeat re-stamps `Updated` and touches NOTHING else (no phase guessing, no sub invention) - a dedicated field was rejected because no consumer depends on "last real state change": `execElapsed` only reads `Updated` when the run is NOT running, and `pm executor stats` classifies crash-vs-running off the JOURNAL's `ts`, never the run-state. **`RunWriter` is the serialization point**: the file write was already atomic, but the race is on the STRUCT (the main goroutine mutates CurrentSub/Phase/Subs right before writing while the ticker writes the same pointer), so every run-state access in the EXECUTOR process goes through `Update(fn)`/`Read(fn)` under one mutex - a mutex inside `WriteRunState` would not have been enough. (The board process still calls `WriteRunState` directly in `launch_executor.go`/`run_control.go`; it shares the file, not the struct, and the file write is atomic.) Cross-process, the atomicity rests on the scratch file being named per WRITER (`<path>.tmp.<pid>`, 0.27.1/pm-cli-48): a shared name let two processes interleave inside one non-atomic `os.WriteFile` and rename a torn mixture, and only the `rename` publishes. Per-pid names no longer self-overwrite, so both failure paths `os.Remove` the scratch file or every failed write leaks one. The interval reaches the call site as `cmd.workerHeartbeatInterval`, a var seeded from the const purely so tests can shrink it. A nil `*RunWriter` is a no-op on every method (a bare `pm work --epic` with no manager has no run-state). Board side: the dashboard renders `♥ <age> ago` next to the elapsed clock ONLY while a worker is actually in flight - gated on `IsLive() && CurrentSession != ""` (`execHeartbeatAge` in `executor_view.go`). `CurrentSession` is pinned right before the worker spawns and cleared in `executeWork` the moment it returns (in the same breath as the heartbeat's own stop - that pairing is load-bearing, keep them together), so the gate tracks the ticker's window on both ends. Both halves were bugs found in review: gating on `IsLive()` alone false-flagged the board's launch seed plus `executor.prepare` + baseline capture (15-min caps each) as hung, and clearing `CurrentSession` only at the sub boundary did the same for the post-worker tail (`applyWorkerResult`'s project flock, then the merge or `git push`). **What the signal does and does not prove**: the ticker lives in the MANAGER process, so a fresh stamp means "the manager is alive and inside a worker", not "the worker is making progress" - a `claude -p` wedged on a network read still looks healthy until its 60m timeout. It separates a long sub from a dead/stopped manager (and from a stale run-state whose pid got recycled, which `IsLive()` alone gets wrong); detecting a wedged WORKER would need transcript-tick stamping, which this ticket deliberately did not do.
- **Kill a live run** (`K` → confirm; `killRun` + `RunState.Kill` in `run_control.go`): group-kills the manager tree (SIGTERM to `-pgid`, escalates to SIGKILL ~2s later if still alive), stamps the run-state `failed`, and parks the in-flight sub on `waiting` so the board reflects the stop. The worker is NOT in the manager's group (it leads its own - see Subprocess process groups): it dies because the manager FORWARDS the SIGTERM to the worker's group and only then re-raises on itself, all inside the board's 2s window. That handoff is why the board must signal something catchable - a SIGKILL to the manager cannot be forwarded and would orphan the worker for the rest of its `--timeout`. The **backstop** for the cases where no forwarding can happen (the 2s escalation actually firing, an OOM kill, a crash) is `RunState.WorkerPGID`: `executeWork` publishes the worker group's pgid onto the run-state as the worker spawns and clears it the moment the worker returns - the same set/clear window as `CurrentSession`, and for the same reason, since a pgid left behind is one the next kill would signal after the kernel has recycled it. `RunState.Kill` signals that group IN ADDITION to the manager's (never instead - a live manager still forwards), and `killRun` re-reads the run-state BEFORE signalling because the board's copy is up to a tick old and the pgid changes with every sub. The board's SIGKILL escalation (`execKillCheckMsg`) kills the worker group FIRST - killing the manager first destroys the only thing that could still forward. Since 0.37.1 the escalation no longer carries the pgid in its message: it re-reads the run-state and goes through the SAME verified `RunState.Kill` (see below), so the pgid it signals is the fresh one and the identity check applies to the SIGKILL too.
- **Nothing is signalled until the pid is PROVEN to be the run's own process** (0.37.1, `RunState.Kill` + `execKillCheckMsg`; pm-cli-94, from the same external review - the reviewer's words: this is not a telemetry oversight, it is a real operational-security hole): `Kill` sent `syscall.Kill(-st.PID, sig)` off a pid read out of a FILE, with no check of any kind - and a run-state outlives its process. A `kill -9`, an OOM or a reboot leaves `status: running` behind with a pid nobody cleaned up ("A crashed executor leaves status=running with a dead PID" was already documented at `IsLive`), and after a reboot the numbers get handed out again from the bottom. Pressing `K` on such a card sent SIGTERM - and two seconds later SIGKILL - to the process GROUP of something entirely unrelated, possibly a system process. Now `Kill` verifies identity first (`ProcessAliveSinceStamp` against the run's own `Started`, the pm-cli-93 predicate) and returns a typed `StaleRunError` naming the pid instead of signalling. Three consequences worth keeping straight. (a) **The worker group rides on the MANAGER's proof**, not its own: a worker starts DURING the run, i.e. after the stamp, so the start-time test cannot apply to it - what makes `WorkerPGID` trustworthy is that a live manager clears it the moment its worker returns (plus a cheap `ProcessAlive` guard). (b) **The refusal is loud and reconciling, never silent**: `killRun` reports "Run already gone (nothing signalled), state reconciled", still stamps the run failed / parks the in-flight sub / journals the stop with that wording, and schedules NO escalation against a pid it just refused. (c) **The escalation re-reads and re-verifies** - two seconds is ample for the manager to exit and for its number to be reused, and a SIGKILL cannot be taken back, so no fresh state (or a state whose pid has moved on to another run) means no signal. Test seam: `killSignal` is `syscall.Kill` behind a var, so tests assert what WOULD be signalled without a test process ever signalling a group; board-side fixtures that need the "stopped it" path now spawn a real detached sleeper (`liveRunPID`), because a made-up pid exercises the refusal instead.
- **Subprocess process groups + bounded Wait** (0.30.1, `internal/cmd/work_proc.go`; pm-cli-57): `runWorker` and `captureBaseline` spawn through `groupCmd`/`runGroupCmd`, which set `Setpgid` (own group), a `Cancel` that SIGTERMs the GROUP and escalates to SIGKILL after `procKillGrace`, and `WaitDelay` (`procWaitDelay`, 5s). Before this, `--timeout` enforced nothing: `exec.CommandContext` signalled only the `claude` process, so descendants survived, and stdout is collected through an os.Pipe every descendant inherits - `Wait` blocked until the LAST holder of the write end closed it, i.e. past the deadline forever, while the heartbeat kept stamping `running`. Consumed by the `/executor-retro` skill to mine real-run history (fail rates, park reasons, durations) for epic-flow improvements.
- **Handoff contract + `pm executor show` / `pm executor doctor`** (0.28.0, `internal/storage/handoff.go`, `internal/cmd/executor_show.go`, `internal/cmd/executor_doctor.go`; pm-cli-49): the executor block supplied project knowledge for EXECUTION structurally (`context_repos`, `phases`, `baseline` -> injected into the worker prompt) but nothing for the ACCEPTANCE that happens after a run - that knowledge lived in `<repo>/.claude/evidence-playbook.md`, a path hardcoded in the global `batch-finish` skill, and `pm context`/MCP did not expose the executor block at all. pm cannot inject an acceptance prompt (it never spawns the acceptance - a human or a CC session does), so the fix is to make the convention a RESOLVABLE contract instead. **`executor.handoff`** is deliberately two fields, `playbook` (path, relative resolves against the repo) + `runtime_skill` (bare name of the project-local skill that drives the simulator/device/browser): config states WHAT exists and WHERE, the playbook states what each tool is FOR and WHEN - and anything pm can DERIVE (the runtime skill's `scripts/` inventory) is derived, never configured, since duplicated knowledge drifting is the problem being solved. Rejected for that reason: `read_full_skill`/`escalation` (process rules, identical in every project -> global skill) and `required_sections` (a second copy of what pm reads off the skill). `Executor.ResolveHandoff(projPath)` returns paths + existence + derived scripts, best-effort (a missing file is reported, never an error). **`pm executor show [project]`** prints the profile as RESOLVED, not as written: phase bindings, run config, **worktree slots with their merged env** (the authoritative simulator ids / dev-server ports), context repos, and the handoff block with the derived scripts. That slot section is the point - the orbit playbook had hand-copied both UDIDs and both Metro ports, correct only until a slot changes. `pm context` / `pm_context` get ONE POINTER LINE (`## Executor: pm executor show <slug>` / `executor_profile` key), never the profile: pm_context runs at every session start (~15k chars measured), so the profile is charged only to the session that opens it. **`pm executor doctor [project]`** validates COMPLETENESS, not syntax, and the level split is the design: **ERROR = a binary filesystem fact** (declared playbook absent, dead `context_repos` path, slot path that exists but is not a git worktree - i.e. one `EnsureWorktree` would refuse) -> exit 1; **WARN = a heuristic over prose** (playbook never names a script the runtime skill ships; playbook hardcodes a slot env VALUE verbatim) -> exit 0, because one false alarm is how a validator gets switched off for good. `--strict` promotes warnings to exit 1 once the heuristics have earned trust. Drift matching is on the verbatim value with a `len >= 4` floor (so "1"/"on" match nothing) and reports file:line + the offending line so a human can judge it. An uncreated slot is OK (first `--additional` run creates it). Landed with the skill-side half in the same pass: `batch-finish`/`batch-finish-auto` now call `pm executor show` instead of the hardcoded path and are told to read the runtime SKILL.md in full, and orbit's playbook gained a "what each tool is FOR" section (plus escalation: one round of looking that does not settle a claim becomes instrumentation) and lost its copied UDIDs/ports -> doctor clean, including `--strict`.
- **Readiness contract: doctor sees the two omissions that kill a first run, and `--dry-run` stops lying** (0.37.0, `executor_doctor.go` + `run_epic.go`; pm-cli-90, from the 2026-08-07 executor retro): the fields and the gates all existed, but every tool that says "ready" looked past what actually stops a run, so a project could pass the whole chain and die on the real one. Measured end to end in an isolated `PM_DATA_DIR`: `pm projects add demo` -> `DefaultStatuses` with no `merged`/`pushed` -> `pm executor doctor demo` says **0 errors** -> `pm run-epic demo t1 --dry-run` prints a confident plan including `done status: merged` and **exits 0** -> the real run dies immediately on `done status "merged" is not in project demo statuses`. Three holes, one thesis. (a) **`checkBaseline`** WARNs when `executor.baseline` is unset. That omission is the most expensive single failure cluster the journal records - 8 subs / $44.24 across `orbit-62` + `-63`, every worker rediagnosing the same pre-existing breakage and then booking it against its own diff - and it sat invisible for SEVEN runs on a project doctor called healthy (the local `orbit` block predated the field; the VPS copy had it since 2026-08-03, which is drift nothing was watching). WARN not ERROR, per this file's split: a run without a baseline works exactly as every run did before 0.25.0. The hint is evidence-driven - when `phases.verify.cmd` is bound it names that command (the two are normally the same and `init` writes both, so one being set alone IS the signal), otherwise it points at `pm executor init`. (b) **the no-executor-block branch no longer returns early** - it runs `checkLandingStatuses` against `GetExecutor()`'s built-in defaults first. A project with no block IS the fresh project, i.e. precisely the one whose statuses list has no landing status, and stopping at "run `pm executor init`" reported it as healthy. (c) **the `done_status` gate moved into `planEpic`** as `epicPlan.doneStatusGate` (via the extracted `epicDoneStatusGate`), so `--dry-run` reaches the same verdict the real run does: it prints the WHOLE plan first (that is what a dry-run is for) and then returns the blocker, exiting non-zero. `executeEpic` still enforces it before touching a branch or a status - the gate did not move, its RESOLUTION did. A dry-run that reports readiness it never checked is worse than no dry-run, because it is the check people run instead of the real thing.
- **`pm executor stats [project]`** (0.25.3, `internal/cmd/executor_stats.go`): read-only rollup of that journal, so a retro no longer starts by hand-parsing JSONL. Prints runs per kind (`work`/`run-epic`) with their terminal status, the sub-outcome histogram, and duration/turns/cost totals + averages. The histogram's fixed print order is `subResultOrder` (`verified, merged, pushed, blocked, failed, conflict, skipped, manual` - zeros included, so "0 conflict" is visibly different from "not tracked"); anything outside it sorts alphabetically after, which today means **`aborted` (0.37.0) has no reserved row** - it prints when it occurs but never as a zero. Project resolution matches the other commands (arg, else `detectProjectFromCwd`); an empty, missing or corrupt-only journal prints a note and exits 0, never an error. Aggregation is a pure `aggregateJournal` (start lines paired FIFO with their terminal line by `runKey`) + `renderJournalStats`, so it is table-driven testable. `runKey` is `{id,kind,task_id,pid}`: since 0.27.0 (pm-cli-47) `id` is the journal's `run_id` and pairs lines EXACTLY - two terminal lines sharing an id are always one run (so a double kill counts once), two runs with different ids never merge (so a reused pid whose `start` was lost is no longer swallowed as its predecessor's kill-race twin - measured pre-fix: that run's subs/turns/cost vanished, and a double kill doubled them). `kind`/`task_id`/`pid` stay in the key because the leftover-start pass needs a holder pid, and because pre-0.27.0 lines have no id and fall back to the old ambiguous pairing plus its end-vs-killed heuristic. Three reads of the output need care: (1) a leftover `start` is a **crash** only when its pid is dead or its stamp is older than `liveWindow` (24h) - a live, recent pid reads as `running` instead, because stats is routinely run mid-epic, and the window is what stops a recycled pid on an ancient entry from masquerading as a live run forever; (2) `status` says how the MANAGER exited, not whether the work landed (`run_epic.go` hardcodes `done` on its end line whatever the subs did), so the real verdict is the sub histogram; (3) `pm run-epic` is re-entrant and re-records already-done/not-ready/dep-blocked subs as `skipped` on EVERY run, so the raw sub count inflates across re-runs - the output splits `N (X worker-backed, Y gate decision(s))` and tags `skipped`/`manual` rows `(gate)`, and turns/cost averages exclude them (they spawn no worker and report zeros). No `--json`/`--since` flags (not needed yet).
- **The acceptance becomes the third run kind: `pm finish`, the acceptance claim, auto-chain, and the Runs view** (0.41.0, epic pm-cli-100, 2026-08-08): the acceptance procedure (the `batch-finish`/`batch-finish-auto` skills) used to require a live interactive CC session, nothing stopped two acceptance sessions from taking the same run, and there was no screen listing what runs exist at all - run-state was only visible by entering one task's detail view. Four pieces, each valuable alone. (1) **The claim** (`internal/storage/finish_claim.go`, sub 100-1): a TTL lock (10 minutes, refreshed by the live acceptance the way `RunWriter.Heartbeat` refreshes run-state) stored NEXT TO THE RUN's run-state in `<projectDir>/.executor/` - never beside the accepting session, because the run may live on another machine (a mac pid written into a file on the VPS is unverifiable, so liveness is time-based, never pid-based; the claim carries `host` for messages). Atomic via the `AcquireWorktreeLock` pattern: link(2) of a fully-written tmp, expired takeover by rename-aside. Known residual window documented in `stealExpiredClaim`: between rename-aside and restore the path is briefly empty. (2) **`pm finish [tracker]`** (sub 100-4, on the run-state split from 100-2): a headless worker whose prompt tells it to invoke the `batch-finish-auto` skill - verified experimentally before the epic (2026-08-07) that headless `claude -p` sees and can invoke global skills, which is the founding fact of the design: pm supplies process, harness, guard and claim; the ~630-line procedure stays in the skill. `--yolo` by default (the acceptance is inherently broad - worktrees, ssh, git push, runtime scripts - and a curated allowlist would block it at 3am; worker-guard rides along regardless), keeps user-scope MCP (the skills drive pm through it - ordinary workers get the strict-mcp cut instead), `--sim` reserved for attended runs. The acceptance's files are `<tracker>.finish.json`/`.finish.log`/`.finish.md`: `ExecutorRunPath` is `<taskID>.json` and `ReadRunStates` keys by task ID, so an unsplit acceptance state would overwrite the very run being accepted (`storage.RunKindFinish` routes the paths; the encoding is documented as non-injective for a task literally named `x.finish`). (3) **Auto-chain** (sub 100-6): `finish_mode: auto|off` on the tracker (validated like `mode`/`epic_mode`, tri-state over MCP) makes `executeEpic` spawn a detached, Setsid `pm finish` as its LAST act, after the summary and the epic PR - no daemon and no watcher, because the manager lives to the end of the run and knows when it finished. Best-effort by contract (a failed spawn is a stderr line naming `pm finish <tracker>`, never the run's error; a held claim - a live `batch-finish-auto` session accepting subs in flight - is a quiet no-op; an account-wall abort does not chain, since most of the batch never ran). Same machine only: runner cannot reach the mac behind NAT, so "batch on the VPS, sim acceptance on the mac" is always manual - which is the attended variant anyway. Independent mode checks the base branch back out before chaining, because it otherwise ends on the last sub's branch and `git worktree add` refuses a branch already checked out - the acceptance could never open a worktree for the last sub of any batch. The chained child gets no seeded run-state (declined as beyond 100-6's AC; a child dying before `pm finish` writes its own state leaves only the .finish.log). (4) **The Runs view** (subs 100-7/100-8): `pm runs` prints one row per tracker across all projects - run state AND acceptance state, including the count of unresolved visual claims, which is the user's morning TODO list (a detached acceptance never touches the simulator, so "acceptance done" without that count reads as finished when the visual half was never checked). `storage.LocalRunRows` is the ONE aggregation (the TUI never recounts - the pre-BuildTrackers lesson); `--json` is the board's contract. Remote runners come from the GLOBAL registry `<pm-root>/config.yaml` (`storage.LoadConfig`, sub 100-3: missing file = no remotes, unparsable = loud error naming file and line, because a typo silently emptying the registry would just look like "nothing is running remotely"; entries validated per the path-component rules). The board's `viewRuns` (`R`) fetches remote rows on demand only, never on the tick - each tick with ssh in it is seconds of wedged render. Naming: deliberately NOT "journal" (already means two things) - this is "runs" (the view) and "report" (the acceptance artifact). Rejected during design: a session logger (run-state already is the log), sessions coordinating with each other (pm is the bus - the run writes artifacts, the acceptance reads them, one direction), a watcher daemon, and copying the procedure into pm's prompt.

**A crashed manager's `doing` sub is recovered, not "not ready"** (pm-cli-104, 2026-08-08). Observed on epic pm-cli-100: the manager was SIGKILLed mid-sub (a CC harness killed the background task's process group), the sub stayed on `doing` - the `aborted` path returns a sub to its ready status, but a SIGKILL cannot - and the re-entrant re-run skipped it as `not ready (status doing)` while reporting the run `done`. A run that did nothing to a sub looked like a finished epic; the fix at the time was a human moving the sub back to `todo` by hand. Now `planEpic` reads the tracker's PREVIOUS run-state (`crashRecoveredSubs`, read-only and best-effort): prior status `running` + dead pid (the `IsLive` criterion, `ProcessAliveSinceStamp` against the run's own `Started`, so a recycled pid reads as dead too) marks the subs that state left mid-flight (`SubRun.Status == "running"`, plus `CurrentSub`). `classifySub` drives such a sub when it sits on `doing` exactly - any other status (a human parked it on `waiting`, a custom status) is NOT the crash signature and stays a skip - with a loud "recovered after crash" stderr line, and it still passes the `depends_on` gate like any candidate. A `doing` sub NOT owned by a dead run (e.g. a human working it right now) is untouched, as is everything under a LIVE prior run. `--dry-run` shows the same verdict (`[RECOVER]` in the sub table) because the detection lives in the side-effect-free `planEpic`, per the readiness-contract rule (0.37.0). Deliberately narrow: only this one signature, no general "reconcile task statuses against history" pass - the spec's own instruction was to close the observed gap, not design a reconciler.

**Reviewer spawns are forced synchronous - the async default was eating whole review rounds** (pm-cli-105, 2026-08-08). Three subs of epic pm-cli-100 landed on `blocked` with "review not collected" despite done work and green verify, each costing a human a hand-run review round and a hand merge - the largest manual-cleanup item of both runs. The cause, established from the worker transcripts rather than the hypotheses in the ticket (sessions `315ff4ff`, 100-3 round 1; `3f5742db`, 100-6 round 2): the harness's Agent tool runs subagents IN THE BACKGROUND by default ("Async agent launched... you will be notified"), and the worker never passed `run_in_background`. A headless worker whose mandate is "your final message is the envelope" then ends its turn while the reviewer is still running; when the completion notification happened to arrive first (100-6 round 1), the review survived by timing luck; when it did not, the re-invoked worker went looking for a way to wait (`ToolSearch select:Monitor` - not available to workers), found `TaskStop`, killed its own reviewer and returned blocked. Both ticket hypotheses were wrong in the details: the worker was not out of turns (31 of 150) and did not pass `run_in_background: true` - the DEFAULT was the trap. Fix at the layer that already owns spawn policy (0.38.0): `forceSyncSpawn` in the guard's rewrite pins `run_in_background: false` on every generic-type spawn it allows, so the call blocks and the tool result IS the report - there is no async window, nothing to poll, nothing to stop. Scoped like the model pin (generic types only - a custom agent type running in the background is somebody's deliberate design); an absent field is forced too, because absent MEANS background on the measured build (claude 2.1.224); a non-bool value reads as unset. The review-phase prompt now states the contract (spawns block; never background, never stop one), telemetry gained `background` - what the WORKER asked for, recorded before pm's correction so the measurement cannot flatter the fix - and the deliberate non-goal: no TaskStop blocking in the guard, because with a synchronous spawn the worker is inside the tool call for the reviewer's whole life and there is nothing to stop.

- **Terminology: "odbiór" -> "acceptance" everywhere in prose** (pm-cli-106, 2026-08-08, user decision): the Polish word is gone from code comments, help strings, docs, prompts and the batch-finish skills in favor of "acceptance" - the name the code already used (`RunKindFinish`, the acceptance claim, the ACCEPTANCE column). Prose only: the command stays `pm finish`, no API identifiers, run-state file names or frontmatter fields changed. Historical design-log entries were renamed too - a terminology rename is not a change to the content of a decision, and a greppable zero beats a half-migrated vocabulary. In the skills, the quoted Polish USER TRIGGER PHRASES in the `description:` frontmatter ("odbiór taska", "odbierz caly batch"...) deliberately stay Polish - they match what the user actually says, which is an utterance, not terminology.

- **The board launches the acceptance and chains --then-finish - the X menu catches up with the third run kind** (pm-cli-107, 0.43.0, 2026-08-08): the user drives pm exclusively through the TUI, but the executor launch menu knew only `pm work`/`pm run-epic` - `pm finish` and `--then-finish` (both 0.41.0) existed as CLI-only surface, so the acceptance still required remembering a command. Two additions, both reusing what the menu already had. (1) **"Run acceptance in background (pm finish)"** (`a`), tracker-only, always via the detached "bg" path - no here/tmux variants on purpose, because an acceptance is detached-and-simulator-free by contract (the argv carries an explicit `--no-sim`, mirroring chainFinish's spawn). The argv is its own pure `finishPMArgs`, not a mode of `executorPMArgs`: `pm finish` takes only the tracker positionally (`--project` is a flag), and the menu's `!` yolo toggle deliberately does not apply (the acceptance is yolo by default per the 100-4 decision - mapping `!` to `--no-yolo` would invert the toggle's meaning in one menu mode). The `#` additional toggle DOES apply: a board-launched acceptance claims its own slot, which is exactly the propagation chainFinish refuses for lifetime reasons that don't exist here. The bg seed's one trap: the log must go to `FinishRunLogPath` - `ExecutorLogPath` would truncate the log of the very run being accepted (the run-state JSON routes itself, `WriteRunState` picks the `.finish.json` path off Kind). The preflight keeps the git-repo check but drops clean-tree: the acceptance forks no branch of its own, and the epic it accepts may have left the checkout mid-state. (2) **The `&` toggle** ("chain acceptance after the run") appends `--then-finish` to the epic argv; off = the flag is absent, so the tracker's `finish_mode` keeps deciding - the board never sends `--then-finish=false`, and the label says so on screen to keep the tri-state honest. The tracker-only guard lives in `executorPMArgs` itself, not in the caller: `pm work` has no such flag, and a stale toggle leaking into a leaf launch would be a flag-parse error. Verified end-to-end in a hermetic sandbox (PM_DATA_DIR store + fake `claude` on PATH): the full acceptance cycle ran through the board - `.finish.json`/`.finish.log` siblings, journal start/end with `yolo:true`, claim released, row in the Runs view, `W` agent-view attach - without a real worker. Out of scope by user decision: a `finish_mode` editor in the TUI (the board does not edit frontmatter, and with these two pieces it is unnecessary).

- **The detail view names the executor keys, and says which run X would start** (0.44.0, 2026-08-08, user report): everything the previous entry built was reachable only by already knowing it. The tracker's subtask header offered `(press p to pick & open)` and nothing else, and the detail view's help bar listed neither `c`, `X`, `W` nor `K` although `updateDetail` dispatches all four - so from the one screen where a user reads a tracker, the launch menu had no trace at all. Worse, the answer to "what does X do here" is not fixed: X is ONE key for three launches (`pm work` on a leaf, `pm run-epic` on a tracker, and the acceptance under `[a]`), and integration-vs-batch is decided by the tracker's `epic_mode` rather than by anything the user presses - the board passes no `--independent` flag, it just runs `pm run-epic` and lets the frontmatter decide. Four changes. (1) The header legend became `(p: pick & open · X: run epic|batch · X→a: accept)`, the noun following `epic_mode`; below `narrowHintWidth` it degrades to the keys alone, since the legend sits one line above a table already clamped to that width. (2) The help bar gained `c: claude` and `X/W/K: exec run/watch/stop`; `s: sessions` gave up its place as the one entry whose subject the head already shows. (3) The head prints `Epic mode:` and `Finish:` for a tracker, both spelled in the behaviour their EMPTY value means (`epic (integration)`, `off (launch with X→a)`) - an omitted line would read as "does not apply" for a mode that is fully in force. (4) `trackerRunNoun` is shared by the legend and the launch menu, because the fix exposed a contradiction it would otherwise have created: the menu titled itself "Run epic" for a tracker the new legend called a batch. A test asserts the two agree rather than each one's wording alone.

- **A second launch over a live run warns, and stops short of blanking its log** (0.44.0, 2026-08-08): `launchExecutor` never asked whether a run of the same kind was already in flight, so `X` twice on one tracker did three things - `os.Create` on the shared log path, a run-state seed carrying the new process's pid, and a spawn that a second `pm finish` then refuses on the acceptance claim. The middle one self-heals within 30s (the acceptance heartbeats), the first does not: the live process holds its own fd and keeps writing at its old offset, leaving a file that begins with a hole where its record was. WARN rather than block, by user decision, and the split is the point - the board's run-state maps are up to a tick old, so a block would be a race deciding whether a launch happens at all, while the authority on a second acceptance already exists in the pm process (the claim, which costs nothing but a message). What is NOT left to judgement is the log: `openRunLog` appends instead of truncating precisely when something live is writing there, since two runs interleaved in one file is confusing and a blanked record is gone. The warning is asked per KIND (`liveRunForLaunch`), never as "is anything running": a run and its acceptance are routinely live together by design, so warning about the run when the user pressed `[a]` would be an alarm about the normal state.

- **The acceptance item says WHEN it fires, because "acceptance" means two things in one overlay** (0.44.0, 2026-08-09, user report on first use): the executor menu offered `[a] Run acceptance in background (pm finish)` two lines under the `&` toggle "chain acceptance after the run" and directly under three items that all launch the epic - so nothing on the line said that pressing it starts one IMMEDIATELY, and starts no run. It now reads `Accept NOW - before, during or after the <epic|batch> (pm finish, detached)`. Naming all three moments is not padding: `pm finish` deliberately never checks whether the run has finished (`batch-finish-auto` is built to accept subs as they land), so pressing it mid-run is a use rather than a mistake, and saying "the run" is what tells the item apart from the three above it. The test asserts the timing words rather than the label verbatim, since the failure being guarded is a user reading it as a fourth way to start the epic.
