## Key patterns

- **Parent/subtask rollup**: `parent` in frontmatter holds a parent task ID (e.g. `atlas-39`), making the task a child of a tracker. Link is one-way (child→parent); a task is a "tracker" iff some other task names it as parent (derived, never stored on the parent). `storage.BuildTrackers(tasks, extraTerminal...)` (in `internal/storage/tracker.go`) groups tasks by parent and returns `[]Tracker` (parent + progress map + child rollup with `brief_line`) plus a `suppressed` set (children + trackers, excluded from flat doing lists). Used by `pm_context` (MCP, `trackers` section) and `pm context` (CLI). The generated rollup replaces hand-maintained board tables in the parent body. Subtask lifecycle: `todo → doing → merged|pushed → done` (add both to the project's `statuses`; which one a green sub lands on depends on the epic mode - see Landing statuses). Children (and the `TrackerChild.order` field) sort by `storage.LessByOrder` (Order asc, then numeric ID, then most-recently-updated) - the SAME comparator the board columns (`filteredTasks`) and the TUI tracker list (`taskChildren`) use, so all three never disagree. Set `order` via the `order` param of `pm_add_task`/`pm_update_task` (`pm_update_task` accepts a 0 to clear it), the `--order` flag of `pm add`, or `pm reorder <parent> <child-id>...` (renumbers the listed children to 10, 20, 30... in the given sequence; resolves the project by the parent's full ID, validates every ID is a real child before writing).
- **Concurrency (lost-update protection)**: task writes are atomic (tmp+rename), so the ONLY hazard is two pm processes (parallel CC sessions' MCP servers, executor managers, the board) interleaving read-modify-write and dropping each other's edits. `Store.LockProject(slug)` (internal/storage/lock.go) is a cross-process flock on `<projectDir>/.pm.lock` - hold it around FindTask -> mutate -> WriteTask and read the task FRESH inside. Wired into: the mutating MCP handlers (add/update/delete), the CLI's own minting/multi-file writers `pm add` (the lock MUST cover `NextTaskID` -> `AddTask`: the ID is derived from the tasks on disk, so two unlocked adds mint the SAME id - O_EXCL only protects the file NAME, and two different titles produce two different names) and `pm reorder` (the widest read-modify-write among the CLI commands: several children, whole-struct writes, so an unlocked run reverts a concurrent `pm_update_task` brief and body included - it re-reads the children FRESH inside the lock), `applyWorkerResult` + `recordSubFeedback` (the executor's long-window writers: their task copies predate a 30+ min worker run and MUST be re-read before writing), and `Store.MoveTask` itself (self-locks + re-reads fresh + refreshes the caller's copy in place - covers all 24 move sites incl. the board's stale card copies). Deliberately NOT wired into the board's OWN writers (the `Ctrl+j/k` order swap in `actions.go`, the add prompt's `time.Now().Unix()%100000` id) - same hazard class as `pm add`/`pm reorder`, still open. RULES: never nest LockProject in one process (second flock on a fresh fd deadlocks against your own lock - release before calling a self-locking callee like MoveTask; the release closure is sync.Once-idempotent for exactly this handoff), and `pm_move_task` deliberately has NO handler-level lock. `MoveTask`'s fresh re-read is a PRECONDITION, not a best-effort refresh: if the task file is gone (a parallel `pm_delete_task`) or the dir cannot be read, it returns an error and writes NOTHING - swallowing that error resurrected deleted tasks from the board's stale card pointers. The executor's two long-window writers now enforce the SAME precondition (via `FindTaskExact`): `applyWorkerResult` returns an error (`pm work` surfaces it; the manager parks the sub) and `recordSubFeedback` returns one that `logIfErr` reports without aborting the run - a task deleted during a 30-minute worker run no longer comes back carrying a brief nobody will look for. `Store.WriteTask` stays lenient on purpose: the board's `doUndo` resurrects a snapshot deliberately. **project.yaml is covered too**: its write path `writeProject` MERGES into the existing file (to keep comments + unknown keys), so its read->write window is wider than a task write's - `Store.CreateProject` (lock taken after MkdirAll; the lock file lives in that dir), `Store.UpdateProject` and `Store.MutateProject` all self-lock, and the same no-nesting rule applies to them. `LockProject` no longer MkdirAll's the project dir - it STATS it and errors when it is missing. The lock file lives inside that dir, so creating it made every one of the 11 lock sites able to conjure a project: a write to a typo'd slug silently created one, and locking a project someone had just deleted resurrected its dir, into which `applyWorkerResult` then wrote a 30-minute-old task - invisible forever, since no `project.yaml` comes back with it. `CreateProject` is the only site that legitimately makes the dir and it MkdirAll's before it locks; every other site resolves an existing slug, and the callers that degrade to an unlocked write on a lock error keep exactly the behaviour they had. A partial-field edit must go through `Store.MutateProject(slug, fn)` (lock -> re-read FRESH -> apply fn -> write), NOT GetProject -> mutate -> UpdateProject, whose lost-update window is as wide as the caller's think time: `pm_update_project` and `pm executor init` patch single fields and would otherwise revert a parallel session's edit to an untouched field. The worktree slot lock is separate and ALSO atomic: claim = link(2) of a fully-written tmp (rival can never read a half-written winner), stale takeover = rename-aside (see AcquireWorktreeLock).
- **Identifiers are PATH COMPONENTS, validated at the store** (pm-cli-74-1): a task ID becomes the leading component of its file name (`Filename` = `<id>-<title-slug>.md`) and a project slug becomes a directory, so both are validated where they are WRITTEN, not only in the MCP handlers - `storage.ValidateTaskID` in `Store.AddTask` (covers `pm add --id`, `pm_add_task`'s `id`, the board's add prompt; runs BEFORE the O_EXCL claim so a rejected ID leaves no phantom file) and `storage.ValidateSlug` in `Store.CreateProject` (before MkdirAll, so `pm projects add ../outside` creates nothing). `ValidateTaskID` is deliberately WIDER than `ValidateSlug` - real data holds `30422` and `ACME-253`, so digits-only and uppercase stay legal - but rejects spaces/non-ASCII on purpose (IDs get quoted into shell commands, branch names and log paths). The third identifier is `project.yaml`'s **`prefix`**, the ID SOURCE for auto-minted ids (`<prefix>-<n>`): `storage.ValidateProjectPrefix` gates it in `CreateProject`, in `pm_update_project`, and in `MutateProject` **only when the value CHANGES** (a legacy project carrying a bad prefix must stay editable in its other fields, or `pm executor init` could never touch it). A prefix that slipped in by hand still fails at add time, with an error that names the prefix and the project.yaml path instead of an ID nobody typed. `pm migrate-ids` is the one renumbering path that bypasses `AddTask` (it rewrites via the lenient `WriteTask`), so it validates the prefix in its PREFLIGHT - checking per task would renumber the alphabetically earlier projects before failing.
- **`pm work`/`pm run-epic` one-arg resolution** (pm-cli-74-1): the single-argument form scans projects in `FindTask`'s OWN three tiers (exact ID -> unique ID prefix -> title substring), each tier deciding alone, and ERRORS listing the candidates when a tier matches several projects - first-hit-wins in sorted order used to spawn a 60-minute worker in the WRONG repo. The cwd project is a TIEBREAK INSIDE a tier, never a short-circuit: standing in a repo settles a tie but does not let its title mention outrank another project's exact ID. Archived projects are excluded (as in `GetAllTasks`) unless you are standing in one; the explicit two-arg form still reaches everything. A query that is ambiguous INSIDE one project contributes `<slug>/<several>` rather than dropping out of the scan (dropping out is first-wins by another route).
- **Statuses are per-project** — read via `Store.GetProjectStatuses(slug)`. Default: `[todo, doing, waiting, done]`. Override in `project.yaml`. "ALL" view merges all projects' statuses. **Every mutation path validates** (0.29.2): `Store.MoveTask` and MCP `pm_update_task`'s `status` param reject a status outside the project's set (plus system-level `archived`, always legal) - a typo'd `pm mv` used to write it and the task vanished from every board column. `pm run-epic` hard-gates an unlisted `done_status` at run start (failing the merged-move AFTER the merge landed would desync the re-entrant done check and re-drive the sub); the INDEPENDENT-mode landing status degrades instead of gating when it is the built-in default - see Landing statuses.

## Debugging TUI layout

The instrumentation recipe and the height budget behind CLAUDE.md's layout-debugging rule:

1. **Colored section markers** - add `lipgloss.NewStyle().Background(color).Render("[TAG]")` at section boundaries to see exactly where each section starts
2. **Debug status bar** - replace the status bar with key metrics: `h` (terminal height), `curH` (computed height), `pad` (padding lines), `mch` (max card height), per-column content line counts
3. **Key formula**: `viewBoard` total visual lines = `strings.Count(output, "\n") + 1`. Must equal `m.height`. If `curH > h`, top lines get cut off by bubbletea
4. **Build with `-dbg` suffix**: use version like `0.7.1-dbg` so debug builds are clearly identified
5. **Clean up**: remove all debug code before committing. Restore `version` import if status bar uses it

Layout height budget for `viewBoard` (each item = newlines contributed):
- Title with `Padding(0,0,1,0)` + explicit `\n`: 2
- Tabs + `\n\n`: 2
- Column border/padding (`Padding(1,2)` + `RoundedBorder`): 4
- Column content (cards): `maxCardHeight` (variable)
- `\n` after columns: 1
- Confirmation line (always reserved): 1
- Status bar (no trailing `\n`): 1 visual line
- Total = `maxCardHeight + 11` (+ 1 if search/add active)

The `maxCardHeight` is computed dynamically: `m.height - overhead` where overhead accounts for all non-column lines. Column content is clamped (truncated if over, padded if under) to exactly `maxCardHeight` newlines so `JoinHorizontal` produces consistent height across projects.

## Agent docs (`pm docs`)

The canonical agent-facing usage contract lives in `docs/agent-guide.md` (a CLAUDE.md-shaped block wrapped in `pm:agent-guide` markers) + `docs/task-authoring.md`, embedded into the binary via the root-level `docs` package (go:embed) and printed by `pm docs claude` / `pm docs authoring`. Install = `pm docs claude >> ~/.claude/CLAUDE.md`; a user's CLAUDE.md is a CONSUMER of that output, never a second copy to hand-sync. **When tool semantics or the usage contract change, update `docs/agent-guide.md` in the same PR** - it ships with the release, so drift = a binary that contradicts its own guide.
## MCP server (`pm mcp`)

- **No MCP resources** (pm-cli-72-3): the 3 resources (`pm://projects`, `pm://tasks/{project}/{status}`, `pm://project/{slug}`) were removed - `pm://tasks` bypassed every output budget `pm_list_tasks` enforces (full briefs, no 50-task cap, no archived exclusion - exactly what 0.24.0/0.28.1 fixed), `pm://projects` dropped the `archived` field, and all three duplicated a tool with a worse copy. Grepped for real consumers (repo, docs/, `~/.claude/CLAUDE.md`) before deleting - none found. Use the equivalent tool instead: `pm_list_projects`, `pm_list_tasks`, `pm_get_task`/`pm_context`.
- **Output budget** (0.24.0): `pm_list_tasks` defaults to the 50 newest tasks (`limit` param overrides; `limit<=0` → default) and returns a wrapper `{tasks, total, shown, note}` - `note` states "N of M tasks shown ... narrow with project/status or raise limit" whenever the list was truncated. List summaries carry ONE-LINE briefs (`storage.BriefLine`: first non-empty line, 120-rune cap); `ac` stays full. `pm_context` caps each doing-task `body` at 2000 runes (`contextBodyLimit` in `tools.go`) with a pointer to `pm_get_task` for the rest - `brief` is never truncated there (it IS the designed cold-start vehicle). `pm_get_task` remains unbounded. **The rollup is a summary, not a reading surface** (0.28.1, pm-cli-50 - `pm_context` for orbit returned 61 757 chars over MCP and blew the tool's token limit while the same rollup from the terminal was 15 746): every brief inside `trackers` is one line - `storage.Tracker.BriefLine` (JSON `brief_line`, was the full `brief`) alongside the children's, set in `BuildTrackers` so the CLI/TUI/MCP share ONE rule - and a **finished tracker collapses its children** (`trackerFinished`: the parent's own status is terminal AND every child is `done`/`archived`/a landing status → `Children` nil + `children_omitted: true`, `Progress`/`Total` survive). That collapse is the structural half: finished epics accumulate forever and were the one part of the payload growing without bound, while a still-open child (e.g. `waiting` under a closed parent) keeps the full list. `focus_tasks` briefs and the cross-project branch's `doing_tasks` briefs compress too - they are listings. The project-scoped `doing_tasks` brief stays FULL on purpose. Measured on orbit: 62 726 → 44 350 chars MCP, 15 771 → 13 077 CLI.
- **Invariants**: links merge (never remove), body_append appends to the Log (never replaces), spec rewrites the Spec block in place, tags replace if provided, epic_mode overwrites if provided (validated). `branch`/`parent`/`brief`/`ac` are tri-state on `pm_update_task` (pm-cli-72-3, matching `mode`/`model`/`epic_mode`): omit = keep, empty string = clear; `title` stays required-non-empty (never clearable). `pm_list_tasks`/`pm_update_task`/`pm_move_task` reject a `status` outside the project's (or, cross-project, the union of every active project's) status list - `archived` is always legal. `pm_update_project` rejects a `statuses` replacement that would orphan tasks sitting on a dropped status (handler-level only, not storage - CLI/manual project.yaml edits stay lenient); an empty `statuses: []` resets to `DefaultStatuses` and is checked against THAT effective set, not the empty literal. `pm_create_project` rejects a `slug` that isn't a safe path component (`storage.ValidateSlug`, `^[a-z0-9][a-z0-9._-]*$` - deliberately not `slug == Slugify(slug)`, since `Slugify` strips literal hyphens and would reject real slugs like `app-orbit`).
- **Task mutations live in `internal/service`, and the MCP handlers are thin** (pm-cli-118-3): the cockpit's HTTP API (`pm serve`, pm-cli-118-5) has to mutate tasks exactly as MCP does - the same status validation, tri-state fields, link merge, Spec/Log zones and lock discipline - and that logic sat in closures inside `registerTools`, callable from nowhere else. `service.AddTask/UpdateTask/MoveTask/DeleteTask` now hold it verbatim over `storage.TaskStore`; `pm_add_task`/`pm_update_task`/`pm_move_task`/`pm_delete_task` decode, call and encode. The argument structs MOVED to the service package (their `jsonschema` tags are plain struct tags, so the descriptions stay one copy) and `tools.go` aliases them - the generated tool schemas were diffed before/after the refactor and are byte-identical. Caller-caused failures (status outside the set, bad mode/epic_mode/finish_mode) are typed `*service.ValidationError` so a transport can map them (MCP tool error, HTTP 400); everything else passes through. `MoveTask` checks the status up front with the store's own rule (archived always legal) purely to type that failure - the store re-checks and the message is the same. NOT added, on purpose: parent-existence validation and an empty-title rejection on add - neither exists today (a missing parent is an orphan in `BuildTrackers`), and this sub is behaviour-preserving.
- **The read side, projects and journals follow the mutations into `internal/service`** (pm-cli-118-4): `ListTasks`, `GetTask`, `Context` (with `ProjectContext`/`CrossProjectContext` and the cwd resolution), `ListProjects`, `CreateProject`, `UpdateProject` and `JournalAdd`/`JournalList` moved verbatim, so `pm serve` can return the SAME JSON agents get over MCP and `pm_context` and a future `/api/context` are one function. The DTOs became exported types with their json tags; the two results that were `map[string]any` (`projectContext`, the journal-add reply) became structs whose field order equals the maps' alphabetical key order, which is what keeps `encoding/json` emitting the same bytes - verified by dumping the tool schemas plus 35 tool calls (every read tool, every error path, budgets, journals) on one fixed store from the epic branch and from this branch and diffing: identical. `mcpserver` keeps type/const aliases and two one-line wrappers under the OLD unexported names so its test files did not change at all - the point of the tests was to stay untouched, and a rename in a test is a change a reviewer has to read. Caller-caused failures are typed `*ValidationError` on the read side too (a status outside the set, an unsafe slug/prefix, an orphaning statuses replacement, an undeclared journal, a malformed date); "not found" stays an untyped error because `FindTask` has no not-found sentinel - adding one belongs to the HTTP sub, which is the first caller that needs a 404. NOT done: repointing the `pm context` CLI onto the service functions (optional in the task, and its printer walks its own structures - a rewrite for no visible change).
- **`pm serve`: the cockpit's read-only HTTP face, on the service layer** (pm-cli-118-5): `internal/server` is stdlib `net/http` (the user's decision: HTTP JSON + SSE + go:embed React, no framework), and every JSON body IS the `internal/service` DTO the MCP tool returns - that is what the two service subs were for. Three decisions worth the line. (1) **The remote-runs fetch is injected, not moved**: `remoteRunRows` needs `groupCmd` and the test-patched `remoteRunsTimeout`, both in `internal/cmd`, which imports the server for the command - so the server takes a `RemoteRuns` hook and `cmd/serve.go` wires `pm runs`' own function in; `pm runs` is byte-identical and the escape hatch ("`{remote: not implemented}`") was not needed. In the handler tests the hook is a fake, so `?remote=1` is covered without ssh. (2) **404 needed a sentinel**: `FindTask`/`FindTaskExact`/`ResolveProject` now wrap `storage.ErrTaskNotFound`/`ErrProjectNotFound` with the message text unchanged (the sentinel text is the phrase the messages always led with), so the transport maps by `errors.Is` instead of matching prose; ambiguous ids are 400 (the caller can narrow), everything untyped is 500. (3) **The SSE poll reads directory metadata, never content**: a fingerprint of names+sizes+mtimes of the task files and of `.executor/*.json|*.claim` per project, compared every 2 s; a difference emits `tasks`/`runs` with the slug and the client refetches. Parsing run-states on every tick would cost a JSON decode per file per poll for information the client is going to fetch anyway. Routes are `GET`-qualified (including the SPA catch-all) so the mux returns 405 for any mutation attempt by itself - a read-only server should refuse, not silently serve index.html to a POST. Placeholder page when the bundle is absent answers 200 on purpose.- **The web front end is a replaceable view layer over a permanent API layer** (pm-cli-118-6): `web/` is the plainest stack that works - npm, Vite, React, TypeScript strict, Tailwind utility classes on native elements, TanStack Query + Router, oxlint + prettier (what the Vite template ships today; the spec said eslint, the template moved on and a second linter config would be a maintenance line for nothing), vitest + testing-library. The user's priority, stated the evening the sub was rewritten, was "it has to work now, it need not be pretty, the UI layer must be improvable later" - so the design decision is the DIRECTORY BOUNDARY, not the look: `src/api/` (hand-written mirrors of the Go DTOs' json tags - no schema generator, a drifted field is `undefined` in one place - plus the fetch client and react-query hooks with the keys the live feed will invalidate by) and `src/lib/` (pure functions, each with a test) are permanent; `src/routes/` and `src/components/` hold no fetch, no `useQuery`, no grouping/sorting/counting, and the visual pass (118-10) replaces exactly those two dirs. Routing is code-based: three routes do not buy the file-based plugin and its generated tree. Toolchain rule: `make check` and `make install` stay node-free (the pre-commit hook and the Go build must not need npm), `make web` fills `internal/server/dist` and restores the `.gitkeep` Vite's `emptyOutDir` removes, `install-full` is the one-shot ship, and CI runs the web checks in a separate job. The server test that asserted "the embed is the placeholder" was wrong the moment `make web` existed - a built tree is as legitimate a build as a bare checkout - so it now asserts whichever it is running in.
- **The shell is rules in `lib/`, wiring in `hooks/`, and dumb views** (pm-cli-118-9): every behaviour a reviewer might argue about is a pure function with a test - the Spec/Log split (`splitSpecLog`, the TUI's rule), relative time (`relativeTime`: minutes/hours within the day, calendar days in the reader's zone after that, an unknown `status_changed` rendered as unknown and never as "just now"), the run cells (`runCells`, a port of `RunCell.String`/`AcceptCell.String` so the page, the board and `pm runs` say the same words), the palette's matching (`paletteItems`; cmdk's own fuzzy filter is switched off so the rule is testable), the key map (`shortcuts`; the one table also renders the `?` dialog, so the help can never disagree with the keys) - and the React around them carries no rule: `useShortcuts` binds keydown and lets a modal `<dialog>` own the keyboard, `useRecentTasks` is localStorage. Three decisions: (1) the remote runs fetch has its OWN query key (`['runs-remote']`), not a child of `['runs']` - a `runs` event from the feed invalidates `['runs']` by prefix, and an ssh round-trip per runner behind a heartbeat would be exactly the poll the API refuses to be; the rows it returns are merged as "local rows + the remote-tagged rows of the last explicit fetch", never re-sorted against each other (they were fetched at different times). (2) The `tasks` event also invalidates `['projects']`: the sidebar counts come from there and move on every task edit - the spec's key list had not named it, and a stale badge next to a live list is the kind of thing that makes a dashboard feel broken. (3) Native `<dialog>` for the palette and the help, `<table>` for runs, a `<button>` drawer for the phone - no component library until the visual pass (118-10), which swaps `components/`, `routes/` and `hooks/` and leaves `api/` and `lib/` alone; the shell tests assert behaviour by role and text, not by markup, for that reason. The PWA is a manifest plus two generated icons and no service worker - installable is the requirement, offline is not; Go's MIME table lacks `.webmanifest`, so the server registers it (a text/plain manifest is not installable). One live check worth repeating after any change to the feed: a task file written into the data dir shows up in the open page within the poll interval, with no reload.
- **Groups are derived from members, and asleep has one flag** (pm-cli-118-12): the cockpit's first data-model change. The user works several repos that are one product (ACME is four pm projects, orbit three) and wanted them as ONE project on the cockpit while the TUI/CLI stay per repo. Two ways to model that: a membership list in the global config (`groups: {acme: [acme-api, acme-zap, ...]}`) or a `group:` field on each member's project.yaml. The field won: a project names where it belongs, `Store.ProjectGroups` derives the groups from the active projects, and there is no list to drift out of step with the directories - the display name is the only thing that lives in the global config (`cockpit.groups.<slug>.name`), because a name is one fact about the group, not N copies in N members. `group` is validated as a slug (it becomes a URL segment, a config key and a filter value; two spellings would split one group in half), on create and on a CHANGE in `MutateProject` - the prefix rule - so a hand-edited bad value never locks the project out of its other edits. Asleep = `archived: true`, the field that already existed and already drives `ListActiveProjects`; the alternative, reading the board's `hidden_projects` from tui-config.yaml, was rejected as UI state of one screen masquerading as a fact about the project. An archived project is in no group and no cockpit aggregation, so a group whose every member sleeps is not listed at all. The `cockpit:` block of config.yaml (`internal/storage/cockpit.go`) holds every cockpit setting in one place next to `remotes` - thresholds, cutoff hour, refresh window, section/source toggles, sidebar - and the file owns TYPE, DEFAULTS, PARSER and VALIDATION only: the meaning of each field belongs to the sub that consumes it (118-13 reads thresholds and sections, 118-14 the cutoff, window and sources, the SPA the sidebar). Two mechanics worth keeping: the file is decoded OVER `DefaultCockpitConfig()`, so an absent key keeps its default while an explicit zero (`cutoff_hour: 0`, midnight) wins without a single pointer field; and the toggle maps are checked against CLOSED lists, so a typo'd section name is a load error rather than a switch that silently controls nothing (the ValidateJournalName argument). `SaveConfig`/`MutateConfig` are the first code to write config.yaml and pay the debt config.go promised: `mergeYAMLDocuments` is `writeProject`'s merge generalised over a known-key set, comments and unknown keys survive, validation runs before the write, and the price of decoding over defaults is that the first save makes every default an explicit key. `ListProjects` (MCP, `/api/projects`) treats a broken config the way it treats a broken project - named in the note, names fall back to slugs - while `ListGroups` (`/api/groups`, the sidebar's read) fails loudly, so the sidebar never shows a wrong name as if it were the setting.
- **One attention queue, three faces** (pm-cli-118-13): the cockpit's home screen is a queue of what needs the human, and the user wanted the same queue in a Claude session's first call (`pm_context`) and in the terminal (`pm today`) - "the same picture for me and for the session". The repo already had the rule for that: `LocalRunRows` and `BuildTrackers` count once in storage and every surface displays, a client never recounts. `BuildAttention` (`internal/storage/attention.go`) follows it: sections in a fixed order, each switched by `cockpit.sections`, rows of ONE shape with a closed `actions` vocabulary decided from the row's state (the Agent Inbox pattern - a UI renders what it is handed and invents nothing), and a `GroupSummary` for the sidebar. Three rules were decided rather than derived. (1) `needs_me` ranks the run's own death above everything and reads a run-state marked `running` with a dead pid as CRASHED, not as running - the runs table's `stale` word, carried over so the queue never promises a run that is not there; a live claim is checked BEFORE the acceptance state (the acceptCell ordering: the claim is the artifact meant to be read across machines) and ranks last, because somebody is on it. (2) A waiting row's age comes from `status_changed` ONLY and an empty stamp is `null`, rendered "since ?" - `updated` moves on every edit and would reset the very clock the row exists to show; the STUCK rule uses the opposite measure, max(updated, status_changed), on purpose, because there the question is "did anything at all happen here". (3) A waiting task without `waiting_for` is flagged `no_reason` and ranked WARN, not hidden: 57 of the user's waiting tasks carried no reason on 2026-09-05 and the flag is what forces adoption. The `changes` section only EMBEDS a digest the caller passes (count + first rows) - the aggregation reads no feed cache and fetches nothing, so 118-14 plugs in without touching it. `pm_context` gets a BUDGET (`service.DigestAttention`): needs_me and stuck_projects whole, waiting capped at ten with the alarms promoted past the cap, every other section a count; best-effort, so a cockpit config typo is a note on the rollup and never a failed session start - while `/api/attention` and `pm today` fail loudly on the same typo, because for them the thresholds are the definition of what they show. `recent` (a session file touched in the last 24 h) ships configurable but not computed: the Claude session-file lookup lives in the board's code and moving it was out of this sub's scope (the spec allowed exactly this); the section says so in its `note`.
- **The change feed is the first code that leaves pm's files, so it is fenced** (pm-cli-118-14): "what changed since yesterday 18:00" needs git and GitHub, and the user's own words set the fence - each source switchable, refresh every 30 minutes but only between 07:00 and 20:00, a manual "fetch now" always, and git limited to the branches pm tasks name plus the repo's open PRs "but designed so widening it is easy". `internal/feed` is that fence. One `Source` interface, a registry of three (pm, git, github), and a new source is one file plus one registry line - Slack (118-19) is the first test of that claim. Three decisions shaped it. (1) **The cache is the product, not the fetch**: events land in JSONL per day under `<pm-root>/.cockpit/changes/` with a STABLE id per event (a commit hash, a comment id, a task+status_changed pair), so a refresh is idempotent by dedup and `pm today`, the attention queue and a restarted `pm serve` read the cache without a single network call - the aggregation from 118-13 embeds `feed.ReadDigest` and fetches nothing, exactly the seam that sub left open. Only in-window events are cached, whatever a source hands back, and a 14-day rotation keeps the directory bounded. (2) **A source fails alone**: `Feed.Refresh` records every source's outcome in a `SourceStatus` (last fetch, error text, event count) and continues past a failure; inside a source, a project without a checkout, without `gh` or with an unauthenticated one is a `*ProjectError` joined with the other projects' events - a dead VPN on one client's repo must not blank the other four. The one thing the refresh refuses to do is read a broken local store (a project whose tasks fail to read), which is not a network condition. (3) **The window is enforced by the scheduler, not the source**: `schedulerTick` asks `RefreshConfig.InWindow(clock())` and does nothing outside it; the manual POST ignores the window because a person asked. The clock is injected (`Options.Clock`), which is what makes "06:59 refreshes nothing, 07:00 does" a 300 ms test instead of a wait. External commands run through a `Runner` - the default gives each command its own process group, a 30 s cap and a group SIGKILL on expiry with pagers and prompts disabled, and `pm serve` injects one built on the executor's `groupCmd` so the discipline is the executor's; the same seam is what lets the tests fake `gh` while running real `git` on a temporary repo with a task branch. The SSE feed gained a third event, `changes`, published through a small fan-out bus rather than the directory-fingerprint poll: the poll exists to notice OTHER writers, while a refresh is this process's own act and can just say so. `NewHandler` returning a `*Handler` with `RunScheduler` is the one signature change; the scheduler needs the same feed and clock the endpoints use, and a handler that owns both is simpler than threading them through a second constructor.

## Journals (`pm journal`)

Added 0.35.0 (pm-cli-83). A **journal** is a per-project append-only record of how ONE chosen, repeatedly-troublesome subsystem actually behaves - the first instance is the iOS simulator rig in app.orbit, whose incidents had accumulated as 15 separate Claude memory files plus a hand-grown section in `.simulator-verify/config.md`: none dated, none counted, none connected to a fix.
- **The distinction that stops it duplicating memory files**: a memory file or a doc holds a **RULE** (current truth, rewritten when it turns out wrong); a journal entry holds an **EVENT** (dated, append-only, never rewritten). A rule can never answer "fifth time this month"; a journal never replaces the rule. The entry's `fix` field NAMES the rule/change it produced, and **an entry with an empty `fix` is OPEN - the open set IS the backlog**, derived, never hand-maintained. This is why the sim-naming norm from the same session went into the skill (a rule) and not into a memory file AND the journal.
- **Storage** (`internal/storage/journal.go`): JSONL per subject at `<projectDir>/.journal/<name>.jsonl`, deliberately the same grain as the executor journal one directory over (`.executor/journal.jsonl`), so the code shape and the reading habit already existed. `Incident` = `{ts, symptom, false_conclusion, cause, cost_min, fix, tags, session}`. `false_conclusion` is the load-bearing field: a subsystem that fails LOUDLY is cheap, one that returns a confident wrong answer is what burns afternoons (the trigger incident was a `RIG DEAD` printed for a live rig). `AppendIncident` RETURNS its write error rather than swallowing it like `AppendJournal` - the executor journal is observability written by a machine mid-run, this is written by whoever just paid the cost, and losing it silently loses the only record.
- **Closing an entry is a new EVENT, never an edit** (0.36.0): `Incident.Resolves []string` lists ids of EARLIER entries this one closes, and `StillOpen` = no own `fix` AND nobody has since closed it. Without it the open count could only ever grow - append-only means an entry cannot be edited to carry a fix decided weeks later - and the backlog would rot, which is the failure the journal exists to prevent. `JournalStats.ClosedLater` reports resolved-by-a-later-entry separately from `Open`, so a review's effect stays visible instead of entries silently vanishing from the count. An unknown `resolves` id is REJECTED before the write: it would fail silently otherwise (entry lands, target stays open, nobody re-derives). **The id is DERIVED, not minted** (`incidentID` = UTC day + 2-byte hash of ts+symptom): deterministic from stored fields, so `ReadIncidents` computes it for lines written before the field existed and the entire pre-existing backlog became closable without rewriting one byte of an append-only file.
- **Ordering rules, both learned from a real bug**: entries are read newest-first (the file stays append-order) and an entry whose `ts` does not parse sorts **LAST** - a raw string comparison put `"not a timestamp"` above every real date, straight to the top of the actionable list. `JournalStats.First/Last` come off the PARSED instant for the same class of reason: RFC3339 permits a numeric offset, so `...T10:00:00+02:00` compares lexicographically after a later `...T09:00:00Z`.
- **Surfaces**: `pm journal list|show|add|stats` (CLI, `--project` flag rather than a second positional) and `pm_journal_add` / `pm_journal_list` (MCP). `pm_journal_add` reports back the recurrence its own entry just produced ("2 entries now share tag X") - that sentence is what turns a log into an argument for fixing the tool, and it costs one line at the one moment someone is already paying attention. Stats travel WITH the entries in `pm_journal_list` rather than in a separate tool: the reason to read a journal is to see whether something recurs, and a caller who needs a second call for the counts will skip it.

## Timeline (`pm timeline`)

Added in pm-cli-140. A **project timeline** is the append-only record of what happened TO a project, plus dated `state` snapshots of where it stands. Measured on the vega project on 2026-09-15, that history had no home: it sat in task Logs (a journal per task - "what happened on 10.09" meant opening four tasks), in project.yaml `notes` ("stan 27.08", a dated snapshot in the field meant for current truth, three weeks stale, and overwriting it would lose the history), and in documents rewritten in place whose previous version lived only in git. None of those answers "what happened this week" or "where did we stand on date X".
- **The boundary that keeps it from being one more pile**: a task Log records what happened IN a task; the timeline records what happened TO the project (direction changes, client decisions, milestones, new people, a document arriving). The change feed's machine events are never imported. It is not the subsystem journal either: that one is an incident record with symptom/cause/fix semantics, and the name was taken.
- **A state is an entry, not a field** (`internal/storage/timeline.go`): kinds are exactly `event`, `decision`, `state`; a new state is a new line and older states stay, so "what did we think on 27.08" stays answerable. A task brief may overwrite because a task ends; a project does not. Nothing else in the tooling surveyed stored a DATED state - everything was either an event or current truth.
- **The default read is the latest state plus every entry after it, never the state alone** (`TimelineDefaultRead`): a state lies from the first entry written after it. The latest DATED state wins, so a hand-edited line with a broken ts cannot hide the real one. The growth control is a signal, not a summariser: `stale` once `TimelineStaleEntries` (10) entries or `TimelineStaleDays` (7) whole days follow the state - the changelog's Unreleased-to-release cut, which the user was already doing by hand in a plan document every few days. With no state at all the read is the newest `TimelineNoStateLimit` (10) entries and a "no state yet" note. The thresholds are constants in storage so every surface agrees.
- **Storage**: JSONL per month at `<projectDir>/.timeline/<YYYY-MM>.jsonl`, the month taken from the entry's own ts (its writer's offset, so 00:30 on the 1st lands in the month its author saw). Readers are agents that grep and want `--since`; humans read through `pm timeline`. Unlike journals nothing is declared in project.yaml - there is exactly one timeline per project. The id is DERIVED (UTC day + 2-byte hash of ts+kind+text, the `incidentID` shape), so a line written by hand gets on read the id a write would stamp. Kind, text and ts are validated before the directory is touched, and a ts after today is refused - a typo'd back-date as a state would otherwise empty the default read and mute the stale signal until that day, with no way to correct an append-only line. On read, bad lines are skipped, undated entries sort last, and lines are read without a length cap (a `bufio.Scanner`'s 1 MiB limit let one long pasted state make the whole timeline unreadable, since the write side accepts any length). No `LockProject`: like `AppendIncident`, an append is one `O_APPEND` write of one line.
- **CLI**: `pm timeline [project]` (default read, `--json`), `add` (`--text -` is the only way stdin is read - reading it whenever stdin is not a terminal could block forever on a pipe nobody closes; `--date` back-dates an entry because seeding an existing project's history is a first-class use, as with the journal), `list` (newest first, `--since`, `--kind`). The session id is stamped when the command runs inside Claude Code.
- **MCP and `pm_context`** (`internal/service/timeline.go`, `internal/mcpserver/timeline.go`): two tools over the service layer, the journal's shape. The tool descriptions carry the rules an agent needs at the moment it writes - task Log vs timeline, a state fits on a screen, write at the brief checkpoint, stale means a new state - because the description is what it reads then. `pm_context` carries the DEFAULT READ, where the journal gets counts only: a journal's readers are the sessions about to touch one subsystem, the timeline's reader is every session that starts on the project, and the delta after a state stays small because the stale signal fires at 10 entries. The state is never cut (the brief rule); the entries after it are capped at 20 keeping the NEWEST, with `since_omitted` saying how many older ones `pm_timeline_list` still has. No timeline = no key. The cross-project rollup gets one line per project (the state's date and first line) - a scan across every project is not where states are read. `pm_timeline_list` switches shape on its arguments (no filter = the default read, any filter = a capped list) rather than splitting into two tools, since both answer "what does the timeline say" and the default is the one an agent should reach for.
- **Cockpit** (`GET /api/timeline/{project}`, `web/src/lib/timelineView.ts`): the group page's "Where we left off" shows each member repo's default read - the state with its date, the entries after it, the stale line - and falls back to the repo's `notes` when the repo has no timeline yet or the read failed, so the section is never blank on the day a timeline starts. A repo with a timeline hides its notes box but keeps the edit action - this section is the only place the web edits notes, and the dialog shows them. Read-only: entries are written over MCP and the CLI. A timeline write is a `tasks` SSE event: the poll folds `.timeline/*.jsonl` into the tasks fingerprint instead of adding an event kind, because the clients that refetch on `tasks` are the ones showing where a project stands; the web invalidates `['timeline', slug]` with the rest.
## Executor (`pm work` / `pm run-epic`)

Runs pm tasks/epics by spawning **isolated headless `claude -p` workers** that implement → test → review → fix → verify, so a multi-subtask epic executes without blowing one session's context. Built + validated (epic `pm-cli-18`; first real run = atlas-64-3 → PR #151, 2026-06-17).
- **`pm work [project] <task>`** (`internal/cmd/work.go`, `work_prompt.go`, `work_git.go`) — the ATOM. Spawns one fresh `claude -p` in the project dir (loads that project's skills/CLAUDE.md/MCP by cwd), runs the inner loop on one task, returns a JSON contract (`{status,summary,branch,commits,unresolved}`). Standalone → draft PR; `--epic` → commit only. `planWork` (assemble, no side effects) + `executeWork` (run + record). `--dry-run` prints the prompt+argv without spending tokens. Flags: `--model` (opus), `--max-turns` (150), `--timeout` (120m; 60m before 0.54.1), `--yolo`, `--allow-dirty`, `--additional` (+ `--slot N`, `--base`) - see Additional worktree mode.
- **Default worker timeout 60m -> 120m** (0.54.1, 2026-08-20): `defaultWorkerTimeout` was lifted on the strength of the retro data the prep skills carried for a year - the 60m ceiling sat INSIDE the real sub-duration distribution (median 14.1 min across 74 worker-backed subs, three subs dead at exactly ~3600 s, one merged at 3530 s), and every wall hit was truncated committed work, not an impossible task. Precedence is unchanged (`--timeout` > `executor.timeout` > default), so a project that set `timeout: 90m` to escape the old default now caps LOWER than the built-in and should drop the field (the VPS orbit profile at the time of the change). The cost is the known one: a genuinely wedged `claude -p` now holds its slot for two hours instead of one before the manager kills it - the heartbeat still only proves the MANAGER is alive. A further raise is not on the table (epic-prep says so): a sub that threatens 120 minutes is a sizing problem or a per-run `--timeout`.
- **`pm run-epic [project] <tracker>`** (`internal/cmd/run_epic.go` + `run_epic_sub.go`) — the MANAGER. Split like `pm work`: side-effect-free `planEpic` (project preflight via the shared `preflightProject`, ready subs, mode, branches - what `--dry-run` prints) + `executeEpic` (the loop). One `driveSubFlow` drives a sub in both modes; the integration/independent differences (fork base, pre-branch checkout, parking, push, merge, branch cleanup) are the `subFlow` hook struct in `run_epic_sub.go`. Creates integration branch `epic/<tracker>`, drives ready subs sequentially (by `Order`), each on `feat/<slug>` branched off the integration branch; merges back `--no-ff` on verify-green → `done_status` (integration) / `done_status_independent` (batch). Blocked/failed/conflict → park on `waiting` + continue, and the sub's reason+open-questions bubble to the parent's `## Manager Notes` (via `recordSubFeedback`, deduped per-sub, refreshed/cleared on eventual merge). Re-entrant (skips merged/done). Ends with ONE draft `epic→main` PR. Never merges to main, never closes the parent.
- **`depends_on` gate** (`unmetDeps` in `run_epic.go`): a sub's `depends_on: [<sub-id>...]` frontmatter lists subs that must be `merged`/`done` first. The manager checks it BEFORE spawning a worker — an unmet dep skips the sub (no worker, no wasted tokens) and leaves it on its ready status (NOT parked on `waiting`), so a re-run auto-picks it up once the dep merges. A genuinely failed sub still goes to `waiting` (needs a fix + flip back to `todo`); a dep-skip is just "not its turn yet". Opt-in (empty = run by `Order`). Settable via `pm_add_task`/`pm_update_task` `depends_on` param; shown in `pm run-epic --dry-run`.
- **`mode: auto | manual` gate** (`classifySub` in `run_epic.go`): a sub's `mode` frontmatter marks it autonomous (`auto`/empty, default - backward compatible) or human-only (`manual`). A `manual` sub is a PERMANENT gate: the manager skips it entirely (no worker spawned, status untouched) on EVERY run, records a distinct `manual` outcome (not `skipped`), and never re-picks it - unlike the re-entrant `depends_on` skip. The human does the work by hand / with CC and moves the sub to `done_status` themselves; only then does the re-entrant done check pick it up. Use for subs needing interactive/visual work (simulator verification, design checks) that a headless `claude -p` can't do. A later auto sub with a `manual` sub in its `depends_on` stays blocked via the normal `unmetDeps` gate until the human moves the manual sub to done (no special-case logic). Only `auto`/`manual` (lowercase) are valid - `storage.ValidateMode` rejects anything else at write time. Settable via `pm_add_task`/`pm_update_task` `mode` param; shown as `[MANUAL]` in `pm run-epic --dry-run`. No CLI flag - it's a per-task frontmatter field.
- **`model` per-sub override** (0.21.1): a sub's `model:` frontmatter (claude alias or full name, e.g. `sonnet`) overrides the run-level `--model` for THAT sub in `pm run-epic` (stderr announces `model override -> ...`), and in `pm work` it wins over the flag DEFAULT but an explicitly passed `--model` wins over the frontmatter (`cmd.Flags().Changed`). Empty = inherit (backward compatible). Purpose: token economy - trivial subs (copy/color/one-prop tweaks) run on a cheaper model while investigation subs stay on opus; batch-prep/epic-prep tag subs at creation. Settable via `pm_add_task`/`pm_update_task` `model` param. Related: the reviewer count was ALSO a prompt rule at 0.36.2 (<~50 changed lines across <=2 files -> 1 reviewer, larger -> 3, production files only) - SUPERSEDED in 0.38.0, where pm sizes the review itself and refuses the spawn past the cap, and the prompt no longer states a number at all. The per-sub `model` override is deliberately independent of it: reviewers run on `executor.review_model` (default opus) whatever cheap model the sub itself was put on.
- **Hook bypass, lost results, and who owns "full validation"** (0.36.3, `worker_guard.go` + `work_result.go` + `work.go` + `work_prompt.go`; all three found in the FIRST real run under the 0.36.2 gate - `orbit-vps-1` on the orbit VPS runner, 2026-08-05 21:11-21:31 UTC, evidence in pm-cli-66-6): the gate change worked (see below), and the run surfaced three defects the isolated validation could not.
  - (a) **The envelope left the forbidden door as the only open one.** A worker's pre-commit hook died on `gitleaks: not found` (the binary was simply absent from that runner). It tried `PATH=... git commit`, then `export PATH=...`, then `ls` outside the repo - the allowlist denied each, because each needs a shell construct the envelope withholds - and then found the one form nothing blocked: `git -c core.hooksPath=/dev/null commit`. That commit is on origin: no secret scan, no lint-staged, and it reads as hook-checked. Two fixes, plus one environment fix (gitleaks installed on the runner). `workerDisallowedTools` grew the leading forms, and **`pm worker-guard`** (hidden command) is now attached to every worker as a PreToolUse hook via `--settings` inline JSON, blocking `--no-verify` / `-n` on commit+push / `core.hooksPath` / `HUSKY=0` / `rm`-ing hook files with an exit-2 message that names the legitimate move (`BLOCKED-ENV:` + return "blocked"). It rides along in `--yolo` too: yolo waives permission PROMPTS, not the project's right to have its commits pass its own hooks. Facts worth not re-deriving, each measured against a probe repo with a deliberately failing hook (2026-08-06): permission patterns match **whole tokens**, so `Bash(git -c core.hooksPath:*)` does NOT match `git -c core.hooksPath=/dev/null ...` (hence the blunter `Bash(git -c *)`); prefix patterns cannot see a **trailing** flag, so `git commit -m x --no-verify` ran under the full disallow list and only the guard stops it; `--settings` **merges** with the repo's own `.claude/settings.json` (a project PreToolUse hook still fired alongside the guard), and inline JSON is accepted by claude 2.1.71 (VPS) as well as 2.1.223 (mac), which materializes it into `/tmp/claude-settings-<uuid>.json` and leaves it there (one ~110-byte file per worker run - harmless, but do not go hunting for what wrote them). The guard **fails open** on an unreadable payload - a guard that failed closed would stop every worker on the machine the first time the hook schema moved.
  - (b) **A finished sub was recorded as failed because its receipt arrived one turn too early.** `orbit-vps-1-1` emitted `StructuredOutput` with `status: "verified"`, branch and commit - and 9 s later a background-task notification (it had run the gate with `run_in_background`) forced one more text turn, so the envelope's `structured_output` came back null and pm reported "worker returned no structured result". `parseWorkerOutput` now falls back to the worker's transcript (`<config>/projects/<encoded cwd>/<session>.jsonl`, both the project's config dir and the default; last StructuredOutput call wins, run stats still lifted from the envelope) and ANNOUNCES the recovery - silent recovery would hide the worker's turn-order defect behind pm papering over it. The prompt side tells the worker to emit the result as its final act with no background task still running.
  - (c) **A tuned verify gate saves nothing if the repo's own docs tell the worker to run the untuned one.** Same run, same box, seven minutes apart: the bound gate took **61.5 s** (tsc 34.3 + cached eslint **9.4** + prettier 17.2) while the worker ALSO ran `yarn validate` mid-implementation - because app.orbit's CLAUDE.md says to - for **155.4 s**. The implement-phase instruction now says the verify phase's bound command IS the project's full validation for the worker, verbatim, and must not be swapped for the equivalent named in the repo's docs. Fixing this in the project's CLAUDE.md instead was rejected: that file is the team's, and the tuned wrapper is per-runner.
- **Liveness has a second criterion: a recycled pid is not the holder** (0.37.1, `internal/storage/process.go` + `process_{darwin,linux,other}.go`; pm-cli-93, same external review): `ProcessAlive` was a bare `Signal(0)`, i.e. it answered "does a process with this number exist" when every caller meant "is the process that wrote this lock still running". Pids get RECYCLED - the journal already learned this on the other side of the same hazard (the `run_id` fix, 0.27.0) - so a `.pm-executor.lock` orphaned by a reboot or a `kill -9` read as held by whoever later inherited the number, and the worktree slot stayed busy until a human deleted the file; `pm executor stats` booked the crashed run as still running. `WorktreeLock.Started` had been written since day one and compared against nothing. Now `ProcessAliveSince(pid, ref)` / `ProcessAliveSinceStamp(pid, rfc3339)` add the process START TIME as the second criterion: a pid cannot be reused while its owner lives, so a process that started BEFORE the stamp is necessarily the one that wrote it, and one that started after it necessarily is not. Wired into all four readers - `LiveWorktreeHolder`, `AcquireWorktreeLock`'s stale check, `LiveSessionHolder`, `RunState.IsLive` - plus `aggregateJournal`, whose injected predicate grew a `time.Time` parameter fed by the start line's own `ts`. Three rules that are not incidental: (a) **EPERM counts as ALIVE** - a process owned by another user exists; the error directions are asymmetric, since reading a live holder as dead steals its lock and corrupts a running job while reading a dead one as alive costs a wait. (b) **Missing information degrades to bare liveness, never to "dead"** - a zero/unparseable stamp, or a platform that cannot report a start time, behaves exactly as pre-0.37.1. (c) **A 5-second grace** absorbs the RFC3339 second-truncation plus startup skew between a holder starting and stamping. The start time comes from the kernel, not from forking `ps`: `SysctlKinfoProc` on darwin, `/proc/<pid>/stat` field 22 + `/proc/stat` btime on linux (this is a render-path call). Fixture note: a run-state fixture claiming to have started before the test binary did now reads as recycled - use pid 1, which is alive everywhere and older than any stamp a test can write.
- **The hook directory is not writable by ANY tool** (0.37.1, `worker_guard.go`; pm-cli-92-1, from an external review of the repo, 2026-08-07): the 0.36.3 guard closed the commit-time doors and left the edit-time ones open. It registered a single `Bash` matcher and returned 0 for every other tool, while `workerAllowedTools` grants bare `Write`/`Edit` with no path restriction at all - so a worker denied `git commit --no-verify` could write `.git/hooks/pre-commit` to `exit 0` and then commit normally, with the commit reading as hook-checked. The bash side was open too: only `rm|mv|chmod` on the hook dir was watched, and `Bash(sed:*)` + `Bash(echo:*)` are BOTH on the allowlist, so `sed -i "1i exit 0" .git/hooks/pre-commit` and `echo "exit 0" > .git/hooks/pre-commit` needed nobody's permission. Now: the bash patterns cover in-place sed, `tee`, shell redirects and a wider verb list, and a SECOND PreToolUse matcher (`Write|Edit|MultiEdit|NotebookEdit`) judges `tool_input.file_path`. Three design points. (a) **The write matcher is a separate entry, never an alternation folded into the Bash one** - the `Bash` spelling is the one measured against a live claude (2026-08-06) and must not move; if a build matches tool names literally rather than as a regex, the new entry simply never fires and the bash side, where the cheap doors were, is untouched. (b) **The guard, not a path-negative allowlist entry** (the alternative the report offered): the allow/disallow lists are not passed at all under `--yolo`, so a rule living only there protects exactly the runs that need it least, while the guard rides along in both modes. (c) **The protected path is the whole of `.git`, not just `.git/hooks`** - `core.hooksPath` lives in `.git/config`, which is the same door one level up; `.gitignore` and `.github/` are not under `.git/` and stay writable, since the trailing separator is what decides. Reads are deliberately untouched (`cat .husky/pre-commit`, `Read`, `Glob`): a worker fixing what a hook complains about has to be able to see it. Fail-open on an unreadable payload or an unknown tool is unchanged.
- **Prose is not an action: the commit message is stripped before the patterns see it** (0.37.1, `worker_guard.go`; pm-cli-92-3, same review): the patterns ran against the WHOLE command string, so `git commit -m "add -n flag support to the parser"` was refused with a lecture about bypassing hooks - a deny for something the worker did not do, which is the guard's own founding failure one level up (a guard that cries wolf gets worked around, and this deny message tells the worker to report `BLOCKED-ENV:` and return "blocked", so a sentence in a commit message could cost a whole sub). `--no-verify` and `core.hooksPath` in a message did the same. `stripMessagePayload` now blanks the payload of `--message`/`-m`/`-am` (quoted or a single bare word, never crossing a `;`/`&&`/`|`) before matching. The boundary is the point and is tested directly: only the PAYLOAD goes, so `git commit -m "x" --no-verify` and `git commit -m "x" -n` - the trailing forms permission patterns cannot see, and the reason the guard exists - are still blocked. The pre-existing allowed case `git commit -m "document the no-verify ban"` had passed only because it lacked the double hyphen: the same class of bug, caught for one pattern and missed for the other.
- **The worker result is never lost to the envelope's shape** (0.54.2, pm-cli-117, 2026-08-20): `pm run-epic` on orbit-136 (2 subs, both finished, one pushed) recorded both `failed` with `parse claude result: json: cannot unmarshal array into Go value of type cmd.claudeEnvelope` and wrote nothing into either task - the human recovered both results from the transcripts by hand. - **Run-state heartbeat + `storage.RunWriter`** (`internal/storage/executor_run.go`): before this, `Updated` only moved on sub BOUNDARIES, so a 41-minute sub was indistinguishable from a hung run (`IsLive()` says "the process exists", not "it is making progress") - and with a 60m worker timeout an observer waited up to an hour to find out. Now `executeWork` starts a ticking goroutine right before spawning the worker and stops it the moment the worker returns (`RunWriter.Heartbeat(storage.HeartbeatInterval)`, fixed 30s - deliberately no flag and no project.yaml knob), covering `pm run-epic` (per sub, on the manager's shared epic-level run-state passed down via `workOptions.runWriter`) AND standalone `pm work` (its own). The stop func is idempotent and WAITS for the goroutine to exit, so nothing can stamp the file after the run. The heartbeat re-stamps `Updated` and touches NOTHING else (no phase guessing, no sub invention) - a dedicated field was rejected because no consumer depends on "last real state change": `execElapsed` only reads `Updated` when the run is NOT running, and `pm executor stats` classifies crash-vs-running off the JOURNAL's `ts`, never the run-state. **`RunWriter` is the serialization point**: the file write was already atomic, but the race is on the STRUCT (the main goroutine mutates CurrentSub/Phase/Subs right before writing while the ticker writes the same pointer), so every run-state access in the EXECUTOR process goes through `Update(fn)`/`Read(fn)` under one mutex - a mutex inside `WriteRunState` would not have been enough. (The board process still calls `WriteRunState` directly in `launch_executor.go`/`run_control.go`; it shares the file, not the struct, and the file write is atomic.) Cross-process, the atomicity rests on the scratch file being named per WRITER (`<path>.tmp.<pid>`, 0.27.1/pm-cli-48): a shared name let two processes interleave inside one non-atomic `os.WriteFile` and rename a torn mixture, and only the `rename` publishes. Per-pid names no longer self-overwrite, so both failure paths `os.Remove` the scratch file or every failed write leaks one. The interval reaches the call site as `cmd.workerHeartbeatInterval`, a var seeded from the const purely so tests can shrink it. A nil `*RunWriter` is a no-op on every method (a bare `pm work --epic` with no manager has no run-state). Board side: the dashboard renders `♥ <age> ago` next to the elapsed clock ONLY while a worker is actually in flight - gated on `IsLive() && CurrentSession != ""` (`execHeartbeatAge` in `executor_view.go`). `CurrentSession` is pinned right before the worker spawns and cleared in `executeWork` the moment it returns (in the same breath as the heartbeat's own stop - that pairing is load-bearing, keep them together), so the gate tracks the ticker's window on both ends. Both halves were bugs found in review: gating on `IsLive()` alone false-flagged the board's launch seed plus `executor.prepare` + baseline capture (15-min caps each) as hung, and clearing `CurrentSession` only at the sub boundary did the same for the post-worker tail (`applyWorkerResult`'s project flock, then the merge or `git push`). **What the signal does and does not prove**: the ticker lives in the MANAGER process, so a fresh stamp means "the manager is alive and inside a worker", not "the worker is making progress" - a `claude -p` wedged on a network read still looks healthy until its 60m timeout. It separates a long sub from a dead/stopped manager (and from a stale run-state whose pid got recycled, which `IsLive()` alone gets wrong); detecting a wedged WORKER would need transcript-tick stamping, which this ticket deliberately did not do.
- **Kill a live run** (`K` → confirm; `killRun` + `RunState.Kill` in `run_control.go`): group-kills the manager tree (SIGTERM to `-pgid`, escalates to SIGKILL ~2s later if still alive), stamps the run-state `failed`, and parks the in-flight sub on `waiting` so the board reflects the stop. The worker is NOT in the manager's group (it leads its own - see Subprocess process groups): it dies because the manager FORWARDS the SIGTERM to the worker's group and only then re-raises on itself, all inside the board's 2s window. That handoff is why the board must signal something catchable - a SIGKILL to the manager cannot be forwarded and would orphan the worker for the rest of its `--timeout`. The **backstop** for the cases where no forwarding can happen (the 2s escalation actually firing, an OOM kill, a crash) is `RunState.WorkerPGID`: `executeWork` publishes the worker group's pgid onto the run-state as the worker spawns and clears it the moment the worker returns - the same set/clear window as `CurrentSession`, and for the same reason, since a pgid left behind is one the next kill would signal after the kernel has recycled it. `RunState.Kill` signals that group IN ADDITION to the manager's (never instead - a live manager still forwards), and `killRun` re-reads the run-state BEFORE signalling because the board's copy is up to a tick old and the pgid changes with every sub. The board's SIGKILL escalation (`execKillCheckMsg`) kills the worker group FIRST - killing the manager first destroys the only thing that could still forward. Since 0.37.1 the escalation no longer carries the pgid in its message: it re-reads the run-state and goes through the SAME verified `RunState.Kill` (see below), so the pgid it signals is the fresh one and the identity check applies to the SIGKILL too.
- **Nothing is signalled until the pid is PROVEN to be the run's own process** (0.37.1, `RunState.Kill` + `execKillCheckMsg`; pm-cli-94, from the same external review - the reviewer's words: this is not a telemetry oversight, it is a real operational-security hole): `Kill` sent `syscall.Kill(-st.PID, sig)` off a pid read out of a FILE, with no check of any kind - and a run-state outlives its process. A `kill -9`, an OOM or a reboot leaves `status: running` behind with a pid nobody cleaned up ("A crashed executor leaves status=running with a dead PID" was already documented at `IsLive`), and after a reboot the numbers get handed out again from the bottom. Pressing `K` on such a card sent SIGTERM - and two seconds later SIGKILL - to the process GROUP of something entirely unrelated, possibly a system process. Now `Kill` verifies identity first (`ProcessAliveSinceStamp` against the run's own `Started`, the pm-cli-93 predicate) and returns a typed `StaleRunError` naming the pid instead of signalling. Three consequences worth keeping straight. (a) **The worker group rides on the MANAGER's proof**, not its own: a worker starts DURING the run, i.e. after the stamp, so the start-time test cannot apply to it - what makes `WorkerPGID` trustworthy is that a live manager clears it the moment its worker returns (plus a cheap `ProcessAlive` guard). (b) **The refusal is loud and reconciling, never silent**: `killRun` reports "Run already gone (nothing signalled), state reconciled", still stamps the run failed / parks the in-flight sub / journals the stop with that wording, and schedules NO escalation against a pid it just refused. (c) **The escalation re-reads and re-verifies** - two seconds is ample for the manager to exit and for its number to be reused, and a SIGKILL cannot be taken back, so no fresh state (or a state whose pid has moved on to another run) means no signal. Test seam: `killSignal` is `syscall.Kill` behind a var, so tests assert what WOULD be signalled without a test process ever signalling a group; board-side fixtures that need the "stopped it" path now spawn a real detached sleeper (`liveRunPID`), because a made-up pid exercises the refusal instead.
- **Subprocess process groups + bounded Wait** (0.30.1, `internal/cmd/work_proc.go`; pm-cli-57): `runWorker` and `captureBaseline` spawn through `groupCmd`/`runGroupCmd`, which set `Setpgid` (own group), a `Cancel` that SIGTERMs the GROUP and escalates to SIGKILL after `procKillGrace`, and `WaitDelay` (`procWaitDelay`, 5s). Before this, `--timeout` enforced nothing: `exec.CommandContext` signalled only the `claude` process, so descendants survived, and stdout is collected through an os.Pipe every descendant inherits - `Wait` blocked until the LAST holder of the write end closed it, i.e. past the deadline forever, while the heartbeat kept stamping `running`. Two consequences worth keeping straight: (a) `exec.ErrWaitDelay` is returned by `Wait` ONLY when the command itself exited 0 (a non-zero exit always wins as `*ExitError`), so both call sites treat it as success-with-leftovers - the worker's envelope is still honoured and a baseline captured that way is still GREEN, not "no baseline"; (b) the post-Wait SIGKILL is deliberately NOT fired on a plain non-zero exit (a red baseline is routine) - only when the deadline fired or WaitDelay unblocked us, since `Wait` has already reaped the leader and the pgid could in principle be recycled. `executor.prepare` (`runPrepare`) still uses a bare `exec.CommandContext`: it writes to `*os.File`s so it cannot hang on a pipe, but its 15-min cap still only kills the direct `sh`.
- **Executor journal** (`internal/storage/executor_journal.go`): append-only JSONL history of executor runs at `<project>/.executor/journal.jsonl` - the durable cross-run record (RunState is the LIVE state of one run, overwritten in place; the journal is never rewritten). Event model: `start` line when a run begins, `end` line with per-sub outcomes (`result`/`note`/`branch`/`duration_s`/`session`/`turns`/`cost_usd` - turns+cost lifted off the `claude -p` envelope's `num_turns`/`total_cost_usd` by `parseClaudeResult`, also stamped onto `SubRun`; `branch` = where the sub's work landed, empty for skips - the key artifact for independent batches) + run duration when it finishes, `killed` line appended by the board's `killRun` on the dead manager's behalf; a `start` with no `end`/`killed` = untracked crash. Written by `pm run-epic` (manager level) and standalone `pm work` (epic subs are journaled by the manager, not per-worker). Every line of ONE physical run carries the same `run_id` (0.27.0, `storage.NewRunID`, also stored on `RunState` so the board's `killRun` - a different process - stamps the manager's id on its `killed` line): `{kind,task_id,pid}` is NOT a run identity because pids get recycled, and without an id a consumer has to guess whether a second terminal line is a kill race (one run) or a distinct run whose `start` append was lost. - **Handoff contract + `pm executor show` / `pm executor doctor`** (0.28.0, `internal/storage/handoff.go`, `internal/cmd/executor_show.go`, `internal/cmd/executor_doctor.go`; pm-cli-49): the executor block supplied project knowledge for EXECUTION structurally (`context_repos`, `phases`, `baseline` -> injected into the worker prompt) but nothing for the ACCEPTANCE that happens after a run - that knowledge lived in `<repo>/.claude/evidence-playbook.md`, a path hardcoded in the global `batch-finish` skill, and `pm context`/MCP did not expose the executor block at all. pm cannot inject an acceptance prompt (it never spawns the acceptance - a human or a CC session does), so the fix is to make the convention a RESOLVABLE contract instead. **`executor.handoff`** is deliberately two fields, `playbook` (path, relative resolves against the repo) + `runtime_skill` (bare name of the project-local skill that drives the simulator/device/browser): config states WHAT exists and WHERE, the playbook states what each tool is FOR and WHEN - and anything pm can DERIVE (the runtime skill's `scripts/` inventory) is derived, never configured, since duplicated knowledge drifting is the problem being solved. Rejected for that reason: `read_full_skill`/`escalation` (process rules, identical in every project -> global skill) and `required_sections` (a second copy of what pm reads off the skill). `Executor.ResolveHandoff(projPath)` returns paths + existence + derived scripts, best-effort (a missing file is reported, never an error). **`pm executor show [project]`** prints the profile as RESOLVED, not as written: phase bindings, run config, **worktree slots with their merged env** (the authoritative simulator ids / dev-server ports), context repos, and the handoff block with the derived scripts. That slot section is the point - the orbit playbook had hand-copied both UDIDs and both Metro ports, correct only until a slot changes. `pm context` / `pm_context` get ONE POINTER LINE (`## Executor: pm executor show <slug>` / `executor_profile` key), never the profile: pm_context runs at every session start (~15k chars measured), so the profile is charged only to the session that opens it. **`pm executor doctor [project]`** validates COMPLETENESS, not syntax, and the level split is the design: **ERROR = a binary filesystem fact** (declared playbook absent, dead `context_repos` path, slot path that exists but is not a git worktree - i.e. one `EnsureWorktree` would refuse) -> exit 1; **WARN = a heuristic over prose** (playbook never names a script the runtime skill ships; playbook hardcodes a slot env VALUE verbatim) -> exit 0, because one false alarm is how a validator gets switched off for good. `--strict` promotes warnings to exit 1 once the heuristics have earned trust. Drift matching is on the verbatim value with a `len >= 4` floor (so "1"/"on" match nothing) and reports file:line + the offending line so a human can judge it. An uncreated slot is OK (first `--additional` run creates it). Landed with the skill-side half in the same pass: `batch-finish`/`batch-finish-auto` now call `pm executor show` instead of the hardcoded path and are told to read the runtime SKILL.md in full, and orbit's playbook gained a "what each tool is FOR" section (plus escalation: one round of looking that does not settle a claim becomes instrumentation) and lost its copied UDIDs/ports -> doctor clean, including `--strict`.
- **Readiness contract: doctor sees the two omissions that kill a first run, and `--dry-run` stops lying** (0.37.0, `executor_doctor.go` + `run_epic.go`; pm-cli-90, from the 2026-08-07 executor retro): the fields and the gates all existed, but every tool that says "ready" looked past what actually stops a run, so a project could pass the whole chain and die on the real one. Measured end to end in an isolated `PM_DATA_DIR`: `pm projects add demo` -> `DefaultStatuses` with no `merged`/`pushed` -> `pm executor doctor demo` says **0 errors** -> `pm run-epic demo t1 --dry-run` prints a confident plan including `done status: merged` and **exits 0** -> the real run dies immediately on `done status "merged" is not in project demo statuses`. Three holes, one thesis. (a) **`checkBaseline`** WARNs when `executor.baseline` is unset. That omission is the most expensive single failure cluster the journal records - 8 subs / $44.24 across `orbit-62` + `-63`, every worker rediagnosing the same pre-existing breakage and then booking it against its own diff - and it sat invisible for SEVEN runs on a project doctor called healthy (the local `orbit` block predated the field; the VPS copy had it since 2026-08-03, which is drift nothing was watching). WARN not ERROR, per this file's split: a run without a baseline works exactly as every run did before 0.25.0. The hint is evidence-driven - when `phases.verify.cmd` is bound it names that command (the two are normally the same and `init` writes both, so one being set alone IS the signal), otherwise it points at `pm executor init`. (b) **the no-executor-block branch no longer returns early** - it runs `checkLandingStatuses` against `GetExecutor()`'s built-in defaults first. A project with no block IS the fresh project, i.e. precisely the one whose statuses list has no landing status, and stopping at "run `pm executor init`" reported it as healthy. (c) **the `done_status` gate moved into `planEpic`** as `epicPlan.doneStatusGate` (via the extracted `epicDoneStatusGate`), so `--dry-run` reaches the same verdict the real run does: it prints the WHOLE plan first (that is what a dry-run is for) and then returns the blocker, exiting non-zero. `executeEpic` still enforces it before touching a branch or a status - the gate did not move, its RESOLUTION did. A dry-run that reports readiness it never checked is worse than no dry-run, because it is the check people run instead of the real thing.
- **`pm executor stats [project]`** (0.25.3, `internal/cmd/executor_stats.go`): read-only rollup of that journal, so a retro no longer starts by hand-parsing JSONL. Prints runs per kind (`work`/`run-epic`) with their terminal status, the sub-outcome histogram, and duration/turns/cost totals + averages. The histogram's fixed print order is `subResultOrder` (`verified, merged, pushed, blocked, failed, conflict, skipped, manual` - zeros included, so "0 conflict" is visibly different from "not tracked"); anything outside it sorts alphabetically after, which today means **`aborted` (0.37.0) has no reserved row** - it prints when it occurs but never as a zero. Project resolution matches the other commands (arg, else `detectProjectFromCwd`); an empty, missing or corrupt-only journal prints a note and exits 0, never an error. Aggregation is a pure `aggregateJournal` (start lines paired FIFO with their terminal line by `runKey`) + `renderJournalStats`, so it is table-driven testable. `runKey` is `{id,kind,task_id,pid}`: since 0.27.0 (pm-cli-47) `id` is the journal's `run_id` and pairs lines EXACTLY - two terminal lines sharing an id are always one run (so a double kill counts once), two runs with different ids never merge (so a reused pid whose `start` was lost is no longer swallowed as its predecessor's kill-race twin - measured pre-fix: that run's subs/turns/cost vanished, and a double kill doubled them). `kind`/`task_id`/`pid` stay in the key because the leftover-start pass needs a holder pid, and because pre-0.27.0 lines have no id and fall back to the old ambiguous pairing plus its end-vs-killed heuristic. Three reads of the output need care: (1) a leftover `start` is a **crash** only when its pid is dead or its stamp is older than `liveWindow` (24h) - a live, recent pid reads as `running` instead, because stats is routinely run mid-epic, and the window is what stops a recycled pid on an ancient entry from masquerading as a live run forever; (2) `status` says how the MANAGER exited, not whether the work landed (`run_epic.go` hardcodes `done` on its end line whatever the subs did), so the real verdict is the sub histogram; (3) `pm run-epic` is re-entrant and re-records already-done/not-ready/dep-blocked subs as `skipped` on EVERY run, so the raw sub count inflates across re-runs - the output splits `N (X worker-backed, Y gate decision(s))` and tags `skipped`/`manual` rows `(gate)`, and turns/cost averages exclude them (they spawn no worker and report zeros). No `--json`/`--since` flags (not needed yet).

**A crashed manager's `doing` sub is recovered, not "not ready"** (pm-cli-104, 2026-08-08). Observed on epic pm-cli-100: the manager was SIGKILLed mid-sub (a CC harness killed the background task's process group), the sub stayed on `doing` - the `aborted` path returns a sub to its ready status, but a SIGKILL cannot - and the re-entrant re-run skipped it as `not ready (status doing)` while reporting the run `done`. A run that did nothing to a sub looked like a finished epic; the fix at the time was a human moving the sub back to `todo` by hand. Now `planEpic` reads the tracker's PREVIOUS run-state (`crashRecoveredSubs`, read-only and best-effort): prior status `running` + dead pid (the `IsLive` criterion, `ProcessAliveSinceStamp` against the run's own `Started`, so a recycled pid reads as dead too) marks the subs that state left mid-flight (`SubRun.Status == "running"`, plus `CurrentSub`). `classifySub` drives such a sub when it sits on `doing` exactly - any other status (a human parked it on `waiting`, a custom status) is NOT the crash signature and stays a skip - with a loud "recovered after crash" stderr line, and it still passes the `depends_on` gate like any candidate. A `doing` sub NOT owned by a dead run (e.g. a human working it right now) is untouched, as is everything under a LIVE prior run. `--dry-run` shows the same verdict (`[RECOVER]` in the sub table) because the detection lives in the side-effect-free `planEpic`, per the readiness-contract rule (0.37.0). Deliberately narrow: only this one signature, no general "reconcile task statuses against history" pass - the spec's own instruction was to close the observed gap, not design a reconciler.

**Reviewer spawns are forced synchronous - the async default was eating whole review rounds** (pm-cli-105, 2026-08-08). Three subs of epic pm-cli-100 landed on `blocked` with "review not collected" despite done work and green verify, each costing a human a hand-run review round and a hand merge - the largest manual-cleanup item of both runs. The cause, established from the worker transcripts rather than the hypotheses in the ticket (sessions `315ff4ff`, 100-3 round 1; `3f5742db`, 100-6 round 2): the harness's Agent tool runs subagents IN THE BACKGROUND by default ("Async agent launched... you will be notified"), and the worker never passed `run_in_background`. Both ticket hypotheses were wrong in the details: the worker was not out of turns (31 of 150) and did not pass `run_in_background: true` - the DEFAULT was the trap. Scoped like the model pin (generic types only - a custom agent type running in the background is somebody's deliberate design); an absent field is forced too, because absent MEANS background on the measured build (claude 2.1.224); a non-bool value reads as unset. The review-phase prompt now states the contract (spawns block; never background, never stop one), telemetry gained `background` - what the WORKER asked for, recorded before pm's correction so the measurement cannot flatter the fix - and the deliberate non-goal: no TaskStop blocking in the guard, because with a synchronous spawn the worker is inside the tool call for the reviewer's whole life and there is nothing to stop.

The handoff block now takes an optional third field, `rig_skill`, naming the skill that BRINGS THE RUNTIME INTO EXISTENCE - deliberately distinct from `runtime_skill`, which drives a runtime that already exists; conflating them would put "how to verify" and "how to boot" behind one name and the acceptance reads them at different moments (every visual claim vs. only when the status check says DOWN). Resolution got a shared helper (`resolveSkillRef`) searching the repo's `.claude/skills` then `.claude/commands`, then falling back to the user's global `~/.claude/skills` - new for BOTH skill fields, because a rig skill is typically machine knowledge (how THIS machine's dev loop stands up, spanning three repos) and forcing a copy into the repo would recreate the drift the contract exists to remove; project-local always wins, and the existing precedence is unchanged for configs that resolved before. The rig skill's `scripts/` are deliberately NOT inventoried by `show` (unlike the runtime skill's): the runtime inventory exists so the playbook can be checked for mentions of each tool, while a rig skill's SKILL.md is its own manual, read whole exactly once, when the runtime is down. `doctor` stays on its axis: unset `rig_skill` is silence (a CLI project's runtime needs no standing up - warning every project would be noise), declared-but-unresolvable is ERROR (a binary filesystem fact: the acceptance would be sent to a cold-start procedure that does not exist). `pm executor stats`/`context` are untouched - the field is read at acceptance time, by `pm executor show`, which prints it with a status-check-first warning so nobody restarts a healthy rig.

- **A same-session re-claim is the hand acceptance's heartbeat** (0.49.0, pm-cli-113): a claim taken by hand (`pm finish claim`) had NO refresh path at all - `AcquireFinishClaim` refused every live claim including the holder's own, `RefreshFinishClaim` needs the claim struct only the resident `pm finish` process retains, and the CLI printed "NOTHING refreshes a claim taken by hand" as a fact. So a batch-finish-auto session's claim lapsed 10 minutes in (orbit-117: started == refreshed for a 23-minute acceptance), leaving the run invisible to every surface and free for the auto-chain to race - the exact collision the claim exists to prevent. Now a live claim re-acquired from the SAME host under the SAME non-empty `--session` is refreshed in place instead of refused: identity is host+session because the pid died with the claiming CLI and `started` is precisely what a later invocation cannot know; an EMPTY session matches nothing (two anonymous claims are two acceptances); the refresh delegates to `RefreshFinishClaim`, inheriting the scratch+rename write, the payload preservation (`started`, pid, session - the claim's age holds still on every surface) and the refusal inside the last refresh-tick before the TTL (a lapsing claim is a takeover in progress, not a refresh candidate; an expired own claim is taken over FRESH, because a real gap must show as one). The CLI tells the two outcomes apart by the stamps - a fresh claim is born with `started == refreshed`, only a refresh separates them - and prints the heartbeat instruction on the claim it can refresh, the lapse warning on the session-less one it cannot. EXCLUDED: lengthening the TTL (it protects runs from dead sessions; the missing piece was refresh, not patience) and a resident refresher process (the CC session is the resident - it just needed a command that works).
- **The 0.47-0.49 review debt paid in one pass** (0.49.1): a high-effort adversarial review of `231f293^..main` (the retro fixes plus `rig_skill`) confirmed six defects; the fixes share one theme - a forensics or telemetry mechanism quietly weaker than its own documentation claimed. (1) ORDERING: every run kind now calls `ReconcileCrashedRuns` BEFORE writing its own run-state - the file is keyed by task id, and the reversed order meant a re-run of the SAME task (the most common follow-up to a crash, and the flagship case the feature's own comment named) destroyed the dead run's forensics one step before the reconciler looked for them; reconciliation only worked when a DIFFERENT task ran first. Covered by an integration test that stages a dead same-task run and asserts the crashed line survives the re-run. (2) `pm finish` now ARMS the crash journal it was already documented as arming - the detached auto-chained acceptance is precisely the run a session harness SIGTERMs, and it died leaving an orphaned start that the reconciler then described as uncatchable, false on both counts; it also reconciles before its state write, same ordering rule. (3) `describeCrash` names a third cause it used to omit: a CATCHABLE signal that landed while no worker was in flight - the signal journaling rides the worker's forwarder (`runGroupCmd` only), so a Ctrl-C between subs writes nothing and is indistinguishable from an OOM kill in the journal; the line says so now instead of sending a retro hunting for a reboot that never happened. **A hand-driven acceptance records its verdict, or it never happened** (pm finish record, 2026-08-12). The ACCEPTANCE column (`pm runs`, board `R`) reads exactly two artifacts: a live claim, and `<tracker>.finish.json`. A headless `pm finish` writes the second; a hand-driven acceptance (a batch-finish-auto session) held only the first - so the moment its claim lapsed, the batch it accepted read as "-", indistinguishable from never accepted (observed on orbit-114/-117: a dead `.finish.claim` next to no `.finish.json`, while -108/-109, accepted headless, kept their verdicts). Refusals mirror the claim's semantics: a LIVE claim held by anyone else refuses unless `--session` matches (the holder recording mid-claim is the designed flow, and the reminder to `pm finish release` is printed), an expired/corrupt claim reads as free, and a headless acceptance whose run-state is `running` + `IsLive` is never overwritten (it records its own result when it returns; a STALE `running` - dead pid - is the recovery case and records fine). Deliberately NO journal lines: `pm executor stats` pairs `start`/`end` by run_id, and an `end` with no `start` would surface in the deaths report as a crash - so a hand acceptance shows in the runs table but not in stats, a documented gap rather than a fake pairing.

- **Settings are a PATCH of a resolved block, and a group's order is a number, not a key position** (pm-cli-118-18): the first write into config.yaml from the web, and two decisions shaped it. (1) **The screen sends what changed, the server keeps the rest**: `POST /api/settings` decodes into pointer fields and toggle maps that merge key by key, so a form with thirty controls posts two keys, a stale tab cannot revert a setting it never touched, and the file keeps its comments and unknown keys through `storage.MutateConfig` - the same merge `writeProject` pays for. The alternative, PUT the whole block, was rejected because the SPA would then have to KNOW the block's shape and defaults to echo them back, and the 118-15 rule is that it never does (`/api/config` resolves the defaults server-side). Validation is the service's, as a `*ValidationError` naming the field, with two minimums stricter than the file's own (`every_seconds` >= 5 min unless 0, thresholds >= 1): a hand-edited file may say `every: 1m` and be honoured, but a form must not make the cockpit the busiest process on the machine by a slip of the wheel. (2) **The sidebar's manual order lives in `cockpit.groups.<slug>.order`**, not in the map's key order the file happens to have: YAML maps carry an order and JSON objects do not, so the 118-15 sidebar had to fall back to the API's order for `manual`. (2) **One subprocess per workspace per refresh, with a wall**: start, a handful of calls, stop - the server's cache warms on each start, which is the price of never keeping a token-holding process alive between refreshes; `SlackTimeout` covers the handshake and every call, and the group is SIGKILLed, so an `npx` that hangs on a network prompt cannot hold the scheduler. (3) **Header-driven CSV**: the server's README describes its tools but not its result columns, and the columns of a tool that returns "a CSV" are exactly what a minor version renames; matching by name over a few spellings each, and treating a row with neither text nor time as the pagination cursor, is what lets a rename degrade to a missing field instead of a permalink filed as a message. Mentions and DMs are found through the user's own handle (`me`), the one fact the server cannot supply - without it the source says so per workspace and still reads the mapped channels. Everything is exercised against a stdio JSON-RPC fake on PATH, so the test runs the real transport and the real parse and touches no workspace.

- **The simulator in a batch run: a per-task runtime phase, a once-per-run rig check, and readings that are hypotheses** (pm-cli-122, 2026-09-05, retro section 3). Workers never touched the iOS simulator, so every sim-dependent fix landed at acceptance, and the journal held 20+ sub notes of "TODO: verify on simulator". Three verified causes, three fixes, in payback order. (a) No rig existed for the worktree slot - `executor.prepare` was `yarn install` and slot 1's simulator was not even booted while its Metro ran - so `executor.rig` is a project command run ONCE per run after prepare, in the claimed slot WITH the slot's env (`SIM_UDID`, the port - prepare deliberately gets none), and only when a sub of the run has `runtime: on`; it never aborts anything, it produces a verdict (`RIG UP` / `RIG DEAD (<reason>)`) that is rendered into the runtime-on workers' prompts and journaled as `rig: up|dead`. Decided with the user: the cold start stays OUT of the run - a native build is 15-40 min on the sim-rig journal, and a headless run that spends 40 min building and then still reads DEAD makes every sub pay for a machine problem nobody is there to see; `rigTimeout` (10 min) is the rule's enforcement, a warm start (boot, Metro, launch, prove) fits under it. (b) The worker contract routed the sim to TODO and the allowlist had no `xcrun`/`curl`/skill scripts - so a sixth phase `runtime` (after verify, before pr; bound per project like any phase, the orbit binding is `skill: simulator-verify`, a web project binds its own - pm-cli-123) is opt-in PER TASK via `runtime: on`, and `executor.runtime_tools` are appended to the allowlist for that task's worker only. Decided with the user: a frontmatter FIELD, not a tag - MCP `tags` replace wholesale, so one unrelated re-tag would drop a tag-based opt-in silently, and a field is validated, tri-state and visible in `--dry-run` (`runtime=on`). A runtime-off task sees `runtime: skip` and an unchanged envelope: "subs without a visual AC pay nothing extra" is the acceptance criterion and it holds at the run level too (no runtime sub = no rig check at all). (c) The rig produces false readings even with a human present (32 sim-rig incidents, 15 false readings, 8h20), and a headless worker has nobody to catch a confident false PASS - so a reading is never a verdict: the runtime phase runs AFTER the gate and can neither upgrade nor demote verify-green, and every reading is an `OBSERVED:` line in `unresolved` carrying a positive AND a negative control plus the evidence path, phrased as what was seen, never as "verified on the simulator" - a hypothesis the acceptance confirms with the same controls. The worker never boots, builds, relaunches or re-points the runtime; a reading it could not take is a `TODO:`. Rejected: making every sub drive the sim (cost, and the false-reading tax paid on every sub), a cold start inside the run (above), a tag-based opt-in (above). `pm executor doctor` WARNs on each half-configured combination of binding / rig / tools and is silent when the phase is unused. Not in this change: the batch-finish skills treating `OBSERVED:` as a claim to re-check (a skill edit, outside the repo), and the orbit `project.yaml` block itself (`rig`, `phases.runtime`, `runtime_tools`) - both follow once a real batch with one visual sub has run.
- **`handoff.runtime_skill` may be global, but never silently** (pm-cli-123, `internal/storage/handoff.go`): the web runtime driver (`web-verify`, `~/.claude/skills`) is one skill for every web project on the machine - Next.js, Vite + React, the cockpit itself - so copying it into each repo's `.claude/skills` would recreate the drift the handoff contract exists to remove, and a repo-only `runtime_skill` (0.49.1) made every web project's doctor ERROR on the one correct configuration. The 0.49.1 concern was real, though: a repo-missing skill that happens to exist on this machine passes silently and fails on the machine the repo is synced to. Both hold at once by resolving in the repo first, falling back to the pinned `claude_config_dir` (the dir the acceptance actually loads skills from, as for `rig_skill`), and FLAGGING the fallback (`ResolvedHandoff.RuntimeSkillGlobal`): `doctor` reports it as a WARN naming the dir (`--strict` promotes it), `show` prints a line under the skill, and a name found nowhere stays an ERROR that now names both searched roots. Rejected: a separate `global_runtime_skill` field (two names for one concept, and the playbook's script inventory would have to know which one to read) and making the fallback silent (the 0.49.1 bug, verbatim).
- **The cockpit's look is a morning paper, and the view layer proved replaceable** (pm-cli-118-10, 2026-09-05): the visual pass the user postponed on 2026-09-02 ("now it has to work, it does not have to be pretty") ran last, over the complete set of screens, with the `frontend-design` skill loaded first and the direction written to the task's Log and accepted before the first edit. The direction: an editorial ledger - a masthead with the date, sections in a fixed order separated by rules, rows as dispatch lines - because the screen is read once in the morning, top to bottom, and a dashboard of tiles and charts answers a different question ("how are we doing") than the one the cockpit exists for ("what needs me"). Fraunces for the masthead and section heads, Instrument Sans for everything else, warm OKLCH neutrals, a dark theme that is lighter surfaces rather than inverted colours, one highlighter band for the keyboard selection, state glyphs always next to their colour (the user's rule from 118-8, kept). Three decisions worth recording. (1) **The layer boundary was the acceptance test, and it held**: `web/src/api/` and `web/src/lib/` did not change by one line and the 140 vitest tests passed with no assertion edited - which is only possible because 118-9 put every rule in `lib/` with a test and left the components with props in, JSX out. The one temptation was `cn` (shadcn's class joiner), which its CLI wants in `lib/utils.ts`; it lives in `components/ui/cn.ts` instead, because `lib/` is domain rules and this is a styling helper. (2) **shadcn and lucide are material, not the look, and part of shadcn was declined on purpose**: Radix Dialog, Select, Checkbox and Tabs would have replaced the native `<dialog>`, `<select>`, `<input type=checkbox>` and the URL-driven tab links the tests assert on - a change of behaviour dressed as a change of looks - so only the presentational components were copied (`button badge input textarea separator kbd table tooltip`), and even those are styled through the ledger's own tokens rather than shadcn's defaults. The `@/` alias the copied components import through is the one build-config change (tsconfig `paths`, vite `resolve.alias`). (3) **Fonts ship in the binary**: `@fontsource-variable` packages bundled by Vite instead of a font CDN, because the cockpit is reached over Tailscale from a phone that may have no route to Google Fonts, and a page that renders in a fallback face on the machine it was designed for is not the page that was designed. Cost: ~110 KB of woff2 in `dist/assets`, subset by unicode-range so a Latin page loads two files. Rejected: a second accent colour (the severity palette already carries four hues; an interaction accent on top reads as noise, so links and pressed pills are ink), animating anything but the one entrance and the dialogs (the reference: one orchestrated reveal beats scattered micro-interactions), and cards - the wireframe's bordered blocks became rules, because a card around every section is the tile dashboard by another name. Verified by hand in Chrome (desktop, light and dark, the dialog, the help, the palette) and in Playwright at a 390 px viewport (Chrome's window floor is ~500 px); the user's own review on a phone is the acceptance criterion.
- **The human's status beats the machine's run-state files in the attention queue** (pm-cli-118-11 follow-up, 2026-09-05): on the first real morning with the cockpit, 9 of the 21 "needs me" rows were trackers the user had already moved to `done` - orbit-108 sat under "acceptance failed: stopped by user" because of a `finish.json` from a month earlier, and eight more under "run finished, no acceptance yet". `needsMeRows` iterated every tracker `BuildTrackers` returned and read only `.executor/`, never the tracker's own status, so a decision taken in the board or in Linear changed nothing on the home screen. Now a tracker on `done` or `archived` (`closedByHuman`) is skipped in `needs_me`, and a child whose parent is closed is skipped in `landed_no_pr`. Landing statuses (`merged` / `pushed`) deliberately do NOT count: they are the executor's stamps, and a tracker on them is precisely one still waiting for a human. The files are left alone - deleting run state is the cleanup screen's job (the cockpit-cleanup tracker), and a re-opened tracker gets its rows back for free. The wider gap this exposed - no "ignore" verb for a run the human will not accept, no bulk action over 56 waiting tasks without a reason, no way to tell a quiet-by-nature repo from a stuck one - is recorded as the cleanup tracker's spec rather than patched here.
- **The review floor** (pm-cli-130, 2026-09-06; `internal/cmd/review_floor.go`): the 2026-09-06 end-to-end test of the runtime phase (report `~/.claude/pm/pm-cli/.research/runtime-phase-e2e-2026-09-06.md`) ran four fake epics, and in the fourth (pm-cli-129) the worker skipped the review phase outright - telemetry `spawns: 0`, envelope `verified` - and the manager merged the sub into the epic branch. "Review is decided by pm" (0.38.0) had a ceiling (how many, which model, how many rounds, refuse past it) and no floor; the only signal was a zero in the journal that nothing read. Decision: one rule, `verified` + non-empty production diff + zero reviewers that ran = not verified, enforced at two points that are deliberately redundant. The hook side is a fifth PreToolUse matcher on `StructuredOutput` - the tool a `--json-schema` worker ends with, whose tool_input IS the envelope - so the refusal lands one turn before the worker would have ended, when it can still spawn the reviewer and finish properly (a demotion after the fact costs a human round-trip). The manager side (`demoteUnreviewed`, after `CollectReviewTelemetry`, before `applyWorkerResult` and the merge/push) covers the cases the hook cannot: a build where the matcher never fires, a result recovered from the transcript, a worker that ended by prose. Both fail open (no telemetry = nothing measured; no diff base; an empty production diff has nothing to review) - the floor guards trust in a landed sub, and a worker stuck at its final turn because a hook could not see the repo would be the reviewer cap's original sin one level up. `storage.ReviewTelemetry` gained `reviewers` (top-level, allowed, generic-typed - the number the floor reads; `spawns` keeps its old meaning) and `skipped` (set by the manager on demotion, never by the hook), and `pm executor stats` prints "review skipped: N sub(s)". Rejected: a prompt rule alone (the prompt already said to review; the worker did not), and refusing at the Agent-tool level (there is nothing to refuse when the worker never calls it).
- **`$SLOT` in runtime_tools, and the rig section that shows the forms** (pm-cli-130, 2026-09-06): the runtime phase's allowlist (pm-cli-122) named the skill scripts by the main checkout's absolute path, and in the e2e test not one runtime worker executed a skill script - test A's worker typed the slot's relative path (10 of 71 calls denied, 85 turns of raw `xcrun` instead), the web workers typed `~/...`, `export WEB_PORT=...`, `WEB_PORT=5181 node ...` and `sh <script>` (4 and 7 denials). Every one of those is a different literal prefix, and no static pattern can name a slot path that differs per slot. Decision: a `$SLOT` placeholder expanded per render to the worker's tree (one entry serves every slot AND the main checkout), the UP rig section lists the exact prefixes and the slot's variable names with the two rules the denials broke (no export/prefix, no `~`/relative/`sh`), and the doctor WARNs on the one shape known to be wrong (a main-checkout path with slots declared). Rejected: making pm rewrite the worker's command in the guard hook (a rewrite of a Bash command is a much wider door than a rewrite of a spawn's input, and the allowlist is Claude Code's, not pm's); an allowlist wildcard `Bash(<dir>/*:*)` as the fix (undocumented glob semantics - the per-script prefix is the documented form); the spec's "WARN on any path outside every slot and the config dir" (a skill installed under a toolkit repo and symlinked into the project is legitimate, and would have warned). Kept out of the prompt itself: the allowlist rules live in the rig section because only a runtime-ON worker with an UP rig needs them.
- **A server that answers is not an app that mounted** (pm-cli-130, 2026-09-06; web-verify skill + the pm-cli data-dir rig, no pm change): the cockpit rig's false UP in e2e test C1 came from keeping Vite between rigs while `prepare` swapped `node_modules` under it - the HTTP probes were green and the page was blank (504 "Outdated Optimize Dep" on every dep).
