# The cockpit

`pm serve` is the HTTP face of pm: a JSON API, a change feed and a React app. **Using it** below is the current state - screens, keys, routes, what the API writes. The sections after it are the design record of what was built, screen by screen, each in the words of the task that built it; a later entry supersedes an earlier one, so where an early entry says a button is "disabled until X lands", the entry for X is where it went live. The rules an agent editing it must obey stay in `CLAUDE.md`. The `pm-cli-118-15` ids are this repo's own convention for a task; where [design-log.md](design-log.md) has an entry under the same id, it carries the reasoning.

## Using it

```sh
pm serve --addr 127.0.0.1:7070
```

The front end is a Node build, so it is in the binary only after `make install-full` from a clone; a `go install` binary serves the API and a placeholder page that says so. The change feed's scheduler runs `git` and `gh` in the projects' checkouts every `cockpit.refresh.every` inside `cockpit.refresh.window`; its cache lives under `<pm data dir>/.cockpit/`.

**Security: there is none.** No auth, no TLS, and the API is not read-only: its POST routes edit tasks, focus and settings, start and kill runs, launch sessions and can spend tokens. The only guard is the `X-PM-Client: cockpit` header every POST must carry, which stops a stray cross-site form, not a person. Bind it to localhost and reach it over a tunnel you trust (Tailscale, ssh).

**Screens** (`web/src/routes/router.tsx`):

| route | screen |
|---|---|
| `/` `?g=<group>` | Today: the attention queue, group chips, refresh, dismiss / restore per section |
| `/g/$group` `?tab=&repo=` | one group: overview (where we left off, doing list, trackers), board, runs, changes |
| `/p/$slug` | a project: alias to its group's board tab |
| `/p/$slug/t/$id` | one task: Spec / Log, status select, brief and `waiting_for` edits |
| `/runs` | solo shifts first, with the solo launch form; the executor runs table only when `cockpit.show_executor` is on; "fetch remote" is an explicit button |
| `/changes` `?g=` | the change feed with source chips, mark seen, and the LLM report panel |
| `/review`, `/review/$id` | PR code review: start from a PR URL, a Slack message or a sentence; the report, cancel, one-click approve |
| `/solo/$project/$shift` | a solo shift's report as a digest, mark read |
| `/settings` | the `cockpit:` block as a form, plus per-project group / Slack mapping / asleep |

**Keys** (`web/src/lib/shortcuts.ts`): `1` Today, `2` Changes, `3` Runs, `4` Review, `,` Settings; `j`/`k`/`Enter` walk rows; `t` toggles focus on the selected task; `g` then a letter filters by group; `[`/`]` switch tabs; `Esc` closes; `?` help; `Cmd/Ctrl+K` the palette.

**Row actions** are the closed `actions` set the API puts on every attention row; the UI words them and never invents one (`web/src/lib/rowActions.ts`). Live: `open`, `claim`, `rerun_finish`, `resume_run`, `kill`, `release_claim`, `dismiss`, `open_report`, `focus_toggle`, `set_waiting_for`, `back_to_todo`, `mark_seen`, `sleep_project`. Still pending: `report` (no acceptance-report view yet) and `open_pr` (needs the task's PR link). Every action but `dismiss` goes through a confirm dialog.

**API** (`internal/server/server.go`; every route is method-qualified, an unknown `/api/*` path is a JSON 404, errors are `{"error": "..."}` with 400 for a validation or ambiguity error, 404 for an unknown task or project, 409 for a busy claim or a stale run, 500 otherwise):

| GET | |
|---|---|
| `/api/projects`, `/api/groups`, `/api/config` | projects with counts; groups; the resolved `cockpit:` block |
| `/api/tasks`, `/api/tasks/{project}/{id}`, `/api/context` | the `pm_list_tasks` / `pm_get_task` / `pm_context` shapes |
| `/api/timeline/{project}` | the timeline default read with its verification block |
| `/api/attention` `?project=` `?group=` | the queue, `pm today --json` byte for byte |
| `/api/runs` `?remote=1`, `/api/runs/{project}/{id}/plan` | run rows (remote only on request), the argv a launch would run |
| `/api/focus`, `/api/changes`, `/api/report` | today's plan; the feed; the LLM report state |
| `/api/reviews`, `/api/reviews/{id}` | PR reviews |
| `/api/solo`, `/api/solo/plan`, `/api/solo/{id}`, `/api/solo/{project}/{shift}/report` | shifts, the launch preview, one shift, its report digest |
| `/api/events` | SSE: `tasks {project}`, `runs {project}`, `changes {sources}`, `report`, `settings`, `ping` - what changed, never what to do; the page refetches |

| POST (needs `X-PM-Client: cockpit`) | |
|---|---|
| `/api/tasks/{project}/{id}` | status, brief, `waiting_for` |
| `/api/focus/toggle` | add / remove a task on today's plan |
| `/api/projects/{slug}` | group, Slack mapping, `archived` |
| `/api/settings` | the `cockpit:` block, written back with comments kept |
| `/api/runs/{project}/{id}/{action}` `?yolo=&additional=` | `claim`, `release_claim`, `rerun_finish`, `resume_run`, `kill` through `internal/runctl` |
| `/api/changes/refresh`, `/api/changes/seen` | refresh the feed now; mark rows seen |
| `/api/report`, `/api/report/dismiss` | write the LLM report (spends tokens); dismiss its suggestion |
| `/api/reviews`, `/api/reviews/{id}/cancel`, `/api/reviews/{id}/approve` | start, cancel, approve a PR review |
| `/api/solo`, `/api/solo/{id}/stop` | launch a solo shift (`claude --bg`, Claude Code 2.1.272 or newer), stop one |
| `/api/attention/dismiss`, `/api/attention/restore` | hide rows of `needs_me` / `solo_reports` / `landed_no_pr`; bring them back |

The SSE poll fingerprints directory metadata only (names, sizes, mtimes of `*.md`, `project.yaml`, `.timeline/*.jsonl`, `.executor/*.json` and `*.claim`) every 2 s, pings every 15 s. The remote-runs ssh fetch is injected from `internal/cmd` and never runs unless asked.

## The design record

## Today and the group sidebar

**Today + the group sidebar (pm-cli-118-15)**: `/` is the Today screen over `/api/attention` (`routes/TodayPage.tsx`), `?g=<group>` narrows every section to one group through the API's own `?group=` (the filter lives in the URL so a phone bookmark carries it; `indexRoute.validateSearch` + `lib/groupFilter`); the old project list is no longer `/`, its content lives on under `/p/$slug`. Sections render EXACTLY the ones the API returns, in its order - the UI knows their wording (`lib/attentionView` `sectionMeta`: title, one "how it is counted" line, the empty-state sentence) and a view cap (`SECTION_CAP` 7 + "show all", `capSection`; the API's own truncation, e.g. the changes digest, is reported as "+N more on this section's screen"), never their membership. A row (`components/AttentionRow`) is glyph + project chip + id/title + the API's `reason` + age (`lib/ageLabel`: `age_seconds` null renders "since ?", never another stamp) + one button per entry of the row's `actions` - `lib/rowActions` words each action and says which sub enables it (`open` works, `open_pr`/`report` wait for a link/endpoint, the rest are disabled with the sub id as the title until 118-16/118-21 land - they did, and every action but `report` and `open_pr` is live now, see Using it). Glyphs are text, never colour alone (`lib/glyphs`: severity ✗▲●○, the waiting/stuck sections override with ⧗/◔; the sidebar's counter columns ✗👁⧗◔). The sidebar (`components/GroupSidebar`) reads the `groups` summary of the unscoped attention query and the `cockpit.sidebar` block of `/api/config` through `lib/sidebarView`: `columns` (default: glyph, name, four counters with zeros as dots, member repos under a multi-repo group when `show_repos`), `plain` (no counters), `rail` (glyphs only, names in tooltips), `width` in px; `sort` `worst` = the API's order, `last_activity` sorted in lib, `manual` FALLS BACK to the API order (JSON object keys carry no order - an explicit order field on the config endpoint is what would enable it); asleep projects are one "asleep (N)" line. A group link opens its first repo's board until the group page (118-17) exists (`groupTarget`). On a phone the sidebar is a chip strip over the content (the drawer is gone). Keys: `1/2/3/,` switch screens (`/`, `/changes`, `/runs`, `/settings` - the two 118-18 screens are placeholder routes so the keys already lead somewhere; `4` = `/review` arrived with the PR review screen), `j/k/Enter` walk the home rows, `t` is registered for focus (wired in 118-16), `g <letter>` is a chord filtering by group (`groupHotkeys` assigns one letter per group, `useShortcuts` arms it for 1.5 s). New query key: `['config']`. Tests: `lib/*.test.ts` per rule, `shell.test.tsx` home over a fake `/api/attention` (order, empty sentence, cap/elsewhere, actions, `?g=` narrowing via the exact-URL fake route, the chord, `1/3`, `j/k/Enter`, the three sidebar variants + `last_activity`).

## The group page and the Runs screen

**The group page + the Runs screen (pm-cli-118-17)**: `/g/$group` (`routes/GroupPage.tsx`) is the project page of the cockpit - a group is one client/product over one or more repos (`group` on every `/api/projects` row; `lib/groupView` derives members, name, the board repo) - with the tab in the URL (`?tab=overview|board|runs|changes`, `?repo=` for the board; `[`/`]` step the tabs). **`/p/$slug` is an ALIAS**: with no task open it redirects (`<Navigate replace>`) to that repo's group, Board tab, so old links and the palette keep working; with a task open it stays the detail's layout (board beside the detail) - the board itself moved to `routes/BoardPane.tsx`, shared by both. Overview: "Where we left off" = the `notes` of EVERY member repo (`/api/projects` rows now carry `notes`; editing goes through the 118-16 dialog as `edit_notes` -> `POST /api/projects/{slug}`; the spec's `cockpit.groups.<slug>.notes` does not exist - 118-12 never added it - so per-repo notes are the v1, recorded as a SPEC-CONFLICT in the sub's brief); "Needs me" and "Waiting on" are the SAME `AttentionSection` rows as the home, narrowed by the API's `?group=` (side by side from the `wide:` breakpoint, 820 px, defined in `index.css`); "In progress (doing)" = the doing tasks of every member (one `tasksQuery` per repo via `useQueries`), ordered in `lib/doingView` by activity = the later of `updated`/`status_changed` (the API has no such field; the derivation lives in lib with a test, never in a component), idle past `cockpit.doing_idle_days` (from `/api/config`) marked ◔, a tracker row shows its rollup progress; "Trackers" = each member's `/api/context` rollup joined with its `/api/runs` row (`trackerRows`), cells worded by `lib/runCells`. Board tab = `BoardPane` with a repo switcher; Runs tab = the Runs screen filtered to the members; Changes tab = the feed's events of the group (`filterChanges`, plain list). **Runs** (`routes/RunsPage.tsx`, `lib/runsView`): the default order is "needs me first" = a JOIN with the `needs_me` section of the unscoped `/api/attention` - its order IS the rank (failed › visual › landed without acceptance › partial › live claim), the UI adds no ranking of its own; `newest` = the API's order, `by project` = a stable sort over it; the default filter "unfinished only" = the run is live OR the queue has a row for it (remote and placeholder rows are always kept - they were asked for); the first column is a fixed-width glyph (the queue's severity, ▶ live, ○ otherwise), and three time columns come off the new raw stamps (`runTimes`: duration to the end or to now, since-end for a finished run, heartbeat age for a live one). Tests: `lib/runsView|doingView|groupView.test.ts`, `shell.test.tsx` "group page" (header, chips, tabs, notes, narrowed queue, doing order + idle, trackers join, the `/p/` redirect, repo switch, `[`/`]`, changes tab) and "runs" (default filter + order, the three times, sort toggles, remote fetch).

## The Changes screen, Settings and the settings write

**The Changes + Settings screens and the settings write (pm-cli-118-18)**: `/changes` (`routes/ChangesPage.tsx`) is the whole feed off `/api/changes` with the source chips doubling as filter AND status (`lib/changesView` `sourceChips`: off / never fetched / error text / last HH:MM; an erroring source lists its error under the strip), a group filter in the URL (`?g=`, the home's `groupFilter` + the `g <letter>` chord), "refresh now", "mark all seen" and a per-row "seen" (both through the 118-16 dialog as `mark_seen`), unseen rows highlighted, row times as `eventTimeText` (HH:MM today, "yest. HH:MM", else "Mon DD HH:MM"), and the `ReportPanel` placeholder above the feed ("report is off" until 118-20). `/settings` (`routes/SettingsPage.tsx`) is ONE form over the resolved `/api/config` (`lib/settingsView`: `formFromConfig` -> the user edits -> `patchFromForm(base, edited)` = the PATCH of what changed, nothing else, or null) in the wireframe's groups (sources + `git: scan every branch`, cutoff, refresh, thresholds, the read-only needs-me order, home sections in `SECTION_ORDER`, sidebar, project groups with name + manual `order` + a per-repo group select), saved by an explicit Save to **`POST /api/settings`** -> `service.UpdateSettings` (pointer fields = absent keeps; toggle maps and `groups` merge key by key; validated as a `*ValidationError` NAMING the field before the write - hour 0-23, window `HH:MM-HH:MM` ending after it starts, `every_seconds` 0 = off or >= `MinRefreshEvery` 5 min, thresholds >= 1, variant/sort/section/source names from the closed lists, group slugs; then `storage.MutateConfig` keeps comments and unknown keys, and the resolved block is answered). Below the form, the per-project settings write each `project.yaml` through the existing `POST /api/projects/{slug}` (`service.UpdateProjectInput` gained `slack`; `group` and `archived` already decoded): a Slack row (workspace label + channels text, `slackMappingOf` parses "a, #b c"; an empty mapping REMOVES the key), the Asleep section (`archived`), and the repo-to-group select - **sleep, wake and move go through the dialog** (`confirmText` kinds `sleep_project`/`wake_project`/`move_repo`; sleep warns that the project leaves every group and the queue), the form's Save and a Slack row's save are explicit buttons and post directly. **Config on the wire, 118-18 additions**: `groups` is an ARRAY in the manual order (`storage.CockpitConfig.GroupOrder`: placed groups by `order` then slug, unplaced after by slug - a JSON object carries no order, which is why the sidebar's `manual` sort was a fallback until now; `lib/settingsView` `manualSidebarOrder` applies it, groups the config does not name follow in the API's order), each with `order` (`cockpit.groups.<slug>.order`, 0 = unplaced); `git.all_branches` (`cockpit.git`, read by the git source through **`feed.Configurable`** - `Refresh` hands every source implementing `Configure(cfg)` the CURRENT block before its Fetch, so an edit takes effect on the next refresh, no restart; the slack source of 118-19 takes its server list the same way). After a settings write the server publishes **SSE `event: settings`** (`{}`; the `changeBus` now carries `{event, data}`), and the client invalidates `['config']`, `['attention']`, `['projects']`, `['groups']` (`useLiveInvalidation`); the `settings` mutation kind invalidates the same plus `['changes']` explicitly. Nothing is cached per process: every handler re-reads config.yaml, so a change is live on the next request. `pm config show` prints the group order and the git switch. Tests: `service/config_test.go` `TestUpdateSettings` (patch keeps the rest + comments, every bad value names its field and writes nothing, 0 = off), `server_test.go` `TestSettings` (403/400, the write + SSE + next GET, project group/archived/slack with `# comment` kept, empty slack removes the key), `storage/cockpit_test.go` (GroupOrder, negative order, git round-trip, slack in project.yaml), `web/src/lib/changesView|settingsView.test.ts`, `shell.test.tsx` "changes screen" (chips + states, source and group narrowing, mark seen through the dialog with the row's `ts`) and "settings screen" (values from the API, Save disabled until dirty then posts only the diff, sleep asks and warns, a Slack row saves, a repo move asks). ## Mutations from the web

**Mutations batch 1 (pm-cli-118-16) - every POST is the MCP tool's service function, behind one header**: `POST /api/tasks/{project}/{id}` decodes its body STRAIGHT into `service.UpdateTaskInput` (`DisallowUnknownFields` - a typo'd field is a 400, never a silent no-op; the path's project/id override the body) and calls `service.UpdateTask`, so tri-state (`""` clears, omitted keeps), link merge, Spec/Log, status validation and `LockProject` are the service's and never re-stated; `POST /api/focus/toggle` `{task_id}` -> `service.ToggleFocus` (new: the board's `t` over the same `storage.FocusPlan` - the task must exist in an active project, a stale plan is carried over like the board's `handleStalePlan` before the toggle, no lock because focus.yaml is root-level and the board writes it lock-free too); `POST /api/projects/{slug}` -> `service.UpdateProject` (the cockpit sends `notes`; an empty `notes` means KEEP, as in MCP, so notes cannot be cleared from the web). **Every POST under `/api/` needs `X-PM-Client: cockpit`** (`server.ClientHeader`/`ClientValue`, `requireClient`) or it is a 403 before the body is read - the 118-14 POSTs (`/changes/refresh`, `/changes/seen`) included; not auth (there is none, localhost/Tailscale), the one thing a cross-site form or a stray curl does not send. Errors as before (400/403/404/500). Tests: `TestMutations` in `server_test.go` (403 matrix, tri-state, Log append, 400s, 404s, path-over-body, focus round-trip through `ReadFocusPlan` + `/api/focus`, project notes, and an HTTP-vs-service comparison on two identical fixtures whose resulting tasks must match byte for byte minus the stamps); `service/focus_test.go`. **Web**: `apiPost` always sends the header; `api/mutations.ts` = `MutationRequest` (task | focus | seen | project) + `runMutation` + `useRowMutation` (invalidates `['attention']`, `['tasks', slug]`, `['task', slug]`, `['context', slug]`, `['focus']`, and `['changes']`/`['projects']` per kind - explicitly, never relying on the SSE event alone). **Every action goes through ONE confirmation dialog** (the user's rule: nothing fires by accident): `lib/confirmText` is the pure part - `describeAction` (heading = id + title, project, one sentence of what will happen, an optional field pre-filled by `initialValue`, a warning: `waiting` without a reason warns "no reason = alarm", an empty brief warns "clears") and `requestFor` (the exact body: `set_waiting_for` = status waiting + reason in one request, `back_to_todo` = status todo + `waiting_for: ""`, `mark_seen` = the row's `since` as `ts`); `components/ConfirmDialog` renders it in a native `<dialog>` (form submit = Enter in an input, ⌘/Ctrl+Enter in the textarea, Esc cancels; focus moves into the dialog on open so both work); `hooks/useConfirmedAction` is the glue (pending action + value + the mutation + a 3 s toast). Home: the row buttons `focus`/`waiting…`/`back to todo`/`seen` are live (`lib/rowActions` `pending: ''`), `t` on the selected row asks the same dialog, run-control actions stay disabled until 118-21. Detail (`/p/$slug/t/$id`): a status `<select>` over the project's statuses (choosing one opens the dialog; `waiting` asks for the reason), `set/edit reason`, `write/edit brief` (textarea, overwrite like MCP); body/Spec are NOT editable from the web in v1. Tests: `lib/confirmText.test.ts`, `shell.test.tsx` "mutations go through the dialog" (open + Esc = no request, `t` + confirm posts `/api/focus/toggle` with the header, waiting warning + Enter posts status + reason, brief textarea + ⌘Enter, status select, a 400 keeps the dialog open with the error).

## Run control

**Run control from the web (pm-cli-118-21) - `internal/runctl` + `POST /api/runs/{project}/{id}/{action}`**: the attention row's run actions (`claim`, `release_claim`, `rerun_finish`, `resume_run`, `kill`) are the FIRST place HTTP starts processes, and the rules are the board's, re-stated ONCE in `internal/runctl` (no bubbletea; `internal/server` cannot import `internal/cmd`, so the spawn is a detached `pm <args>` like the board's "bg"/"finish" branch, never a call into the manager). `Controller.Plan(project, id, action, flags)` is the one place the argv is decided - it is what `GET /api/runs/{p}/{id}/plan?action=&yolo=1&additional=1` answers (argv, cwd, log, warnings, the claim session, the kill target/pid) and exactly what `Spawn` runs, so the dialog's preview IS the command: `resume_run` = `run-epic <slug> <id>` for a tracker / `work` for a leaf (+`--yolo`, +`--additional` only when the project has worktree slots - `additional_avail`), `rerun_finish` = `finish <id> --project <slug> --no-sim` (+`--additional`) and **never `--sim`** (nobody may be at the screen; there is no tmux variant here). Warnings are the board's (a live run of the same kind, not a git checkout / dirty tree without `--additional`, a held claim) - shown, never blocking. `Spawn`: `os.Executable` (the chainFinish rule, not "pm" on PATH), `Setsid`, the log truncated for a fresh run and APPENDED when one is live, the run-state seeded so the queue shows the run at once, env **`PM_LAUNCH_SOURCE=cockpit`** which `pm run-epic`/`pm work`/`pm finish` stamp into their journal start line as **`source`** (`storage.LaunchSource`; a kill from the web stamps it on its `killed` line too), and `pm executor stats` prints "launched from: N cockpit, M cli/board". `Claim` = `storage.AcquireFinishClaim` with session **`cockpit-<host>`** and a heartbeat goroutine (`ClaimHeartbeat` 3 min, stops at `ClaimMaxHold` 1 h so a forgotten claim lapses on its TTL); a claim held by anyone else is a `*runctl.BusyError` (409, the body names host/pid/session/age); `Release` drops only a claim carrying this session on this host (after a restart too). The attention row of a live claim the cockpit itself holds (`storage.CockpitOwnsClaim`: host + the `cockpit-` prefix) carries the new **`release_claim`** action and says so in its reason. `Kill` is the board's `killRun` step for step (`pickRun` = liveness first, the run wins a tie; re-read by kind; `RunState.Kill(SIGTERM)` with a `*storage.StaleRunError` reported as 409 and NOTHING signalled; the failed stamp, the journal line with the subs so far, `ReleaseWorktreeLock`, the killed acceptance's own claim released by SESSION match, the in-flight sub parked on `waiting`, SIGKILL after `KillEscalation` 2 s only when the re-read state still names the pid); nothing to kill is a 409 too (`*NoRunError`). Errors: 404 unknown project/task, 400 unknown action / a body that is not `runctl.Flags`, 409 busy/stale/no-run, else 500; every POST needs the client header. `Options.RunControl` injects a controller whose `Exe` is a fake script in tests. **Web**: the run kinds are `PendingKind`s (`lib/confirmText` `isRunKind`); `useConfirmedAction` fetches `useRunPlan` (key `['run-plan', p, id, action, yolo, additional]`, `staleTime: 0`) while the dialog is open and re-fetches when a checkbox changes, the confirm button waits for the plan (`loading`), `flagOptions` says which checkboxes each action offers (resume_run: yolo + additional; rerun_finish: additional; the rest none) and disables `additional` when the project has no slots, `previewOf` renders `cd <cwd> && pm ...` (or the kill/claim target) in the dialog's `command preview` block, the plan's warnings render as alerts, and the toast carries pid + log / claim state / the parked sub (`runToast`). The `run` mutation kind invalidates `['runs']`, `['attention']`, `['tasks', p]`, `['context', p]`. `sleep_project` on a stuck-project row goes through the same `sleep_project` dialog as the settings screen. Tests: `internal/runctl/runctl_test.go` (plans incl. never-sim, spawn through a fake `pm` that records argv + `PM_LAUNCH_SOURCE`, the seeded state, kill + escalation + journal + park, stale and no-run, claim heartbeat / re-claim = refresh / release / foreign claim busy), `server_test.go` `TestRunControl` (plan 400/404, 403 without the header, spawn -> `/api/runs` live -> kill -> second kill 409, claim -> `release_claim` on the row -> release, foreign claim 409 naming the holder), `web` `confirmText.test.ts` "run actions" + `shell.test.tsx` "run control" (the plan preview, a flag re-plans, Esc posts nothing, confirm posts the flags, kill names the pid).

## Solo launch

**Solo launch from the web (pm-cli-141, `internal/solo` + `/api/solo`)**: the Runs screen's "launch solo" form starts an unattended `/solo` session as a **`claude --bg` background session** (CC 2.1.272 agent view; `claude attach <id>` jumps in from a terminal, Ctrl+Z detaches, `claude logs`/`claude stop`/`claude rm`), never headless `-p` (no way to jump in) and never tmux. `Controller.Plan(Input)` is the one place the argv is decided and exactly what `Start` runs, so the dialog's preview IS the command: the launcher flags restated once (`buildArgv`: `--dangerously-skip-permissions --autocompact 400k --settings '{"worktree":{"bgIsolation":"none"}}' [--setting-sources user,local iff the repo's .claude/settings.json has permissions.ask rules] [--model m] --name solo-<slug> --bg "/solo <queue> [--sim|--web|--no-runtime] [--push] [--pr] [--max-tasks N] [--max-hours H] [--base b]"`). **`bgIsolation: none` is load-bearing**: without it a bg session refuses Edit/Write in the main checkout until it moves into a `.claude/worktrees/` worktree, and solo works in the main checkout. `--session-id` is IGNORED with `--bg`, so the join is by the short id `--bg` prints (`backgrounded · <id> · <name>`, regex over stdout) and the session UUID (= the shift id) comes later from `claude agents --json --all` (the ONLY supported state interface; `~/.claude/jobs/<id>/state.json` is not a contract) - `Launch.state` is that row's `state` (`working|blocked|done|failed|stopped`; no row = `unknown`, or `starting` within `StartingGrace` 2 min; a stored `Stopped` stamp = `stopped`; a failed spawn = `error`), cached `AgentsTTL` 3 s because the web polls every 5 s while a launch is live (`.shift/` is not in the SSE fingerprint). The supervisor is PER CONFIG DIR, so every call (`--bg`, `agents`, `stop`) runs under the project's `claude_config_dir` and the table's attach command carries a `CLAUDE_CONFIG_DIR=<dir> ` prefix when it is not the default. **Launch env** (`solo.Environ`): `os.Environ()` minus `ANTHROPIC_API_KEY`/`AUTH_TOKEN` (the subscription pays), `CLAUDECODE`/`CLAUDE_PID`/every `CLAUDE_CODE_*`/`CLAUDE_JOB_DIR` (a `pm serve` started inside a CC session leaks its `CLAUDE_CODE_SESSION_ID`, and `pm session-id` reads that FIRST - the solo guard marker would carry a foreign id), plus `CLAUDE_CONFIG_DIR=<project's>` and `PM_LAUNCH_SOURCE=cockpit`; NEVER `PM_HEADLESS` (project hooks read it as "no simulator"). Stop is ONLY `claude stop <id>` - the supervisor RESTARTS a process killed by a signal.
