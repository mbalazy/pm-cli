# pm-cli

Local task tracker. Data: `~/.claude/pm/<project-slug>/`, binary: `pm`.

## Build

```
make install              # build + install (uses VERSION from Makefile)
make check                # gofmt-check + vet + staticcheck + go test ./...
make test-race             # go test -race ./... (also run by CI, not part of check)
make install VERSION=X.Y.Z  # override version
```

Git hooks live in `githooks/` (versioned; `git config core.hooksPath githooks` - already set locally). `pre-commit` just runs `make check`, so the hook, `make check`, and CI share one target set and can't drift apart. `staticcheck` is resolved via PATH → `go env GOBIN` → `GOPATH/bin` and fails with an install hint when missing (`go install honnef.co/go/tools/cmd/staticcheck@latest`). Fix failures - never bypass with `-n`.

CI (`.github/workflows/ci.yml`) runs on push to `main` and on every PR: `make fmt-check`, `make vet`, `make staticcheck`, `make test-race` - the same Makefile targets used locally, plus the race detector (deliberately not part of `make check`, which stays fast for the local commit-time gate).

IMPORTANT: Always use `make install` (not raw `go install`). Version is set via ldflags in Makefile. Bump `VERSION` in Makefile on each release. Current: **0.37.1**. Binary goes to `~/.local/share/go/bin/pm` (GOBIN).

## Tests

```
go test ./internal/... -v          # all tests
go test ./internal/storage/ -v     # single package
go test ./internal/storage/ -run TestSlugify -v  # single test
```

Always add tests when implementing new features or fixing bugs. Conventions:
- Go stdlib `testing`, table-driven tests, `t.Run("case", ...)` subtests
- `t.TempDir()` for I/O tests (auto-cleanup)
- Same package tests (access to unexported functions)
- `setupTestStore(t)` helper in `store_test.go` for tests needing a Store with project + tasks
- Invariant tests (links merge, Log append, Spec rewrite, brief lifecycle) live in `tools_test.go`; the `ApplySpec`/`ExtractSpec` unit tests live in `internal/storage/spec_test.go`
- **Executor paths**: test through a FAKE `claude` binary (`fakeClaude` in `internal/cmd/work_exec_test.go` - a PATH-prepended script emitting a canned result envelope), never by spending tokens; covers verified/blocked/crash/garbage paths of `executeWork` (the envelope's green word was `merged` before 0.34.0 and is still accepted - `normalizeWorkerStatus`)
- **MCP handlers**: test END-TO-END via the SDK in-memory transport (`startMCP` in `internal/mcpserver/e2e_test.go`) so the real registered closures run - do NOT re-simulate handler logic in the test body (the pre-0.23 tests did, which is why coverage sat at 12%)
- **Concurrency**: lock/race invariants live in `internal/storage/lock_test.go` + the `TestAcquireWorktreeLockAtomicRace` two-acquirer hammer in `worktree_test.go`; run suspects under `-race`

## Verification

- After code changes: `make check` (runs fmt-check + vet + staticcheck + test); run `make test-race` too before pushing anything touching concurrency/locking
- After TUI changes: `make install` + run `pm board` and test interactively
- After MCP changes: `make install` + test with `pm_context` / `pm_list_tasks` in Claude Code
- After storage changes: verify task files in `~/.claude/pm/` have correct frontmatter

## Key patterns

- **Frontmatter tasks**: `.md` file with YAML frontmatter (id, title, status, created, updated, links, branch, parent, tags, brief, ac, order, sessions, depends_on, mode, model, epic_mode) + markdown body
- **Parent/subtask rollup**: `parent` in frontmatter holds a parent task ID (e.g. `atlas-39`), making the task a child of a tracker. Link is one-way (child→parent); a task is a "tracker" iff some other task names it as parent (derived, never stored on the parent). `storage.BuildTrackers(tasks, extraTerminal...)` (in `internal/storage/tracker.go`) groups tasks by parent and returns `[]Tracker` (parent + progress map + child rollup with `brief_line`) plus a `suppressed` set (children + trackers, excluded from flat doing lists). Used by `pm_context` (MCP, `trackers` section) and `pm context` (CLI). The generated rollup replaces hand-maintained board tables in the parent body. Subtask lifecycle: `todo → doing → merged|pushed → done` (add both to the project's `statuses`; which one a green sub lands on depends on the epic mode - see Landing statuses). Children (and the `TrackerChild.order` field) sort by `storage.LessByOrder` (Order asc, then numeric ID, then most-recently-updated) - the SAME comparator the board columns (`filteredTasks`) and the TUI tracker list (`taskChildren`) use, so all three never disagree. Set `order` via the `order` param of `pm_add_task`/`pm_update_task` (`pm_update_task` accepts a 0 to clear it), the `--order` flag of `pm add`, or `pm reorder <parent> <child-id>...` (renumbers the listed children to 10, 20, 30... in the given sequence; resolves the project by the parent's full ID, validates every ID is a real child before writing).
- **Brief field**: `brief` in frontmatter stores short session context ("where we left off"). Overwrites on each update (not append). Preserved on all status transitions (including done/archived - useful for summaries/reverts). Returned by `pm_context` for doing tasks.
- **AC field**: `ac` in frontmatter stores acceptance criteria. Overwrites on each update (same as brief). Preserved on all status transitions. Returned in `pm_context` and `pm_list_tasks` summaries. When executing a task, constrain work to AC - don't add unrequested features or deviate from stated criteria.
- **Spec / Log body zones**: the body splits into two zones with opposite write rules, solving append-only-rot on long-lived tasks. The **Spec** zone (delimited by `<!-- spec:start -->`/`<!-- spec:end -->` markers, written via the `spec` param) is the current-truth document - rewritten wholesale in place via `storage.ApplySpec(body, spec)` (`internal/storage/spec.go`). Everything outside the markers is the append-only **Log** (written via `body_append`). `storage.ExtractSpec(body)` returns the Spec content. The TUI detail view renders the markers as visible `## Spec (current truth)` / `## Log (history, append-only)` headers (`bodyToDisplayMarkdown` in `view_detail.go`). Markers default to the top of the body (Spec first, Log below); if absent when `spec` is first set, a block is prepended and the existing body becomes the Log. Canonical flow: rewrite Spec + append a one-line pointer to the Log.
- **Concurrency (lost-update protection)**: task writes are atomic (tmp+rename), so the ONLY hazard is two pm processes (parallel CC sessions' MCP servers, executor managers, the board) interleaving read-modify-write and dropping each other's edits. `Store.LockProject(slug)` (internal/storage/lock.go) is a cross-process flock on `<projectDir>/.pm.lock` - hold it around FindTask -> mutate -> WriteTask and read the task FRESH inside. Wired into: the mutating MCP handlers (add/update/delete), the CLI's own minting/multi-file writers `pm add` (the lock MUST cover `NextTaskID` -> `AddTask`: the ID is derived from the tasks on disk, so two unlocked adds mint the SAME id - O_EXCL only protects the file NAME, and two different titles produce two different names) and `pm reorder` (the widest read-modify-write among the CLI commands: several children, whole-struct writes, so an unlocked run reverts a concurrent `pm_update_task` brief and body included - it re-reads the children FRESH inside the lock), `applyWorkerResult` + `recordSubFeedback` (the executor's long-window writers: their task copies predate a 30+ min worker run and MUST be re-read before writing), and `Store.MoveTask` itself (self-locks + re-reads fresh + refreshes the caller's copy in place - covers all 24 move sites incl. the board's stale card copies). Deliberately NOT wired into the board's OWN writers (the `Ctrl+j/k` order swap in `actions.go`, the add prompt's `time.Now().Unix()%100000` id) - same hazard class as `pm add`/`pm reorder`, still open. RULES: never nest LockProject in one process (second flock on a fresh fd deadlocks against your own lock - release before calling a self-locking callee like MoveTask; the release closure is sync.Once-idempotent for exactly this handoff), and `pm_move_task` deliberately has NO handler-level lock. `MoveTask`'s fresh re-read is a PRECONDITION, not a best-effort refresh: if the task file is gone (a parallel `pm_delete_task`) or the dir cannot be read, it returns an error and writes NOTHING - swallowing that error resurrected deleted tasks from the board's stale card pointers. The executor's two long-window writers now enforce the SAME precondition (via `FindTaskExact`): `applyWorkerResult` returns an error (`pm work` surfaces it; the manager parks the sub) and `recordSubFeedback` returns one that `logIfErr` reports without aborting the run - a task deleted during a 30-minute worker run no longer comes back carrying a brief nobody will look for. `Store.WriteTask` stays lenient on purpose: the board's `doUndo` resurrects a snapshot deliberately. **project.yaml is covered too**: its write path `writeProject` MERGES into the existing file (to keep comments + unknown keys), so its read->write window is wider than a task write's - `Store.CreateProject` (lock taken after MkdirAll; the lock file lives in that dir), `Store.UpdateProject` and `Store.MutateProject` all self-lock, and the same no-nesting rule applies to them. `LockProject` no longer MkdirAll's the project dir - it STATS it and errors when it is missing. The lock file lives inside that dir, so creating it made every one of the 11 lock sites able to conjure a project: a write to a typo'd slug silently created one, and locking a project someone had just deleted resurrected its dir, into which `applyWorkerResult` then wrote a 30-minute-old task - invisible forever, since no `project.yaml` comes back with it. `CreateProject` is the only site that legitimately makes the dir and it MkdirAll's before it locks; every other site resolves an existing slug, and the callers that degrade to an unlocked write on a lock error keep exactly the behaviour they had. A partial-field edit must go through `Store.MutateProject(slug, fn)` (lock -> re-read FRESH -> apply fn -> write), NOT GetProject -> mutate -> UpdateProject, whose lost-update window is as wide as the caller's think time: `pm_update_project` and `pm executor init` patch single fields and would otherwise revert a parallel session's edit to an untouched field. The worktree slot lock is separate and ALSO atomic: claim = link(2) of a fully-written tmp (rival can never read a half-written winner), stale takeover = rename-aside (see AcquireWorktreeLock).
- **Identifiers are PATH COMPONENTS, validated at the store** (pm-cli-74-1): a task ID becomes the leading component of its file name (`Filename` = `<id>-<title-slug>.md`) and a project slug becomes a directory, so both are validated where they are WRITTEN, not only in the MCP handlers - `storage.ValidateTaskID` in `Store.AddTask` (covers `pm add --id`, `pm_add_task`'s `id`, the board's add prompt; runs BEFORE the O_EXCL claim so a rejected ID leaves no phantom file) and `storage.ValidateSlug` in `Store.CreateProject` (before MkdirAll, so `pm projects add ../outside` creates nothing). `ValidateTaskID` is deliberately WIDER than `ValidateSlug` - real data holds `30422` and `ACME-253`, so digits-only and uppercase stay legal - but rejects spaces/non-ASCII on purpose (IDs get quoted into shell commands, branch names and log paths). The third identifier is `project.yaml`'s **`prefix`**, the ID SOURCE for auto-minted ids (`<prefix>-<n>`): `storage.ValidateProjectPrefix` gates it in `CreateProject`, in `pm_update_project`, and in `MutateProject` **only when the value CHANGES** (a legacy project carrying a bad prefix must stay editable in its other fields, or `pm executor init` could never touch it). A prefix that slipped in by hand still fails at add time, with an error that names the prefix and the project.yaml path instead of an ID nobody typed. `pm migrate-ids` is the one renumbering path that bypasses `AddTask` (it rewrites via the lenient `WriteTask`), so it validates the prefix in its PREFLIGHT - checking per task would renumber the alphabetically earlier projects before failing.
- **`pm work`/`pm run-epic` one-arg resolution** (pm-cli-74-1): the single-argument form scans projects in `FindTask`'s OWN three tiers (exact ID -> unique ID prefix -> title substring), each tier deciding alone, and ERRORS listing the candidates when a tier matches several projects - first-hit-wins in sorted order used to spawn a 60-minute worker in the WRONG repo. The cwd project is a TIEBREAK INSIDE a tier, never a short-circuit: standing in a repo settles a tie but does not let its title mention outrank another project's exact ID. Archived projects are excluded (as in `GetAllTasks`) unless you are standing in one; the explicit two-arg form still reaches everything. A query that is ambiguous INSIDE one project contributes `<slug>/<several>` rather than dropping out of the scan (dropping out is first-wins by another route).
- **Project config**: `~/.claude/pm/<slug>/project.yaml` — name, path, repo, stack, notes, links, tags, statuses. Writes go through `writeProject` (0.29.2): the fresh marshal is MERGED into the existing YAML node tree - comments and unknown top-level keys in a hand-tuned file survive (unchanged subtrees keep their original nodes), cleared known fields drop - and the file is written atomically (tmp+rename). `pm executor init` re-running over an annotated executor block no longer destroys the annotations.
- **Statuses are per-project** — read via `Store.GetProjectStatuses(slug)`. Default: `[todo, doing, waiting, done]`. Override in `project.yaml`. "ALL" view merges all projects' statuses. **Every mutation path validates** (0.29.2): `Store.MoveTask` and MCP `pm_update_task`'s `status` param reject a status outside the project's set (plus system-level `archived`, always legal) - a typo'd `pm mv` used to write it and the task vanished from every board column. `pm run-epic` hard-gates an unlisted `done_status` at run start (failing the merged-move AFTER the merge landed would desync the re-entrant done check and re-drive the sub); the INDEPENDENT-mode landing status degrades instead of gating when it is the built-in default - see Landing statuses.
- **Archive is system-level** — `StatusArchived` is NOT a project status. Never add to `DefaultStatuses` or `project.yaml`. `filteredTasks()` excludes archived. `Ctrl+a` toggles archive view.
- **TUI has 4 views**: `viewBoard`, `viewDetail`, `viewArchive`, `viewProjectInfo`. `previousView` controls where detail/escape returns to.

## Debugging TUI layout

When fixing layout/rendering bugs, don't guess at line counts. Add temporary instrumentation and have the user screenshot:

1. **Colored section markers** - add `lipgloss.NewStyle().Background(color).Render("[TAG]")` at section boundaries to see exactly where each section starts
2. **Debug status bar** - replace the status bar with key metrics: `h` (terminal height), `curH` (computed height), `pad` (padding lines), `mch` (max card height), per-column content line counts
3. **Key formula**: `viewBoard` total visual lines = `strings.Count(output, "\n") + 1`. Must equal `m.height`. If `curH > h`, top lines get cut off by bubbletea
4. **Build with `-dbg` suffix**: use version like `0.7.1-dbg` so debug builds are clearly identified
5. **Clean up**: remove all debug code before committing. Restore `version` import if status bar uses it

Layout height budget for `viewBoard` (each item = newlines contributed):
- Title with `Padding(0,0,1,0)` + explicit `\n`: 2
- Tabs + `\n\n`: 2
- Column border/padding (`Padding(1,2)` + `RoundedBorder`): 4
- Column content (cards): `maxCardHeight` (variable)
- `\n` after columns: 1
- Confirmation line (always reserved): 1
- Status bar (no trailing `\n`): 1 visual line
- Total = `maxCardHeight + 11` (+ 1 if search/add active)

The `maxCardHeight` is computed dynamically: `m.height - overhead` where overhead accounts for all non-column lines. Column content is clamped (truncated if over, padded if under) to exactly `maxCardHeight` newlines so `JoinHorizontal` produces consistent height across projects.

## Gotchas

- **Headless executor workers cannot write anywhere under `~/.claude`** (CC sensitive-path guard; `claude -p` has no one to approve the prompt, so it is a hard refusal, unlike an interactive session which just asks). That is why the source lives in `~/repos/pm-cli` while the data dir stays in `~/.claude/pm/` - and why a worker task that needs to write into the data dir will fail.
- `storage.DefaultStatuses` is the single source of truth for defaults - don't hardcode `[todo, doing, done]` elsewhere
- `ParseStatus` returns `TaskStatus`, not `(TaskStatus, error)` - it lowercases any string
- Task files live next to `project.yaml` in the same dir (not in a subdirectory)
- Links is `map[string]string` (freeform key=url), not a typed struct
- Version is set via ldflags at build time (`internal/version/version.go`) - defaults to "dev" without ldflags
- `cardHeight()` is an estimate for reference only - not used for scroll or rendering logic. Both `fixScrollOffsets` and `viewBoard` render cards and measure actual `\n` count to handle text wrapping correctly. Column content is clamped to `maxCardHeight` as a safety net.
- **Task reorder**: `Ctrl+j/k` swaps task order within a column via `Order int` field in TaskMeta. If all tasks have `Order==0`, sequential orders are assigned first. `filteredTasks()` sorts by Order asc, then Updated desc.
- **Sessions**: `Sessions []string` in TaskMeta stores Claude session IDs (appended by TUI on launch, or via MCP `sessions` param). Used for `--resume` and `session_count` in MCP output. MCP `pm_get_task` returns full `sessions` list; `pm_update_task` and `pm_add_task` accept `sessions` param (append-only).
- **Session detection**: `pm session-id` prints current CC session UUID. Strategy: (1) walk process tree for `claude --resume <id>` arg, (2) fallback to newest .jsonl in `~/.claude/projects/<encoded-cwd>/`. Requires `CLAUDECODE=1` env var.
- **Worktree naming**: `worktreeName(t)` uses `t.Meta.Branch` if set, otherwise `Slugify(t.Meta.Title)`. Produces semantic branch names (e.g. `feat/enable-analytics` not `atlas-9`).

## MCP server (`pm mcp`)

Stdio MCP server for Claude Code. Registered as user-scope MCP: `claude mcp add --transport stdio --scope user pm -- ~/.local/share/go/bin/pm mcp`.

- **Package**: `internal/mcpserver/` — `server.go` (setup + Run), `tools.go` (10 tools)
- **Subcommand**: `internal/cmd/mcp.go` — `pm mcp` cobra command
- **SDK**: `github.com/modelcontextprotocol/go-sdk/mcp` — typed `AddTool[In, Out]` for auto schema generation
- **Tools**: `pm_context`, `pm_list_tasks`, `pm_get_task`, `pm_list_projects`, `pm_add_task`, `pm_update_task`, `pm_update_project`, `pm_create_project`, `pm_move_task`, `pm_delete_task`
- **No MCP resources** (pm-cli-72-3): the 3 resources (`pm://projects`, `pm://tasks/{project}/{status}`, `pm://project/{slug}`) were removed - `pm://tasks` bypassed every output budget `pm_list_tasks` enforces (full briefs, no 50-task cap, no archived exclusion - exactly what 0.24.0/0.28.1 fixed), `pm://projects` dropped the `archived` field, and all three duplicated a tool with a worse copy. Grepped for real consumers (repo, docs/, `~/.claude/CLAUDE.md`) before deleting - none found. Use the equivalent tool instead: `pm_list_projects`, `pm_list_tasks`, `pm_get_task`/`pm_context`.
- **CWD auto-detection**: `pm_context` with `cwd` param matches against project.yaml `path` fields
- **Output budget** (0.24.0): `pm_list_tasks` defaults to the 50 newest tasks (`limit` param overrides; `limit<=0` → default) and returns a wrapper `{tasks, total, shown, note}` - `note` states "N of M tasks shown ... narrow with project/status or raise limit" whenever the list was truncated. List summaries carry ONE-LINE briefs (`storage.BriefLine`: first non-empty line, 120-rune cap); `ac` stays full. `pm_context` caps each doing-task `body` at 2000 runes (`contextBodyLimit` in `tools.go`) with a pointer to `pm_get_task` for the rest - `brief` is never truncated there (it IS the designed cold-start vehicle). `pm_get_task` remains unbounded. **The rollup is a summary, not a reading surface** (0.28.1, pm-cli-50 - `pm_context` for orbit returned 61 757 chars over MCP and blew the tool's token limit while the same rollup from the terminal was 15 746): every brief inside `trackers` is one line - `storage.Tracker.BriefLine` (JSON `brief_line`, was the full `brief`) alongside the children's, set in `BuildTrackers` so the CLI/TUI/MCP share ONE rule - and a **finished tracker collapses its children** (`trackerFinished`: the parent's own status is terminal AND every child is `done`/`archived`/a landing status → `Children` nil + `children_omitted: true`, `Progress`/`Total` survive). That collapse is the structural half: finished epics accumulate forever and were the one part of the payload growing without bound, while a still-open child (e.g. `waiting` under a closed parent) keeps the full list. `focus_tasks` briefs and the cross-project branch's `doing_tasks` briefs compress too - they are listings. The project-scoped `doing_tasks` brief stays FULL on purpose. Measured on orbit: 62 726 → 44 350 chars MCP, 15 771 → 13 077 CLI.
- **Trackers rollup**: `pm_context` returns a `trackers` section (parent+subtask rollup) when any task has children. Children/trackers are suppressed from the flat `doing_tasks` list. `pm_add_task`/`pm_update_task` accept a `parent` param. Same rollup is available offline via the `pm context [project]` CLI command (`internal/cmd/context.go`) - useful when the running MCP holds a stale binary.
- **Executor fields over MCP** (0.26.0): `pm_get_task` returns `model` and `epic_mode`; `pm_add_task`/`pm_update_task` accept `epic_mode` (update: omit = keep, `""` = clear - the `mode`/`model` pattern). Validation is enforced at the storage layer (`storage.ValidateEpicMode` in `writeTask`, like `ValidateMode` for `mode`), with handler-level pre-checks that are LOAD-BEARING, not cosmetic (a writeTask failure after the O_EXCL claim would leave a 0-byte phantom file - see pm-cli-41). Lets `/batch-prep` set up an independent tracker entirely via MCP with a read-back confirm.
- **Invariants**: links merge (never remove), body_append appends to the Log (never replaces), spec rewrites the Spec block in place, tags replace if provided, epic_mode overwrites if provided (validated). `branch`/`parent`/`brief`/`ac` are tri-state on `pm_update_task` (pm-cli-72-3, matching `mode`/`model`/`epic_mode`): omit = keep, empty string = clear; `title` stays required-non-empty (never clearable). `pm_list_tasks`/`pm_update_task`/`pm_move_task` reject a `status` outside the project's (or, cross-project, the union of every active project's) status list - `archived` is always legal. `pm_update_project` rejects a `statuses` replacement that would orphan tasks sitting on a dropped status (handler-level only, not storage - CLI/manual project.yaml edits stay lenient); an empty `statuses: []` resets to `DefaultStatuses` and is checked against THAT effective set, not the empty literal. `pm_create_project` rejects a `slug` that isn't a safe path component (`storage.ValidateSlug`, `^[a-z0-9][a-z0-9._-]*$` - deliberately not `slug == Slugify(slug)`, since `Slugify` strips literal hyphens and would reject real slugs like `app-orbit`).

## Journals (`pm journal`) — per-project record of a flaky subsystem

Added 0.35.0 (pm-cli-83). A **journal** is a per-project append-only record of how ONE chosen, repeatedly-troublesome subsystem actually behaves - the first instance is the iOS simulator rig in app.orbit, whose incidents had accumulated as 15 separate Claude memory files plus a hand-grown section in `.simulator-verify/config.md`: none dated, none counted, none connected to a fix.

- **The distinction that stops it duplicating memory files**: a memory file or a doc holds a **RULE** (current truth, rewritten when it turns out wrong); a journal entry holds an **EVENT** (dated, append-only, never rewritten). A rule can never answer "fifth time this month"; a journal never replaces the rule. The entry's `fix` field NAMES the rule/change it produced, and **an entry with an empty `fix` is OPEN - the open set IS the backlog**, derived, never hand-maintained. This is why the sim-naming norm from the same session went into the skill (a rule) and not into a memory file AND the journal.
- **Storage** (`internal/storage/journal.go`): JSONL per subject at `<projectDir>/.journal/<name>.jsonl`, deliberately the same grain as the executor journal one directory over (`.executor/journal.jsonl`), so the code shape and the reading habit already existed. `Incident` = `{ts, symptom, false_conclusion, cause, cost_min, fix, tags, session}`. `false_conclusion` is the load-bearing field: a subsystem that fails LOUDLY is cheap, one that returns a confident wrong answer is what burns afternoons (the trigger incident was a `RIG DEAD` printed for a live rig). `AppendIncident` RETURNS its write error rather than swallowing it like `AppendJournal` - the executor journal is observability written by a machine mid-run, this is written by whoever just paid the cost, and losing it silently loses the only record.
- **Agnostic by config**: `Project.Journals` (`journals:` in project.yaml, name + one-line subject) is the whole of the mechanism's project-awareness - nothing in the code knows what a simulator is. A journal NAME is a file name, so `ValidateJournalName` gates it with the same `ValidateSlug` rule as project slugs (see "Identifiers are PATH COMPONENTS"). An **undeclared name is an error, never an implicit create**, in both the CLI and MCP: a typo would silently open a second file and split one history in half.
- **Closing an entry is a new EVENT, never an edit** (0.36.0): `Incident.Resolves []string` lists ids of EARLIER entries this one closes, and `StillOpen` = no own `fix` AND nobody has since closed it. Without it the open count could only ever grow - append-only means an entry cannot be edited to carry a fix decided weeks later - and the backlog would rot, which is the failure the journal exists to prevent. `JournalStats.ClosedLater` reports resolved-by-a-later-entry separately from `Open`, so a review's effect stays visible instead of entries silently vanishing from the count. An unknown `resolves` id is REJECTED before the write: it would fail silently otherwise (entry lands, target stays open, nobody re-derives). **The id is DERIVED, not minted** (`incidentID` = UTC day + 2-byte hash of ts+symptom): deterministic from stored fields, so `ReadIncidents` computes it for lines written before the field existed and the entire pre-existing backlog became closable without rewriting one byte of an append-only file.
- **Ordering rules, both learned from a real bug**: entries are read newest-first (the file stays append-order) and an entry whose `ts` does not parse sorts **LAST** - a raw string comparison put `"not a timestamp"` above every real date, straight to the top of the actionable list. `JournalStats.First/Last` come off the PARSED instant for the same class of reason: RFC3339 permits a numeric offset, so `...T10:00:00+02:00` compares lexicographically after a later `...T09:00:00Z`.
- **The cost average divides by `Costed`, not `Total`** - entries that recorded a cost. Dividing by the total would make a subsystem look CHEAPER the more often someone skipped the field, i.e. exactly backwards.
- **Surfaces**: `pm journal list|show|add|stats` (CLI, `--project` flag rather than a second positional) and `pm_journal_add` / `pm_journal_list` (MCP). `pm_journal_add` reports back the recurrence its own entry just produced ("2 entries now share tag X") - that sentence is what turns a log into an argument for fixing the tool, and it costs one line at the one moment someone is already paying attention. Stats travel WITH the entries in `pm_journal_list` rather than in a separate tool: the reason to read a journal is to see whether something recurs, and a caller who needs a second call for the counts will skip it.
- **`pm_context` / `pm context` get COUNTS ONLY**, never content - the same deliberate rule as the executor profile pointer (0.28.1, when `pm_context` was measured at 62k chars). A journal grows without bound and its readers are the sessions about to touch that subsystem, not every session. A project with no journals declared gains no key at all.

## Executor (`pm work` / `pm run-epic`) — autonomous task execution

Runs pm tasks/epics by spawning **isolated headless `claude -p` workers** that implement → test → review → fix → verify, so a multi-subtask epic executes without blowing one session's context. Built + validated (epic `pm-cli-18`; first real run = atlas-64-3 → PR #151, 2026-06-17).

- **`pm work [project] <task>`** (`internal/cmd/work.go`, `work_prompt.go`, `work_git.go`) — the ATOM. Spawns one fresh `claude -p` in the project dir (loads that project's skills/CLAUDE.md/MCP by cwd), runs the inner loop on one task, returns a JSON contract (`{status,summary,branch,commits,unresolved}`). Standalone → draft PR; `--epic` → commit only. `planWork` (assemble, no side effects) + `executeWork` (run + record). `--dry-run` prints the prompt+argv without spending tokens. Flags: `--model` (opus), `--max-turns` (150), `--timeout` (60m), `--yolo`, `--allow-dirty`, `--additional` (+ `--slot N`, `--base`) - see Additional worktree mode.
- **`pm run-epic [project] <tracker>`** (`internal/cmd/run_epic.go` + `run_epic_sub.go`) — the MANAGER. Split like `pm work`: side-effect-free `planEpic` (project preflight via the shared `preflightProject`, ready subs, mode, branches - what `--dry-run` prints) + `executeEpic` (the loop). One `driveSubFlow` drives a sub in both modes; the integration/independent differences (fork base, pre-branch checkout, parking, push, merge, branch cleanup) are the `subFlow` hook struct in `run_epic_sub.go`. Creates integration branch `epic/<tracker>`, drives ready subs sequentially (by `Order`), each on `feat/<slug>` branched off the integration branch; merges back `--no-ff` on verify-green → `done_status` (integration) / `done_status_independent` (batch). Blocked/failed/conflict → park on `waiting` + continue, and the sub's reason+open-questions bubble to the parent's `## Manager Notes` (via `recordSubFeedback`, deduped per-sub, refreshed/cleared on eventual merge). Re-entrant (skips merged/done). Ends with ONE draft `epic→main` PR. Never merges to main, never closes the parent.
- **`depends_on` gate** (`unmetDeps` in `run_epic.go`): a sub's `depends_on: [<sub-id>...]` frontmatter lists subs that must be `merged`/`done` first. The manager checks it BEFORE spawning a worker — an unmet dep skips the sub (no worker, no wasted tokens) and leaves it on its ready status (NOT parked on `waiting`), so a re-run auto-picks it up once the dep merges. A genuinely failed sub still goes to `waiting` (needs a fix + flip back to `todo`); a dep-skip is just "not its turn yet". Opt-in (empty = run by `Order`). Settable via `pm_add_task`/`pm_update_task` `depends_on` param; shown in `pm run-epic --dry-run`.
- **`mode: auto | manual` gate** (`classifySub` in `run_epic.go`): a sub's `mode` frontmatter marks it autonomous (`auto`/empty, default - backward compatible) or human-only (`manual`). A `manual` sub is a PERMANENT gate: the manager skips it entirely (no worker spawned, status untouched) on EVERY run, records a distinct `manual` outcome (not `skipped`), and never re-picks it - unlike the re-entrant `depends_on` skip. The human does the work by hand / with CC and moves the sub to `done_status` themselves; only then does the re-entrant done check pick it up. Use for subs needing interactive/visual work (simulator verification, design checks) that a headless `claude -p` can't do. A later auto sub with a `manual` sub in its `depends_on` stays blocked via the normal `unmetDeps` gate until the human moves the manual sub to done (no special-case logic). Only `auto`/`manual` (lowercase) are valid - `storage.ValidateMode` rejects anything else at write time. Settable via `pm_add_task`/`pm_update_task` `mode` param; shown as `[MANUAL]` in `pm run-epic --dry-run`. No CLI flag - it's a per-task frontmatter field.
- **`model` per-sub override** (0.21.1): a sub's `model:` frontmatter (claude alias or full name, e.g. `sonnet`) overrides the run-level `--model` for THAT sub in `pm run-epic` (stderr announces `model override -> ...`), and in `pm work` it wins over the flag DEFAULT but an explicitly passed `--model` wins over the frontmatter (`cmd.Flags().Changed`). Empty = inherit (backward compatible). Purpose: token economy - trivial subs (copy/color/one-prop tweaks) run on a cheaper model while investigation subs stay on opus; batch-prep/epic-prep tag subs at creation. Settable via `pm_add_task`/`pm_update_task` `model` param. Related: the generic review phase (`work_prompt.go`) now sizes reviewer count to the diff - <~50 changed lines across <=2 files -> 1 adversarial reviewer, larger -> 3 - counted on PRODUCTION files only since 0.36.2 (see below).
- **Hook bypass, lost results, and who owns "full validation"** (0.36.3, `worker_guard.go` + `work_result.go` + `work.go` + `work_prompt.go`; all three found in the FIRST real run under the 0.36.2 gate - `orbit-vps-1` on the orbit VPS runner, 2026-08-05 21:11-21:31 UTC, evidence in pm-cli-66-6): the gate change worked (see below), and the run surfaced three defects the isolated validation could not.
  - (a) **The envelope left the forbidden door as the only open one.** A worker's pre-commit hook died on `gitleaks: not found` (the binary was simply absent from that runner). It tried `PATH=... git commit`, then `export PATH=...`, then `ls` outside the repo - the allowlist denied each, because each needs a shell construct the envelope withholds - and then found the one form nothing blocked: `git -c core.hooksPath=/dev/null commit`. That commit is on origin: no secret scan, no lint-staged, and it reads as hook-checked. Two fixes, plus one environment fix (gitleaks installed on the runner). `workerDisallowedTools` grew the leading forms, and **`pm worker-guard`** (hidden command) is now attached to every worker as a PreToolUse hook via `--settings` inline JSON, blocking `--no-verify` / `-n` on commit+push / `core.hooksPath` / `HUSKY=0` / `rm`-ing hook files with an exit-2 message that names the legitimate move (`BLOCKED-ENV:` + return "blocked"). It rides along in `--yolo` too: yolo waives permission PROMPTS, not the project's right to have its commits pass its own hooks. Facts worth not re-deriving, each measured against a probe repo with a deliberately failing hook (2026-08-06): permission patterns match **whole tokens**, so `Bash(git -c core.hooksPath:*)` does NOT match `git -c core.hooksPath=/dev/null ...` (hence the blunter `Bash(git -c *)`); prefix patterns cannot see a **trailing** flag, so `git commit -m x --no-verify` ran under the full disallow list and only the guard stops it; `--settings` **merges** with the repo's own `.claude/settings.json` (a project PreToolUse hook still fired alongside the guard), and inline JSON is accepted by claude 2.1.71 (VPS) as well as 2.1.223 (mac), which materializes it into `/tmp/claude-settings-<uuid>.json` and leaves it there (one ~110-byte file per worker run - harmless, but do not go hunting for what wrote them). The guard **fails open** on an unreadable payload - a guard that failed closed would stop every worker on the machine the first time the hook schema moved.
  - (b) **A finished sub was recorded as failed because its receipt arrived one turn too early.** `orbit-vps-1-1` emitted `StructuredOutput` with `status: "verified"`, branch and commit - and 9 s later a background-task notification (it had run the gate with `run_in_background`) forced one more text turn, so the envelope's `structured_output` came back null and pm reported "worker returned no structured result". `parseWorkerOutput` now falls back to the worker's transcript (`<config>/projects/<encoded cwd>/<session>.jsonl`, both the project's config dir and the default; last StructuredOutput call wins, run stats still lifted from the envelope) and ANNOUNCES the recovery - silent recovery would hide the worker's turn-order defect behind pm papering over it. The prompt side tells the worker to emit the result as its final act with no background task still running.
  - (c) **A tuned verify gate saves nothing if the repo's own docs tell the worker to run the untuned one.** Same run, same box, seven minutes apart: the bound gate took **61.5 s** (tsc 34.3 + cached eslint **9.4** + prettier 17.2) while the worker ALSO ran `yarn validate` mid-implementation - because app.orbit's CLAUDE.md says to - for **155.4 s**. The implement-phase instruction now says the verify phase's bound command IS the project's full validation for the worker, verbatim, and must not be swapped for the equivalent named in the repo's docs. Fixing this in the project's CLAUDE.md instead was rejected: that file is the team's, and the tuned wrapper is per-runner.
- **Liveness has a second criterion: a recycled pid is not the holder** (0.37.1, `internal/storage/process.go` + `process_{darwin,linux,other}.go`; pm-cli-93, same external review): `ProcessAlive` was a bare `Signal(0)`, i.e. it answered "does a process with this number exist" when every caller meant "is the process that wrote this lock still running". Pids get RECYCLED - the journal already learned this on the other side of the same hazard (the `run_id` fix, 0.27.0) - so a `.pm-executor.lock` orphaned by a reboot or a `kill -9` read as held by whoever later inherited the number, and the worktree slot stayed busy until a human deleted the file; `pm executor stats` booked the crashed run as still running. `WorktreeLock.Started` had been written since day one and compared against nothing. Now `ProcessAliveSince(pid, ref)` / `ProcessAliveSinceStamp(pid, rfc3339)` add the process START TIME as the second criterion: a pid cannot be reused while its owner lives, so a process that started BEFORE the stamp is necessarily the one that wrote it, and one that started after it necessarily is not. Wired into all four readers - `LiveWorktreeHolder`, `AcquireWorktreeLock`'s stale check, `LiveSessionHolder`, `RunState.IsLive` - plus `aggregateJournal`, whose injected predicate grew a `time.Time` parameter fed by the start line's own `ts`. Three rules that are not incidental: (a) **EPERM counts as ALIVE** - a process owned by another user exists; the error directions are asymmetric, since reading a live holder as dead steals its lock and corrupts a running job while reading a dead one as alive costs a wait. (b) **Missing information degrades to bare liveness, never to "dead"** - a zero/unparseable stamp, or a platform that cannot report a start time, behaves exactly as pre-0.37.1. (c) **A 5-second grace** absorbs the RFC3339 second-truncation plus startup skew between a holder starting and stamping. The start time comes from the kernel, not from forking `ps`: `SysctlKinfoProc` on darwin, `/proc/<pid>/stat` field 22 + `/proc/stat` btime on linux (this is a render-path call). Fixture note: a run-state fixture claiming to have started before the test binary did now reads as recycled - use pid 1, which is alive everywhere and older than any stamp a test can write.
- **The hook directory is not writable by ANY tool** (0.37.1, `worker_guard.go`; pm-cli-92-1, from an external review of the repo, 2026-08-07): the 0.36.3 guard closed the commit-time doors and left the edit-time ones open. It registered a single `Bash` matcher and returned 0 for every other tool, while `workerAllowedTools` grants bare `Write`/`Edit` with no path restriction at all - so a worker denied `git commit --no-verify` could write `.git/hooks/pre-commit` to `exit 0` and then commit normally, with the commit reading as hook-checked. The bash side was open too: only `rm|mv|chmod` on the hook dir was watched, and `Bash(sed:*)` + `Bash(echo:*)` are BOTH on the allowlist, so `sed -i "1i exit 0" .git/hooks/pre-commit` and `echo "exit 0" > .git/hooks/pre-commit` needed nobody's permission. Now: the bash patterns cover in-place sed, `tee`, shell redirects and a wider verb list, and a SECOND PreToolUse matcher (`Write|Edit|MultiEdit|NotebookEdit`) judges `tool_input.file_path`. Three design points. (a) **The write matcher is a separate entry, never an alternation folded into the Bash one** - the `Bash` spelling is the one measured against a live claude (2026-08-06) and must not move; if a build matches tool names literally rather than as a regex, the new entry simply never fires and the bash side, where the cheap doors were, is untouched. (b) **The guard, not a path-negative allowlist entry** (the alternative the report offered): the allow/disallow lists are not passed at all under `--yolo`, so a rule living only there protects exactly the runs that need it least, while the guard rides along in both modes. (c) **The protected path is the whole of `.git`, not just `.git/hooks`** - `core.hooksPath` lives in `.git/config`, which is the same door one level up; `.gitignore` and `.github/` are not under `.git/` and stay writable, since the trailing separator is what decides. Reads are deliberately untouched (`cat .husky/pre-commit`, `Read`, `Glob`): a worker fixing what a hook complains about has to be able to see it. Fail-open on an unreadable payload or an unknown tool is unchanged.
- **Prose is not an action: the commit message is stripped before the patterns see it** (0.37.1, `worker_guard.go`; pm-cli-92-3, same review): the patterns ran against the WHOLE command string, so `git commit -m "add -n flag support to the parser"` was refused with a lecture about bypassing hooks - a deny for something the worker did not do, which is the guard's own founding failure one level up (a guard that cries wolf gets worked around, and this deny message tells the worker to report `BLOCKED-ENV:` and return "blocked", so a sentence in a commit message could cost a whole sub). `--no-verify` and `core.hooksPath` in a message did the same. `stripMessagePayload` now blanks the payload of `--message`/`-m`/`-am` (quoted or a single bare word, never crossing a `;`/`&&`/`|`) before matching. The boundary is the point and is tested directly: only the PAYLOAD goes, so `git commit -m "x" --no-verify` and `git commit -m "x" -n` - the trailing forms permission patterns cannot see, and the reason the guard exists - are still blocked. The pre-existing allowed case `git commit -m "document the no-verify ban"` had passed only because it lacked the double hyphen: the same class of bug, caught for one pattern and missed for the other.
- **A dead worker says what killed it, and an account wall stops the run** (0.37.0, `work_failure.go` + `work.go` + `run_epic.go`/`run_epic_sub.go`; pm-cli-89, from the 2026-08-07 retro): a worker that died WITHOUT producing an envelope was reported as `claude worker failed: exit status 1` and nothing else - six words naming no cause. **4 of the 22 non-green subs** in the first 19 runs died that way, all four on the same thing: the account's hard monthly spend limit, whose message (`You've hit your monthly spend limit · raise it at claude.ai/settings/usage...`) sat as the LAST assistant record in each transcript. Diagnosing it meant pulling session ids out of run-states by hand and grepping transcripts. Two separate fixes. (a) **Say what the worker said.** `workerLastWords` reads the last assistant text message out of the worker's transcript, and pm can always find it because it MINTS the session id and pins it with `claude --session-id` before the worker starts - so this works precisely when no envelope came back. Stderr is the fallback (now tee'd into a bounded `tailWriter` alongside the run log), covering deaths that happen before a transcript exists - a missing binary, a rejected flag. With neither, the message stays exactly as it was: no noise added when there is nothing to add. Worth knowing: the worker's stderr held NOTHING in all four real cases - the run log has two `launching headless worker` lines back to back - so the transcript is the primary source, not the fallback. (b) **Recognise the walls that repeat.** `accountWallReason` matches a small list of ACCOUNT-level phrases (spend limit, credit balance, usage limit, `/login`, invalid key, expired token); a hit becomes an `accountWallError`, `driveSubFlow` returns the new sub result **`aborted`**, and the manager STOPS. It used to march on: after the first wall in run `pm-cli-74` it spawned three more workers, dead 112 s, 2 s and 7 s later, each recorded as an ordinary failure. Matching on TEXT is a compromise, not a preference - the process signal carries nothing (a wall exits 1, like a crash or a bad flag) - so the failure mode is chosen deliberately: an unrecognised wall behaves exactly as before (one failed sub, run continues), never worse, while a false POSITIVE would stop a healthy run, hence phrases specific enough not to appear in a worker's prose about its own task. **The aborted sub goes BACK to its ready status, never parked on `waiting`** (the open question this ticket carried): nothing about it is wrong, and parking would make a human flip every affected sub back by hand; the subs after it are recorded `skipped` (`abortSkips`) with a note naming the abort, the same word and the same "a re-run picks it up" semantics as the `depends_on` gate. In the journal the three words stay distinct - `aborted` (worker ran, hit the wall) vs `failed` (this sub could not be done) vs `skipped` (never started) - plus a run-level `status: failed` + `error`, because a retro that reads a wall as an epic-flow failure draws the wrong conclusion. Nothing switches on the result strings (summary, run-state, `executor stats` histogram are all string-driven), so the new word needed no display changes.
- **Worker gate + review economics** (0.36.2, `work_prompt.go`; measured on the orbit VPS runner, pm-cli-66-3): a 16-line copy fix took 546 s, of which 421 s (77%) was gates, review and commit hooks - the actual code work was 57 s. Three prompt changes, each aimed at one measured line item. (a) **Review sizing counts PRODUCTION files only** - excluding lockfiles, snapshots, generated files AND `*.test.*`/`*.spec.*`/`*.perf.*`/`__tests__/**`: the worker's OWN tests (74 lines) inflated a 16-line/3-file change past the "<~50 lines across <=2 files" threshold, so by the rule a copy tweak qualified for 3 adversarial reviewers (the run actually spawned 2, in 181 s, with zero findings). The exclusion is on the COUNT only - reviewers still get the FULL diff, tests included, because a test that encodes the wrong behavior is exactly what review must catch. **The count is now correct, but do not book a wall-clock saving on it:** an A/B on a throwaway repo (one worker per arm, sonnet, same task) spawned 1 reviewer under BOTH prompts even though the diff (92 lines / 2 files) put the old rule squarely in "spawn 3" territory - so the model follows this sizing instruction loosely, and reviewers run in parallel anyway. What the fix removes is the pathological case (16 production lines + a 74-line test reading as "large"), not a measured 181 s. (b) **Scoped lint is ONE autofix pass**, never check → fix → recheck: the observed run invoked eslint three times on the same four files (14+14+12 s on 2 vCPU, nearly all of it process startup). (c) **"Commit early and often" gained a ceiling**: do not split ONE self-contained change across commits for tidiness - where pre-commit hooks run each commit pays their full cost (~12 s each in that repo), so a 3-way split of one small change triples it. The safety reason for frequent commits (a dying run loses uncommitted work) is untouched; only tidiness-splitting is out. The fourth line item - the repo-wide verify gate itself (154 s, of which 100 s is repo-wide eslint) - is deliberately NOT a pm-cli concern: it is fixed per project by pointing `executor.baseline` + `phases.verify.cmd` at a wrapper that caches the linter OUTSIDE the repo (orbit: 154 s -> 53 s warm, 91 s after a branch switch, 155 s on an empty cache = parity, so no regression in the worst case; the cache must live outside the repo because `pm work` requires a clean tree). Generating that wrapper from `detectVerifyCmd` is a candidate, not done.
- **Premise-verification rules** (0.22.1, `work_prompt.go`, lesson from atlas-63-3/ACME-1305 where a spec-baked decision on a false FE-only premise made a worker remove the 72h option): (a) review generic - a finding that contradicts the PREMISE of a spec decision/assumption is never closed with a defensive guard that hides the contradiction; verify the premise against the authoritative source first, then fix the root or escalate. (b) independent mode - a premise checkable in this repo or a READ-ONLY reference repo is NOT an assumption: the worker must grep/read it and, if evidence refutes a spec-mandated decision, record `SPEC-CONFLICT: <premise> refuted by <evidence>` in `unresolved` instead of silently implementing the disproven variant. Prep-side halves of the same lesson live in the batch-prep/epic-prep skills (no closed "przyjmij X" assumptions; decisions only when source-verified at prep) and batch-finish (spec-baked DECYZJA blocks get the same evidence bar as worker ASSUMPTIONs at odbiór). batch-finish itself is project-agnostic since 2026-07-24: its evidence categories map to concrete tools via a per-project playbook at `<repo>/.claude/evidence-playbook.md` (missing playbook -> the skill derives tools from the repo's CLAUDE.md and offers to scaffold one); first playbook = app.orbit.
- **Independent (batch) epic mode** (`driveSubIndependent` in `run_epic_sub.go`): for a batch of UNRELATED tasks that each end in their own PR, vs the default integration mode built for one coherent feature. Enabled by `epic_mode: independent` on the PARENT tracker's frontmatter (`storage.ValidateEpicMode`; board launches need no extra flag since the tracker declares it) or the `--independent` CLI override. Differences vs integration mode: NO `epic/<tracker>` branch - each sub gets its own branch (`resolveWorkBranch`: task `branch` field, else `feat/<slug>`) forked directly from the base; base precedence consults `executor.base_branch` even WITHOUT `--additional` (independent is new, no pre-worktree compat to preserve): `--base` > `executor.base_branch` > `main`. After the worker finishes, the manager pushes the branch to origin whenever it carries commits (`pushIfAhead`/`gitAheadCount` - pushes even on failed/blocked/worker-crash outcomes: partial work on origin beats work lost to the next `gitFreshBranch` wipe; a failed push is a note, never fatal). NOTHING is merged, no branches deleted, no epic PR (`--no-pr` irrelevant), and the run ends on the last sub's branch. Sub statuses: verify-green -> `done_status_independent` (default `pushed`, NOT the integration `merged` - see Landing statuses), but a non-green sub is NOT parked on `waiting` (`applyWorkerResult` suppresses the blocked->waiting move) - it stays on `doing`, because in this flow a human returns to EVERY sub anyway to finish + verify it. Workers run with the BEST-EFFORT protocol (`buildWorkerSystemPrompt` independent section): never abandon the task, record assumptions as `ASSUMPTION:` and handoff items as `TODO:` in `unresolved` (which lands in the sub's brief/log + parent Manager Notes via the normal plumbing); "verified" = zero NEW verify failures even with open handoff items (pre-existing breakage recorded as `PRE-EXISTING:` never demotes the verdict - see Verification baseline), "blocked" only on zero progress. Journal `branch` field records `independent:<base>` since no single run branch exists. Dry-run prints `mode: INDEPENDENT` + per-sub branches. `classifySub` gates (manual / depends_on / re-entrant done-skip) apply unchanged.
- **Landing statuses + honest sub vocabulary** (0.34.0, `Executor.LandingStatuses`/`IndependentDoneStatus` in `internal/storage/executor.go`, `resolveEpicDoneStatus` in `run_epic.go`, `subFlow.green` in `run_epic_sub.go`; pm-cli-82): ONE word, "merged", used to mean three different things, and in the batch flow it was simply false. Measured on orbit before the fix: 11 of the 26 tasks sitting on status `merged` were batch subs nothing had ever merged - their own journal note in the same breath read `pushed <branch>; TODO: verify on the simulator`. Three layers, now separated by WHO did what. (a) The **worker envelope** (`work.go`) reports what the WORKER did: `verified | blocked | failed`. A worker never merges anything - the manager does, and only in integration mode - so the old green word named a git operation the process it described cannot perform. `normalizeWorkerStatus` folds the legacy `merged` into `verified` at the single parse point (`parseClaudeResult`), so in-flight workers started before an upgrade and every pre-0.34 journal line keep resolving; the JSON-schema enum is the new spelling. (b) The **sub result** in the run-state + journal reports what the MANAGER did: `merged` (integration - in the epic branch) vs `pushed` (independent - on origin, nothing merged), carried by the `subFlow.green` hook so the two modes cannot re-converge on one word by accident; `greenSubResult` is the "did it land" test. `pm executor stats` prints all three green words (`verified` covers standalone `pm work`, which ends in a draft PR). (c) The **task status**: `executor.done_status_independent` (default `pushed`) is a SECOND landing status alongside `done_status` (default `merged`). Its degrade is deliberate and asymmetric: the built-in default falls back to `done_status` with a printed note when the project's `statuses` list has no `pushed` (an upgrade must not refuse a batch that ran yesterday), whereas an EXPLICIT `done_status_independent` is left to hit the existing hard gate - there an unlisted name is a typo in project.yaml and failing loudly is the point. **The prerequisite half was unhardcoding the name**: `done_status` was already configurable, but 5 display/rollup sites compared against the literal `"merged"` (`storage.terminalStatus` -> the finished-tracker collapse, the board's `trackerBadges` + `renderSubtaskTable` counters, `statusGlyph`, `pm context`'s `statusMark`), so renaming it in project.yaml silently zeroed the progress badges and killed the collapse. Now `Store.GetLandingStatuses(slug)` / `GetAllLandingStatuses()` resolve them and `BuildTrackers(tasks, extraTerminal...)` takes them (variadic - most callers and every grouping test have no project context; `StatusMerged` stays in the base terminal set as the built-in DEFAULT, not as the rule). - **Run-state heartbeat + `storage.RunWriter`** (`internal/storage/executor_run.go`): before this, `Updated` only moved on sub BOUNDARIES, so a 41-minute sub was indistinguishable from a hung run (`IsLive()` says "the process exists", not "it is making progress") - and with a 60m worker timeout an observer waited up to an hour to find out. Now `executeWork` starts a ticking goroutine right before spawning the worker and stops it the moment the worker returns (`RunWriter.Heartbeat(storage.HeartbeatInterval)`, fixed 30s - deliberately no flag and no project.yaml knob), covering `pm run-epic` (per sub, on the manager's shared epic-level run-state passed down via `workOptions.runWriter`) AND standalone `pm work` (its own). The stop func is idempotent and WAITS for the goroutine to exit, so nothing can stamp the file after the run. The heartbeat re-stamps `Updated` and touches NOTHING else (no phase guessing, no sub invention) - a dedicated field was rejected because no consumer depends on "last real state change": `execElapsed` only reads `Updated` when the run is NOT running, and `pm executor stats` classifies crash-vs-running off the JOURNAL's `ts`, never the run-state. **`RunWriter` is the serialization point**: the file write was already atomic, but the race is on the STRUCT (the main goroutine mutates CurrentSub/Phase/Subs right before writing while the ticker writes the same pointer), so every run-state access in the EXECUTOR process goes through `Update(fn)`/`Read(fn)` under one mutex - a mutex inside `WriteRunState` would not have been enough. (The board process still calls `WriteRunState` directly in `launch_executor.go`/`run_control.go`; it shares the file, not the struct, and the file write is atomic.) Cross-process, the atomicity rests on the scratch file being named per WRITER (`<path>.tmp.<pid>`, 0.27.1/pm-cli-48): a shared name let two processes interleave inside one non-atomic `os.WriteFile` and rename a torn mixture, and only the `rename` publishes. Per-pid names no longer self-overwrite, so both failure paths `os.Remove` the scratch file or every failed write leaks one. The interval reaches the call site as `cmd.workerHeartbeatInterval`, a var seeded from the const purely so tests can shrink it. A nil `*RunWriter` is a no-op on every method (a bare `pm work --epic` with no manager has no run-state). Board side: the dashboard renders `♥ <age> ago` next to the elapsed clock ONLY while a worker is actually in flight - gated on `IsLive() && CurrentSession != ""` (`execHeartbeatAge` in `executor_view.go`). `CurrentSession` is pinned right before the worker spawns and cleared in `executeWork` the moment it returns (in the same breath as the heartbeat's own stop - that pairing is load-bearing, keep them together), so the gate tracks the ticker's window on both ends. Both halves were bugs found in review: gating on `IsLive()` alone false-flagged the board's launch seed plus `executor.prepare` + baseline capture (15-min caps each) as hung, and clearing `CurrentSession` only at the sub boundary did the same for the post-worker tail (`applyWorkerResult`'s project flock, then the merge or `git push`). **What the signal does and does not prove**: the ticker lives in the MANAGER process, so a fresh stamp means "the manager is alive and inside a worker", not "the worker is making progress" - a `claude -p` wedged on a network read still looks healthy until its 60m timeout. It separates a long sub from a dead/stopped manager (and from a stale run-state whose pid got recycled, which `IsLive()` alone gets wrong); detecting a wedged WORKER would need transcript-tick stamping, which this ticket deliberately did not do.
- **Kill a live run** (`K` → confirm; `killRun` + `RunState.Kill` in `run_control.go`): group-kills the manager tree (SIGTERM to `-pgid`, escalates to SIGKILL ~2s later if still alive), stamps the run-state `failed`, and parks the in-flight sub on `waiting` so the board reflects the stop. The worker is NOT in the manager's group (it leads its own - see Subprocess process groups): it dies because the manager FORWARDS the SIGTERM to the worker's group and only then re-raises on itself, all inside the board's 2s window. That handoff is why the board must signal something catchable - a SIGKILL to the manager cannot be forwarded and would orphan the worker for the rest of its `--timeout`. The **backstop** for the cases where no forwarding can happen (the 2s escalation actually firing, an OOM kill, a crash) is `RunState.WorkerPGID`: `executeWork` publishes the worker group's pgid onto the run-state as the worker spawns and clears it the moment the worker returns - the same set/clear window as `CurrentSession`, and for the same reason, since a pgid left behind is one the next kill would signal after the kernel has recycled it. `RunState.Kill` signals that group IN ADDITION to the manager's (never instead - a live manager still forwards), and `killRun` re-reads the run-state BEFORE signalling because the board's copy is up to a tick old and the pgid changes with every sub. The board's SIGKILL escalation (`execKillCheckMsg`) kills the worker group FIRST - killing the manager first destroys the only thing that could still forward. Since 0.37.1 the escalation no longer carries the pgid in its message: it re-reads the run-state and goes through the SAME verified `RunState.Kill` (see below), so the pgid it signals is the fresh one and the identity check applies to the SIGKILL too.
- **Nothing is signalled until the pid is PROVEN to be the run's own process** (0.37.1, `RunState.Kill` + `execKillCheckMsg`; pm-cli-94, from the same external review - the reviewer's words: this is not a telemetry oversight, it is a real operational-security hole): `Kill` sent `syscall.Kill(-st.PID, sig)` off a pid read out of a FILE, with no check of any kind - and a run-state outlives its process. A `kill -9`, an OOM or a reboot leaves `status: running` behind with a pid nobody cleaned up ("A crashed executor leaves status=running with a dead PID" was already documented at `IsLive`), and after a reboot the numbers get handed out again from the bottom. Pressing `K` on such a card sent SIGTERM - and two seconds later SIGKILL - to the process GROUP of something entirely unrelated, possibly a system process. Now `Kill` verifies identity first (`ProcessAliveSinceStamp` against the run's own `Started`, the pm-cli-93 predicate) and returns a typed `StaleRunError` naming the pid instead of signalling. Three consequences worth keeping straight. (a) **The worker group rides on the MANAGER's proof**, not its own: a worker starts DURING the run, i.e. after the stamp, so the start-time test cannot apply to it - what makes `WorkerPGID` trustworthy is that a live manager clears it the moment its worker returns (plus a cheap `ProcessAlive` guard). (b) **The refusal is loud and reconciling, never silent**: `killRun` reports "Run already gone (nothing signalled), state reconciled", still stamps the run failed / parks the in-flight sub / journals the stop with that wording, and schedules NO escalation against a pid it just refused. (c) **The escalation re-reads and re-verifies** - two seconds is ample for the manager to exit and for its number to be reused, and a SIGKILL cannot be taken back, so no fresh state (or a state whose pid has moved on to another run) means no signal. Test seam: `killSignal` is `syscall.Kill` behind a var, so tests assert what WOULD be signalled without a test process ever signalling a group; board-side fixtures that need the "stopped it" path now spawn a real detached sleeper (`liveRunPID`), because a made-up pid exercises the refusal instead.
- **Subprocess process groups + bounded Wait** (0.30.1, `internal/cmd/work_proc.go`; pm-cli-57): `runWorker` and `captureBaseline` spawn through `groupCmd`/`runGroupCmd`, which set `Setpgid` (own group), a `Cancel` that SIGTERMs the GROUP and escalates to SIGKILL after `procKillGrace`, and `WaitDelay` (`procWaitDelay`, 5s). Before this, `--timeout` enforced nothing: `exec.CommandContext` signalled only the `claude` process, so descendants survived, and stdout is collected through an os.Pipe every descendant inherits - `Wait` blocked until the LAST holder of the write end closed it, i.e. past the deadline forever, while the heartbeat kept stamping `running`. Two consequences worth keeping straight: (a) `exec.ErrWaitDelay` is returned by `Wait` ONLY when the command itself exited 0 (a non-zero exit always wins as `*ExitError`), so both call sites treat it as success-with-leftovers - the worker's envelope is still honoured and a baseline captured that way is still GREEN, not "no baseline"; (b) the post-Wait SIGKILL is deliberately NOT fired on a plain non-zero exit (a red baseline is routine) - only when the deadline fired or WaitDelay unblocked us, since `Wait` has already reaped the leader and the pgid could in principle be recycled. `executor.prepare` (`runPrepare`) still uses a bare `exec.CommandContext`: it writes to `*os.File`s so it cannot hang on a pipe, but its 15-min cap still only kills the direct `sh`.
- **Executor journal** (`internal/storage/executor_journal.go`): append-only JSONL history of executor runs at `<project>/.executor/journal.jsonl` - the durable cross-run record (RunState is the LIVE state of one run, overwritten in place; the journal is never rewritten). Event model: `start` line when a run begins, `end` line with per-sub outcomes (`result`/`note`/`branch`/`duration_s`/`session`/`turns`/`cost_usd` - turns+cost lifted off the `claude -p` envelope's `num_turns`/`total_cost_usd` by `parseClaudeResult`, also stamped onto `SubRun`; `branch` = where the sub's work landed, empty for skips - the key artifact for independent batches) + run duration when it finishes, `killed` line appended by the board's `killRun` on the dead manager's behalf; a `start` with no `end`/`killed` = untracked crash. Run-level entries carry `additional`/`yolo`/`independent` flags plus `work_dir` (the claimed worktree slot on additional runs) so retros can segment integration vs batch runs and tell which slot served a run without parsing `branch`, and (0.26.0) `baseline` = the executor.baseline command WHEN it was actually captured and injected that run - empty when unconfigured OR when capture degraded (couldn't run / timeout), so retros can correlate sub outcomes with baseline presence; usage is recorded, not configuration. Written by `pm run-epic` (manager level) and standalone `pm work` (epic subs are journaled by the manager, not per-worker). Every line of ONE physical run carries the same `run_id` (0.27.0, `storage.NewRunID`, also stored on `RunState` so the board's `killRun` - a different process - stamps the manager's id on its `killed` line): `{kind,task_id,pid}` is NOT a run identity because pids get recycled, and without an id a consumer has to guess whether a second terminal line is a kill race (one run) or a distinct run whose `start` append was lost. Lines written before 0.27.0 have no `run_id` and must keep being paired the old way. All appends best-effort like `WriteRunState`. `ReadJournal` skips corrupt lines. Consumed by the `/executor-retro` skill to mine real-run history (fail rates, park reasons, durations) for epic-flow improvements.
- **Handoff contract + `pm executor show` / `pm executor doctor`** (0.28.0, `internal/storage/handoff.go`, `internal/cmd/executor_show.go`, `internal/cmd/executor_doctor.go`; pm-cli-49): the executor block supplied project knowledge for EXECUTION structurally (`context_repos`, `phases`, `baseline` -> injected into the worker prompt) but nothing for the ODBIÓR (acceptance) that happens after a run - that knowledge lived in `<repo>/.claude/evidence-playbook.md`, a path hardcoded in the global `batch-finish` skill, and `pm context`/MCP did not expose the executor block at all. pm cannot inject an odbiór prompt (it never spawns the odbiór - a human or a CC session does), so the fix is to make the convention a RESOLVABLE contract instead. **`executor.handoff`** is deliberately two fields, `playbook` (path, relative resolves against the repo) + `runtime_skill` (bare name of the project-local skill that drives the simulator/device/browser): config states WHAT exists and WHERE, the playbook states what each tool is FOR and WHEN - and anything pm can DERIVE (the runtime skill's `scripts/` inventory) is derived, never configured, since duplicated knowledge drifting is the problem being solved. Rejected for that reason: `read_full_skill`/`escalation` (process rules, identical in every project -> global skill) and `required_sections` (a second copy of what pm reads off the skill). `Executor.ResolveHandoff(projPath)` returns paths + existence + derived scripts, best-effort (a missing file is reported, never an error). **`pm executor show [project]`** prints the profile as RESOLVED, not as written: phase bindings, run config, **worktree slots with their merged env** (the authoritative simulator ids / dev-server ports), context repos, and the handoff block with the derived scripts. That slot section is the point - the orbit playbook had hand-copied both UDIDs and both Metro ports, correct only until a slot changes. `pm context` / `pm_context` get ONE POINTER LINE (`## Executor: pm executor show <slug>` / `executor_profile` key), never the profile: pm_context runs at every session start (~15k chars measured), so the profile is charged only to the session that opens it. **`pm executor doctor [project]`** validates COMPLETENESS, not syntax, and the level split is the design: **ERROR = a binary filesystem fact** (declared playbook absent, dead `context_repos` path, slot path that exists but is not a git worktree - i.e. one `EnsureWorktree` would refuse) -> exit 1; **WARN = a heuristic over prose** (playbook never names a script the runtime skill ships; playbook hardcodes a slot env VALUE verbatim) -> exit 0, because one false alarm is how a validator gets switched off for good. `--strict` promotes warnings to exit 1 once the heuristics have earned trust. Drift matching is on the verbatim value with a `len >= 4` floor (so "1"/"on" match nothing) and reports file:line + the offending line so a human can judge it. An uncreated slot is OK (first `--additional` run creates it). Landed with the skill-side half in the same pass: `batch-finish`/`batch-finish-auto` now call `pm executor show` instead of the hardcoded path and are told to read the runtime SKILL.md in full, and orbit's playbook gained a "what each tool is FOR" section (plus escalation: one round of looking that does not settle a claim becomes instrumentation) and lost its copied UDIDs/ports -> doctor clean, including `--strict`.
- **Readiness contract: doctor sees the two omissions that kill a first run, and `--dry-run` stops lying** (0.37.0, `executor_doctor.go` + `run_epic.go`; pm-cli-90, from the 2026-08-07 executor retro): the fields and the gates all existed, but every tool that says "ready" looked past what actually stops a run, so a project could pass the whole chain and die on the real one. Measured end to end in an isolated `PM_DATA_DIR`: `pm projects add demo` -> `DefaultStatuses` with no `merged`/`pushed` -> `pm executor doctor demo` says **0 errors** -> `pm run-epic demo t1 --dry-run` prints a confident plan including `done status: merged` and **exits 0** -> the real run dies immediately on `done status "merged" is not in project demo statuses`. Three holes, one thesis. (a) **`checkBaseline`** WARNs when `executor.baseline` is unset. That omission is the most expensive single failure cluster the journal records - 8 subs / $44.24 across `orbit-62` + `-63`, every worker rediagnosing the same pre-existing breakage and then booking it against its own diff - and it sat invisible for SEVEN runs on a project doctor called healthy (the local `orbit` block predated the field; the VPS copy had it since 2026-08-03, which is drift nothing was watching). WARN not ERROR, per this file's split: a run without a baseline works exactly as every run did before 0.25.0. The hint is evidence-driven - when `phases.verify.cmd` is bound it names that command (the two are normally the same and `init` writes both, so one being set alone IS the signal), otherwise it points at `pm executor init`. (b) **the no-executor-block branch no longer returns early** - it runs `checkLandingStatuses` against `GetExecutor()`'s built-in defaults first. A project with no block IS the fresh project, i.e. precisely the one whose statuses list has no landing status, and stopping at "run `pm executor init`" reported it as healthy. (c) **the `done_status` gate moved into `planEpic`** as `epicPlan.doneStatusGate` (via the extracted `epicDoneStatusGate`), so `--dry-run` reaches the same verdict the real run does: it prints the WHOLE plan first (that is what a dry-run is for) and then returns the blocker, exiting non-zero. `executeEpic` still enforces it before touching a branch or a status - the gate did not move, its RESOLUTION did. A dry-run that reports readiness it never checked is worse than no dry-run, because it is the check people run instead of the real thing.
- **`pm executor stats [project]`** (0.25.3, `internal/cmd/executor_stats.go`): read-only rollup of that journal, so a retro no longer starts by hand-parsing JSONL. Prints runs per kind (`work`/`run-epic`) with their terminal status, the six-outcome sub histogram, and duration/turns/cost totals + averages. Project resolution matches the other commands (arg, else `detectProjectFromCwd`); an empty, missing or corrupt-only journal prints a note and exits 0, never an error. Aggregation is a pure `aggregateJournal` (start lines paired FIFO with their terminal line by `runKey`) + `renderJournalStats`, so it is table-driven testable. `runKey` is `{id,kind,task_id,pid}`: since 0.27.0 (pm-cli-47) `id` is the journal's `run_id` and pairs lines EXACTLY - two terminal lines sharing an id are always one run (so a double kill counts once), two runs with different ids never merge (so a reused pid whose `start` was lost is no longer swallowed as its predecessor's kill-race twin - measured pre-fix: that run's subs/turns/cost vanished, and a double kill doubled them). `kind`/`task_id`/`pid` stay in the key because the leftover-start pass needs a holder pid, and because pre-0.27.0 lines have no id and fall back to the old ambiguous pairing plus its end-vs-killed heuristic. Three reads of the output need care: (1) a leftover `start` is a **crash** only when its pid is dead or its stamp is older than `liveWindow` (24h) - a live, recent pid reads as `running` instead, because stats is routinely run mid-epic, and the window is what stops a recycled pid on an ancient entry from masquerading as a live run forever; (2) `status` says how the MANAGER exited, not whether the work landed (`run_epic.go` hardcodes `done` on its end line whatever the subs did), so the real verdict is the sub histogram; (3) `pm run-epic` is re-entrant and re-records already-done/not-ready/dep-blocked subs as `skipped` on EVERY run, so the raw sub count inflates across re-runs - the output splits `N (X worker-backed, Y gate decision(s))` and tags `skipped`/`manual` rows `(gate)`, and turns/cost averages exclude them (they spawn no worker and report zeros). No `--json`/`--since` flags (not needed yet).
