# pm-cli

Local task tracker. Data: `~/.claude/pm/<project-slug>/`, binary: `pm`.

## Build

```
make install              # build + install (uses VERSION from Makefile)
make check                # go vet + staticcheck + go test
make install VERSION=X.Y.Z  # override version
```

Git hooks live in `githooks/` (versioned; `git config core.hooksPath githooks` - already set locally). `pre-commit` runs gofmt-check + vet + staticcheck + tests and unsets the `GIT_*` env git exports into hooks (test-spawned git repos would inherit the hook's index and explode). Both the hook and `make check` resolve the `staticcheck` binary via PATH → `go env GOBIN` → `GOPATH/bin` and fail with an install hint when missing (`go install honnef.co/go/tools/cmd/staticcheck@latest`). Fix failures - never bypass with `-n`.

IMPORTANT: Always use `make install` (not raw `go install`). Version is set via ldflags in Makefile. Bump `VERSION` in Makefile on each release. Current: **0.30.0**. Binary goes to `~/.local/share/go/bin/pm` (GOBIN).

## Tests

```
go test ./internal/... -v          # all tests
go test ./internal/storage/ -v     # single package
go test ./internal/storage/ -run TestSlugify -v  # single test
```

Always add tests when implementing new features or fixing bugs. Conventions:
- Go stdlib `testing`, table-driven tests, `t.Run("case", ...)` subtests
- `t.TempDir()` for I/O tests (auto-cleanup)
- Same package tests (access to unexported functions)
- `setupTestStore(t)` helper in `store_test.go` for tests needing a Store with project + tasks
- Invariant tests (links merge, Log append, Spec rewrite, brief lifecycle) live in `tools_test.go`; the `ApplySpec`/`ExtractSpec` unit tests live in `internal/storage/spec_test.go`
- **Executor paths**: test through a FAKE `claude` binary (`fakeClaude` in `internal/cmd/work_exec_test.go` - a PATH-prepended script emitting a canned result envelope), never by spending tokens; covers merged/blocked/crash/garbage paths of `executeWork`
- **MCP handlers**: test END-TO-END via the SDK in-memory transport (`startMCP` in `internal/mcpserver/e2e_test.go`) so the real registered closures run - do NOT re-simulate handler logic in the test body (the pre-0.23 tests did, which is why coverage sat at 12%)
- **Concurrency**: lock/race invariants live in `internal/storage/lock_test.go` + the `TestAcquireWorktreeLockAtomicRace` two-acquirer hammer in `worktree_test.go`; run suspects under `-race`

## Verification

- After code changes: `make check` (runs vet + test)
- After TUI changes: `make install` + run `pm board` and test interactively
- After MCP changes: `make install` + test with `pm_context` / `pm_list_tasks` in Claude Code

## Key patterns

- **Frontmatter tasks**: `.md` file with YAML frontmatter (id, title, status, created, updated, links, branch, parent, tags, brief, ac, order, sessions, depends_on, mode, model, epic_mode) + markdown body
- **Parent/subtask rollup**: `parent` in frontmatter holds a parent task ID (e.g. `atlas-39`), making the task a child of a tracker. Link is one-way (child→parent); a task is a "tracker" iff some other task names it as parent (derived, never stored on the parent). `storage.BuildTrackers(tasks)` (in `internal/storage/tracker.go`) groups tasks by parent and returns `[]Tracker` (parent + progress map + child rollup with `brief_line`) plus a `suppressed` set (children + trackers, excluded from flat doing lists). Used by `pm_context` (MCP, `trackers` section) and `pm context` (CLI). The generated rollup replaces hand-maintained board tables in the parent body. Subtask lifecycle: `todo → doing → merged → done` (add `merged` to the project's `statuses`). Children (and the `TrackerChild.order` field) sort by `storage.LessByOrder` (Order asc, then numeric ID, then most-recently-updated) - the SAME comparator the board columns (`filteredTasks`) and the TUI tracker list (`taskChildren`) use, so all three never disagree. Set `order` via the `order` param of `pm_add_task`/`pm_update_task` (`pm_update_task` accepts a 0 to clear it), the `--order` flag of `pm add`, or `pm reorder <parent> <child-id>...` (renumbers the listed children to 10, 20, 30... in the given sequence; resolves the project by the parent's full ID, validates every ID is a real child before writing).
- **Brief field**: `brief` in frontmatter stores short session context ("where we left off"). Overwrites on each update (not append). Preserved on all status transitions (including done/archived - useful for summaries/reverts). Returned by `pm_context` for doing tasks.
- **AC field**: `ac` in frontmatter stores acceptance criteria. Overwrites on each update (same as brief). Preserved on all status transitions. Returned in `pm_context` and `pm_list_tasks` summaries. When executing a task, constrain work to AC - don't add unrequested features or deviate from stated criteria.
- **Spec / Log body zones**: the body splits into two zones with opposite write rules, solving append-only-rot on long-lived tasks. The **Spec** zone (delimited by `<!-- spec:start -->`/`<!-- spec:end -->` markers, written via the `spec` param) is the current-truth document - rewritten wholesale in place via `storage.ApplySpec(body, spec)` (`internal/storage/spec.go`). Everything outside the markers is the append-only **Log** (written via `body_append`). `storage.ExtractSpec(body)` returns the Spec content. The TUI detail view renders the markers as visible `## Spec (current truth)` / `## Log (history, append-only)` headers (`bodyToDisplayMarkdown` in `view_detail.go`). Markers default to the top of the body (Spec first, Log below); if absent when `spec` is first set, a block is prepended and the existing body becomes the Log. Canonical flow: rewrite Spec + append a one-line pointer to the Log.
- **Concurrency (lost-update protection)**: task writes are atomic (tmp+rename), so the ONLY hazard is two pm processes (parallel CC sessions' MCP servers, executor managers, the board) interleaving read-modify-write and dropping each other's edits. `Store.LockProject(slug)` (internal/storage/lock.go) is a cross-process flock on `<projectDir>/.pm.lock` - hold it around FindTask -> mutate -> WriteTask and read the task FRESH inside. Wired into: the mutating MCP handlers (add/update/delete), `applyWorkerResult` + `recordSubFeedback` (the executor's long-window writers: their task copies predate a 30+ min worker run and MUST be re-read before writing), and `Store.MoveTask` itself (self-locks + re-reads fresh + refreshes the caller's copy in place - covers all 24 move sites incl. the board's stale card copies). RULES: never nest LockProject in one process (second flock on a fresh fd deadlocks against your own lock - release before calling a self-locking callee like MoveTask; the release closure is sync.Once-idempotent for exactly this handoff), and `pm_move_task` deliberately has NO handler-level lock. The worktree slot lock is separate and ALSO atomic: claim = link(2) of a fully-written tmp (rival can never read a half-written winner), stale takeover = rename-aside (see AcquireWorktreeLock).
- **Project config**: `~/.claude/pm/<slug>/project.yaml` — name, path, repo, stack, notes, links, tags, statuses. Writes go through `writeProject` (0.29.2): the fresh marshal is MERGED into the existing YAML node tree - comments and unknown top-level keys in a hand-tuned file survive (unchanged subtrees keep their original nodes), cleared known fields drop - and the file is written atomically (tmp+rename). `pm executor init` re-running over an annotated executor block no longer destroys the annotations.
- **Statuses are per-project** — read via `Store.GetProjectStatuses(slug)`. Default: `[todo, doing, waiting, done]`. Override in `project.yaml`. "ALL" view merges all projects' statuses. **Every mutation path validates** (0.29.2): `Store.MoveTask` and MCP `pm_update_task`'s `status` param reject a status outside the project's set (plus system-level `archived`, always legal) - a typo'd `pm mv` used to write it and the task vanished from every board column. `pm run-epic` hard-gates an unlisted `done_status` at run start (failing the merged-move AFTER the merge landed would desync the re-entrant done check and re-drive the sub).
- **Archive is system-level** — `StatusArchived` is NOT a project status. Never add to `DefaultStatuses` or `project.yaml`. `filteredTasks()` excludes archived. `Ctrl+a` toggles archive view.
- **TUI has 4 views**: `viewBoard`, `viewDetail`, `viewArchive`, `viewProjectInfo`. `previousView` controls where detail/escape returns to.

## Debugging TUI layout

When fixing layout/rendering bugs, don't guess at line counts. Add temporary instrumentation and have the user screenshot:

1. **Colored section markers** - add `lipgloss.NewStyle().Background(color).Render("[TAG]")` at section boundaries to see exactly where each section starts
2. **Debug status bar** - replace the status bar with key metrics: `h` (terminal height), `curH` (computed height), `pad` (padding lines), `mch` (max card height), per-column content line counts
3. **Key formula**: `viewBoard` total visual lines = `strings.Count(output, "\n") + 1`. Must equal `m.height`. If `curH > h`, top lines get cut off by bubbletea
4. **Build with `-dbg` suffix**: use version like `0.7.1-dbg` so debug builds are clearly identified
5. **Clean up**: remove all debug code before committing. Restore `version` import if status bar uses it

Layout height budget for `viewBoard` (each item = newlines contributed):
- Title with `Padding(0,0,1,0)` + explicit `\n`: 2
- Tabs + `\n\n`: 2
- Column border/padding (`Padding(1,2)` + `RoundedBorder`): 4
- Column content (cards): `maxCardHeight` (variable)
- `\n` after columns: 1
- Confirmation line (always reserved): 1
- Status bar (no trailing `\n`): 1 visual line
- Total = `maxCardHeight + 11` (+ 1 if search/add active)

The `maxCardHeight` is computed dynamically: `m.height - overhead` where overhead accounts for all non-column lines. Column content is clamped (truncated if over, padded if under) to exactly `maxCardHeight` newlines so `JoinHorizontal` produces consistent height across projects.

## Gotchas

- **Headless executor workers cannot write anywhere under `~/.claude`** (CC sensitive-path guard; `claude -p` has no one to approve the prompt, so it is a hard refusal, unlike an interactive session which just asks). That is why the source lives in `~/repos/pm-cli` while the data dir stays in `~/.claude/pm/` - and why a worker task that needs to write into the data dir will fail.
- `storage.DefaultStatuses` is the single source of truth for defaults - don't hardcode `[todo, doing, done]` elsewhere
- `ParseStatus` returns `TaskStatus`, not `(TaskStatus, error)` - it lowercases any string
- Task files live next to `project.yaml` in the same dir (not in a subdirectory)
- Links is `map[string]string` (freeform key=url), not a typed struct
- Version is set via ldflags at build time (`internal/version/version.go`) - defaults to "dev" without ldflags
- `cardHeight()` is an estimate for reference only - not used for scroll or rendering logic. Both `fixScrollOffsets` and `viewBoard` render cards and measure actual `\n` count to handle text wrapping correctly. Column content is clamped to `maxCardHeight` as a safety net.
- **Task reorder**: `Ctrl+j/k` swaps task order within a column via `Order int` field in TaskMeta. If all tasks have `Order==0`, sequential orders are assigned first. `filteredTasks()` sorts by Order asc, then Updated desc.
- **Sessions**: `Sessions []string` in TaskMeta stores Claude session IDs (appended by TUI on launch, or via MCP `sessions` param). Used for `--resume` and `session_count` in MCP output. MCP `pm_get_task` returns full `sessions` list; `pm_update_task` and `pm_add_task` accept `sessions` param (append-only).
- **Session detection**: `pm session-id` prints current CC session UUID. Strategy: (1) walk process tree for `claude --resume <id>` arg, (2) fallback to newest .jsonl in `~/.claude/projects/<encoded-cwd>/`. Requires `CLAUDECODE=1` env var.
- **Worktree naming**: `worktreeName(t)` uses `t.Meta.Branch` if set, otherwise `Slugify(t.Meta.Title)`. Produces semantic branch names (e.g. `feat/enable-analytics` not `atlas-9`).

## MCP server (`pm mcp`)

Stdio MCP server for Claude Code. Registered as user-scope MCP: `claude mcp add --transport stdio --scope user pm -- ~/.local/share/go/bin/pm mcp`.

- **Package**: `internal/mcpserver/` — `server.go` (setup + Run), `tools.go` (10 tools), `resources.go` (3 resources)
- **Subcommand**: `internal/cmd/mcp.go` — `pm mcp` cobra command
- **SDK**: `github.com/modelcontextprotocol/go-sdk/mcp` — typed `AddTool[In, Out]` for auto schema generation
- **Tools**: `pm_context`, `pm_list_tasks`, `pm_get_task`, `pm_list_projects`, `pm_add_task`, `pm_update_task`, `pm_update_project`, `pm_create_project`, `pm_move_task`, `pm_delete_task`
- **Resources**: `pm://projects`, `pm://tasks/{project}/{status}`, `pm://project/{slug}`
- **CWD auto-detection**: `pm_context` with `cwd` param matches against project.yaml `path` fields
- **Output budget** (0.24.0): `pm_list_tasks` defaults to the 50 newest tasks (`limit` param overrides; `limit<=0` → default) and returns a wrapper `{tasks, total, shown, note}` - `note` states "N of M tasks shown ... narrow with project/status or raise limit" whenever the list was truncated. List summaries carry ONE-LINE briefs (`storage.BriefLine`: first non-empty line, 120-rune cap); `ac` stays full. `pm_context` caps each doing-task `body` at 2000 runes (`contextBodyLimit` in `tools.go`) with a pointer to `pm_get_task` for the rest - `brief` is never truncated there (it IS the designed cold-start vehicle). `pm_get_task` remains unbounded. **The rollup is a summary, not a reading surface** (0.28.1, pm-cli-50 - `pm_context` for orbit returned 61 757 chars over MCP and blew the tool's token limit while the same rollup from the terminal was 15 746): every brief inside `trackers` is one line - `storage.Tracker.BriefLine` (JSON `brief_line`, was the full `brief`) alongside the children's, set in `BuildTrackers` so the CLI/TUI/MCP share ONE rule - and a **finished tracker collapses its children** (`trackerFinished`: the parent's own status is terminal AND every child is `done`/`merged`/`archived` → `Children` nil + `children_omitted: true`, `Progress`/`Total` survive). That collapse is the structural half: finished epics accumulate forever and were the one part of the payload growing without bound, while a still-open child (e.g. `waiting` under a closed parent) keeps the full list. `focus_tasks` briefs and the cross-project branch's `doing_tasks` briefs compress too - they are listings. The project-scoped `doing_tasks` brief stays FULL on purpose. Measured on orbit: 62 726 → 44 350 chars MCP, 15 771 → 13 077 CLI.
- **Trackers rollup**: `pm_context` returns a `trackers` section (parent+subtask rollup) when any task has children. Children/trackers are suppressed from the flat `doing_tasks` list. `pm_add_task`/`pm_update_task` accept a `parent` param. Same rollup is available offline via the `pm context [project]` CLI command (`internal/cmd/context.go`) - useful when the running MCP holds a stale binary.
- **Executor fields over MCP** (0.26.0): `pm_get_task` returns `model` and `epic_mode`; `pm_add_task`/`pm_update_task` accept `epic_mode` (update: omit = keep, `""` = clear - the `mode`/`model` pattern). Validation is enforced at the storage layer (`storage.ValidateEpicMode` in `writeTask`, like `ValidateMode` for `mode`), with handler-level pre-checks that are LOAD-BEARING, not cosmetic (a writeTask failure after the O_EXCL claim would leave a 0-byte phantom file - see pm-cli-41). Lets `/batch-prep` set up an independent tracker entirely via MCP with a read-back confirm.\n- **Invariants**: links merge (never remove), body_append appends to the Log (never replaces), spec rewrites the Spec block in place, brief overwrites, ac overwrites, tags replace if provided, parent overwrites if provided, epic_mode overwrites if provided (validated)

## Executor (`pm work` / `pm run-epic`) — autonomous task execution

Runs pm tasks/epics by spawning **isolated headless `claude -p` workers** that implement → test → review → fix → verify, so a multi-subtask epic executes without blowing one session's context. Built + validated (epic `pm-cli-18`; first real run = atlas-64-3 → PR #151, 2026-06-17).

- **`pm work [project] <task>`** (`internal/cmd/work.go`, `work_prompt.go`, `work_git.go`) — the ATOM. Spawns one fresh `claude -p` in the project dir (loads that project's skills/CLAUDE.md/MCP by cwd), runs the inner loop on one task, returns a JSON contract (`{status,summary,branch,commits,unresolved}`). Standalone → draft PR; `--epic` → commit only. `planWork` (assemble, no side effects) + `executeWork` (run + record). `--dry-run` prints the prompt+argv without spending tokens. Flags: `--model` (opus), `--max-turns` (150), `--timeout` (60m), `--yolo`, `--allow-dirty`, `--additional` (+ `--slot N`, `--base`) - see Additional worktree mode.
- **`pm run-epic [project] <tracker>`** (`internal/cmd/run_epic.go`) — the MANAGER. Creates integration branch `epic/<tracker>`, drives ready subs sequentially (by `Order`), each on `feat/<slug>` branched off the integration branch; merges back `--no-ff` on verify-green → `done_status`. Blocked/failed/conflict → park on `waiting` + continue, and the sub's reason+open-questions bubble to the parent's `## Manager Notes` (via `recordSubFeedback`, deduped per-sub, refreshed/cleared on eventual merge). Re-entrant (skips merged/done). Ends with ONE draft `epic→main` PR. Never merges to main, never closes the parent.
- **`depends_on` gate** (`unmetDeps` in `run_epic.go`): a sub's `depends_on: [<sub-id>...]` frontmatter lists subs that must be `merged`/`done` first. The manager checks it BEFORE spawning a worker — an unmet dep skips the sub (no worker, no wasted tokens) and leaves it on its ready status (NOT parked on `waiting`), so a re-run auto-picks it up once the dep merges. A genuinely failed sub still goes to `waiting` (needs a fix + flip back to `todo`); a dep-skip is just "not its turn yet". Opt-in (empty = run by `Order`). Settable via `pm_add_task`/`pm_update_task` `depends_on` param; shown in `pm run-epic --dry-run`.
- **`mode: auto | manual` gate** (`classifySub` in `run_epic.go`): a sub's `mode` frontmatter marks it autonomous (`auto`/empty, default - backward compatible) or human-only (`manual`). A `manual` sub is a PERMANENT gate: the manager skips it entirely (no worker spawned, status untouched) on EVERY run, records a distinct `manual` outcome (not `skipped`), and never re-picks it - unlike the re-entrant `depends_on` skip. The human does the work by hand / with CC and moves the sub to `done_status` themselves; only then does the re-entrant done check pick it up. Use for subs needing interactive/visual work (simulator verification, design checks) that a headless `claude -p` can't do. A later auto sub with a `manual` sub in its `depends_on` stays blocked via the normal `unmetDeps` gate until the human moves the manual sub to done (no special-case logic). Only `auto`/`manual` (lowercase) are valid - `storage.ValidateMode` rejects anything else at write time. Settable via `pm_add_task`/`pm_update_task` `mode` param; shown as `[MANUAL]` in `pm run-epic --dry-run`. No CLI flag - it's a per-task frontmatter field.
- **`model` per-sub override** (0.21.1): a sub's `model:` frontmatter (claude alias or full name, e.g. `sonnet`) overrides the run-level `--model` for THAT sub in `pm run-epic` (stderr announces `model override -> ...`), and in `pm work` it wins over the flag DEFAULT but an explicitly passed `--model` wins over the frontmatter (`cmd.Flags().Changed`). Empty = inherit (backward compatible). Purpose: token economy - trivial subs (copy/color/one-prop tweaks) run on a cheaper model while investigation subs stay on opus; batch-prep/epic-prep tag subs at creation. Settable via `pm_add_task`/`pm_update_task` `model` param. Related: the generic review phase (`work_prompt.go`) now sizes reviewer count to the diff - <~50 changed lines across <=2 files -> 1 adversarial reviewer, larger -> 3.
- **Premise-verification rules** (0.22.1, `work_prompt.go`, lesson from atlas-63-3/ACME-1305 where a spec-baked decision on a false FE-only premise made a worker remove the 72h option): (a) review generic - a finding that contradicts the PREMISE of a spec decision/assumption is never closed with a defensive guard that hides the contradiction; verify the premise against the authoritative source first, then fix the root or escalate. (b) independent mode - a premise checkable in this repo or a READ-ONLY reference repo is NOT an assumption: the worker must grep/read it and, if evidence refutes a spec-mandated decision, record `SPEC-CONFLICT: <premise> refuted by <evidence>` in `unresolved` instead of silently implementing the disproven variant. Prep-side halves of the same lesson live in the batch-prep/epic-prep skills (no closed "przyjmij X" assumptions; decisions only when source-verified at prep) and batch-finish (spec-baked DECYZJA blocks get the same evidence bar as worker ASSUMPTIONs at odbiór). batch-finish itself is project-agnostic since 2026-07-24: its evidence categories map to concrete tools via a per-project playbook at `<repo>/.claude/evidence-playbook.md` (missing playbook -> the skill derives tools from the repo's CLAUDE.md and offers to scaffold one); first playbook = app.orbit.
- **Independent (batch) epic mode** (`driveSubIndependent` in `run_epic.go`): for a batch of UNRELATED tasks that each end in their own PR, vs the default integration mode built for one coherent feature. Enabled by `epic_mode: independent` on the PARENT tracker's frontmatter (`storage.ValidateEpicMode`; board launches need no extra flag since the tracker declares it) or the `--independent` CLI override. Differences vs integration mode: NO `epic/<tracker>` branch - each sub gets its own branch (`resolveWorkBranch`: task `branch` field, else `feat/<slug>`) forked directly from the base; base precedence consults `executor.base_branch` even WITHOUT `--additional` (independent is new, no pre-worktree compat to preserve): `--base` > `executor.base_branch` > `main`. After the worker finishes, the manager pushes the branch to origin whenever it carries commits (`pushIfAhead`/`gitAheadCount` - pushes even on failed/blocked/worker-crash outcomes: partial work on origin beats work lost to the next `gitFreshBranch` wipe; a failed push is a note, never fatal). NOTHING is merged, no branches deleted, no epic PR (`--no-pr` irrelevant), and the run ends on the last sub's branch. Sub statuses: verify-green -> `done_status` as usual, but a non-green sub is NOT parked on `waiting` (`applyWorkerResult` suppresses the blocked->waiting move) - it stays on `doing`, because in this flow a human returns to EVERY sub anyway to finish + verify it. Workers run with the BEST-EFFORT protocol (`buildWorkerSystemPrompt` independent section): never abandon the task, record assumptions as `ASSUMPTION:` and handoff items as `TODO:` in `unresolved` (which lands in the sub's brief/log + parent Manager Notes via the normal plumbing); "merged" = zero NEW verify failures even with open handoff items (pre-existing breakage recorded as `PRE-EXISTING:` never demotes the verdict - see Verification baseline), "blocked" only on zero progress. Journal `branch` field records `independent:<base>` since no single run branch exists. Dry-run prints `mode: INDEPENDENT` + per-sub branches. `classifySub` gates (manual / depends_on / re-entrant done-skip) apply unchanged.
- **Verification baseline + new-failures-only verdict** (0.25.0, `executor.baseline` in project.yaml; `captureBaseline` in `work.go`, `baselineSection` in `work_prompt.go`; lesson from orbit-62/63 where 8/8 batch subs did the work, pushed, and still reported blocked/failed because `yarn validate` was red on PRE-EXISTING lint errors in files outside their diffs - and each worker burned turns re-diagnosing the same old breakage): `baseline` is an optional shell command (typically the project's full verification) captured ONCE per run on the branch the work forks from and injected into every worker prompt as `## Verification baseline` - green (exit 0) means "any failure you see is NEW"; red carries the tail-truncated output (8k cap) as the set of pre-existing failures. `pm run-epic` captures after prepare on the fork ref (base branch in independent mode, integration branch otherwise) and shares it across all subs via `workOptions.baseline`; standalone `pm work` captures in `executeWork` after branch setup + prepare (`workPlan.baselineCmd`) and rebuilds the argv. Best-effort: a baseline that cannot run (or times out, 15-min cap) degrades to no-baseline with a stderr warning, never aborts; a non-zero exit is data, not an error. VERDICT rules (all modes, `buildWorkerSystemPrompt`): verify-green = zero NEW failures - pre-existing breakage (listed in the baseline, or without one demonstrably confined to files outside the diff) never demotes the verdict and is recorded once as `PRE-EXISTING:` in `unresolved`; "failed" = failures the worker's changes introduced. Dry-run (both commands) prints the baseline cmd. Not set = exact pre-0.25 behaviour.
- **Context repos** (`executor.context_repos` in project.yaml, `map[string]string` name->path): read-only reference repos listed in the worker prompt (`## Reference repos (READ-ONLY)`, sorted by name) so a worker can check cross-repo facts (e.g. `backend: ../platform.orbit` for endpoint shapes) instead of guessing. Prompt-level contract only - pm never touches the paths, and the worker is told to never modify them. Independent of epic mode (renders for every worker when configured).

- **Run-state heartbeat + `storage.RunWriter`** (`internal/storage/executor_run.go`): before this, `Updated` only moved on sub BOUNDARIES, so a 41-minute sub was indistinguishable from a hung run (`IsLive()` says "the process exists", not "it is making progress") - and with a 60m worker timeout an observer waited up to an hour to find out. Now `executeWork` starts a ticking goroutine right before spawning the worker and stops it the moment the worker returns (`RunWriter.Heartbeat(storage.HeartbeatInterval)`, fixed 30s - deliberately no flag and no project.yaml knob), covering `pm run-epic` (per sub, on the manager's shared epic-level run-state passed down via `workOptions.runWriter`) AND standalone `pm work` (its own). The stop func is idempotent and WAITS for the goroutine to exit, so nothing can stamp the file after the run. The heartbeat re-stamps `Updated` and touches NOTHING else (no phase guessing, no sub invention) - a dedicated field was rejected because no consumer depends on "last real state change": `execElapsed` only reads `Updated` when the run is NOT running, and `pm executor stats` classifies crash-vs-running off the JOURNAL's `ts`, never the run-state. **`RunWriter` is the serialization point**: the file write was already atomic, but the race is on the STRUCT (the main goroutine mutates CurrentSub/Phase/Subs right before writing while the ticker writes the same pointer), so every run-state access in the EXECUTOR process goes through `Update(fn)`/`Read(fn)` under one mutex - a mutex inside `WriteRunState` would not have been enough. (The board process still calls `WriteRunState` directly in `launch_executor.go`/`run_control.go`; it shares the file, not the struct, and the file write is atomic.) Cross-process, the atomicity rests on the scratch file being named per WRITER (`<path>.tmp.<pid>`, 0.27.1/pm-cli-48): a shared name let two processes interleave inside one non-atomic `os.WriteFile` and rename a torn mixture, and only the `rename` publishes. Per-pid names no longer self-overwrite, so both failure paths `os.Remove` the scratch file or every failed write leaks one. The interval reaches the call site as `cmd.workerHeartbeatInterval`, a var seeded from the const purely so tests can shrink it. A nil `*RunWriter` is a no-op on every method (a bare `pm work --epic` with no manager has no run-state). Board side: the dashboard renders `♥ <age> ago` next to the elapsed clock ONLY while a worker is actually in flight - gated on `IsLive() && CurrentSession != ""` (`execHeartbeatAge` in `executor_view.go`). `CurrentSession` is pinned right before the worker spawns and cleared in `executeWork` the moment it returns (in the same breath as the heartbeat's own stop - that pairing is load-bearing, keep them together), so the gate tracks the ticker's window on both ends. Both halves were bugs found in review: gating on `IsLive()` alone false-flagged the board's launch seed plus `executor.prepare` + baseline capture (15-min caps each) as hung, and clearing `CurrentSession` only at the sub boundary did the same for the post-worker tail (`applyWorkerResult`'s project flock, then the merge or `git push`). **What the signal does and does not prove**: the ticker lives in the MANAGER process, so a fresh stamp means "the manager is alive and inside a worker", not "the worker is making progress" - a `claude -p` wedged on a network read still looks healthy until its 60m timeout. It separates a long sub from a dead/stopped manager (and from a stale run-state whose pid got recycled, which `IsLive()` alone gets wrong); detecting a wedged WORKER would need transcript-tick stamping, which this ticket deliberately did not do.
- **Kill a live run** (`K` → confirm; `killRun` + `RunState.Kill` in `run_control.go`): group-kills the manager tree (SIGTERM to `-pgid`, escalates to SIGKILL ~2s later if still alive), stamps the run-state `failed`, and parks the in-flight sub on `waiting` so the board reflects the stop. The worker is NOT in the manager's group (it leads its own - see Subprocess process groups): it dies because the manager FORWARDS the SIGTERM to the worker's group and only then re-raises on itself, all inside the board's 2s window. That handoff is why the board must signal something catchable - a SIGKILL to the manager cannot be forwarded and would orphan the worker for the rest of its `--timeout`.
- **Subprocess process groups + bounded Wait** (0.30.1, `internal/cmd/work_proc.go`; pm-cli-57): `runWorker` and `captureBaseline` spawn through `groupCmd`/`runGroupCmd`, which set `Setpgid` (own group), a `Cancel` that SIGTERMs the GROUP and escalates to SIGKILL after `procKillGrace`, and `WaitDelay` (`procWaitDelay`, 5s). Before this, `--timeout` enforced nothing: `exec.CommandContext` signalled only the `claude` process, so descendants survived, and stdout is collected through an os.Pipe every descendant inherits - `Wait` blocked until the LAST holder of the write end closed it, i.e. past the deadline forever, while the heartbeat kept stamping `running`. Two consequences worth keeping straight: (a) `exec.ErrWaitDelay` is returned by `Wait` ONLY when the command itself exited 0 (a non-zero exit always wins as `*ExitError`), so both call sites treat it as success-with-leftovers - the worker's envelope is still honoured and a baseline captured that way is still GREEN, not "no baseline"; (b) the post-Wait SIGKILL is deliberately NOT fired on a plain non-zero exit (a red baseline is routine) - only when the deadline fired or WaitDelay unblocked us, since `Wait` has already reaped the leader and the pgid could in principle be recycled. `executor.prepare` (`runPrepare`) still uses a bare `exec.CommandContext`: it writes to `*os.File`s so it cannot hang on a pipe, but its 15-min cap still only kills the direct `sh`.

- **`pm executor stats [project]`** (0.25.3, `internal/cmd/executor_stats.go`): read-only rollup of that journal, so a retro no longer starts by hand-parsing JSONL. Prints runs per kind (`work`/`run-epic`) with their terminal status, the six-outcome sub histogram, and duration/turns/cost totals + averages. Project resolution matches the other commands (arg, else `detectProjectFromCwd`); an empty, missing or corrupt-only journal prints a note and exits 0, never an error. Aggregation is a pure `aggregateJournal` (start lines paired FIFO with their terminal line by `runKey`) + `renderJournalStats`, so it is table-driven testable. `runKey` is `{id,kind,task_id,pid}`: since 0.27.0 (pm-cli-47) `id` is the journal's `run_id` and pairs lines EXACTLY - two terminal lines sharing an id are always one run (so a double kill counts once), two runs with different ids never merge (so a reused pid whose `start` was lost is no longer swallowed as its predecessor's kill-race twin - measured pre-fix: that run's subs/turns/cost vanished, and a double kill doubled them). `kind`/`task_id`/`pid` stay in the key because the leftover-start pass needs a holder pid, and because pre-0.27.0 lines have no id and fall back to the old ambiguous pairing plus its end-vs-killed heuristic. Three reads of the output need care: (1) a leftover `start` is a **crash** only when its pid is dead or its stamp is older than `liveWindow` (24h) - a live, recent pid reads as `running` instead, because stats is routinely run mid-epic, and the window is what stops a recycled pid on an ancient entry from masquerading as a live run forever; (2) `status` says how the MANAGER exited, not whether the work landed (`run_epic.go` hardcodes `done` on its end line whatever the subs did), so the real verdict is the sub histogram; (3) `pm run-epic` is re-entrant and re-records already-done/not-ready/dep-blocked subs as `skipped` on EVERY run, so the raw sub count inflates across re-runs - the output splits `N (X worker-backed, Y gate decision(s))` and tags `skipped`/`manual` rows `(gate)`, and turns/cost averages exclude them (they spawn no worker and report zeros). No `--json`/`--since` flags (not needed yet).
